# P55 — 센터 미연결 회원 온보딩

## 목표
람이 실사용자 화면(`~/Downloads/home_empty.jpeg`)을 가져왔다. 센터에 연결되지 않은 회원이
**아무것도 못 하고 당황한다**.

## 착수 시점 실태 (실측)
그 화면 자체가 자기모순이다:
- 제목 **"센터 선택"**, 부제 "센터 승인을 기다리는 중이에요"
- 경고 문구 **"아래에서 센터를 찾아 가입 요청해보세요"** — 그런데 **아래에 센터 목록이 없다**
- 실제로 있는 건 "가입 요청을 보냈어요 / 승인 대기 중" 카드와 [연결됐는지 확인] [다시 요청]뿐
- 화면 절반이 빈 여백, 홈으로 갈 길 없음

**서버가 아직 못 받는다**(이번 작업의 핵심 제약):
- `Service.JoinRequestCreate`는 **바디의 `center_id`를 의도적으로 무시**하고 `p.CenterID`를 쓴다.
  신규 사용자는 `cfg.DefaultCenterID`로 폴백하므로 **기본 센터로만** 요청이 간다.
  그 자리 주석이 이미 예고했다 — *"멀티센터로 갈 때 '그 센터의 회원인가'를 검증하는 자리가 여기다"*.
  (종전 구현이 바디 값을 그대로 믿어 존재하지 않는 센터로도 200이 나갔고, 남의 센터 큐에
  요청을 밀어넣을 수 있었다. 그래서 막아 둔 것이지 "필요 없어서" 뺀 게 아니다.)
- **회원용 센터 목록 API가 없다** — `GET /v1/admin/centers`는 superadmin 전용.

## 결정 사항

### 0. 요청의 처방 두 개를 기각했다 — 진단은 맞고 처방이 일렀다
람의 원안은 ①홈에 먼저 들여보내기 ②센터 목록에서 골라 가입 신청이었다. 세 팀이 독립적으로
같은 결론에 도달했고, 저장소의 기존 설계 문서(`PT데스크_설계_04` §4)도 같은 방향이었다.

**①홈 진입** — 홈·예약·기록·마이 네 탭의 뷰모델이 전부 `memberId == null`이면
`AuthFailure('로그인이 필요해요')`를 던진다. 전화 인증을 방금 끝낸 사람에게 하는 거짓말이고,
[다시 시도]는 세션을 만들지 않아 **무한 루프**다. 촬영 탭은 더 나쁘다 — throw가 아니라
**조용히 return**이라 사진 4장을 찍고 저장을 눌러도 아무 일도 아무 말도 없다(당황이 아니라
데이터 손실). **정직한 막다른 길 1개가 부정직한 막다른 길 5개가 된다.**

**②센터 목록** — 목록에 넣을 센터가 없다. `ListCenters`가 `if c.Name == "" { continue }`로
거르는데 운영 센터가 신원 미등록이다. 게다가 이름·전화·주소를 입력할 API가 아예 없었다.
목록 UI를 만들어도 화면은 여전히 비고, 지금의 자기모순이 형태만 바꿔 남는다.
**2호점이 실제로 생기면 필요하고, 그때 답은 목록이 아니라 데스크 QR이다.**

### 1. 대기실(Lobby) — 게이트를 옮기지 않고 게이트를 화면답게 만든다
- **판별자를 5개 → `stage` 하나로.** 종전엔 제목=고정 문자열, 부제=stage, 상단 카드=bool
  else 체인, 하단 카드=`joinRequestedAt`이라 **요청 대기 중에 "찾지 못했어요" 경고와
  "승인 대기 중" 카드가 동시에** 떴다(람이 가져온 그 화면). 게다가 그 경고 문구가 가리키는
  '아래' 카드는 **하필 대기 중일 때만 사라진다**. 계산을 한 곳에 모으면 그 조합이 안 만들어진다.
- **거짓 문구 3건 제거**: 제목 "센터 선택"(고를 목록 없음) / "아래에서 센터를 **찾아**"(검색·목록
  없음) / "여러 센터 이용 가능 — 홈 상단에서 전환"(전환 UI는 P54에서 제거, `UserIndex`는 uid당 1건).
- **빈 `Spacer()` 자리에 센터 연락 카드.** 미연결의 다수 원인은 "센터를 못 골라서"가 아니라
  **등록 번호 불일치·미등록**이고, 전화 한 통이면 데스크가 고쳐 다음 재확인에 `join/match`가
  붙는다 — 승인 큐를 거치지 않는 가장 빠른 경로다. **번호가 없으면 통화 버튼을 그리지 않는다.**
- **주 버튼을 탈출 → 진행으로.** `notFound`의 primary가 "다른 번호로 다시 시도"였다.
  정작 해야 할 일이 회색 행 한 줄에 숨어 있어 우선순위가 뒤집혀 있었다.

### 2. 대기 상태의 주인을 로컬 → 서버로 (계약 v2.27)
`GET /v1/me`에 `join_request{status, created_at}`(미연결일 때만). 종전엔 그 사실이 **기기
SharedPreferences에만** 있어서 기기를 바꾸거나 앱을 지웠다 깔면 "요청한 적 없음"으로
오분류됐고, 사용자가 같은 요청을 또 보냈다 — **그 중복이 대표 어드민을 죽이던 재료다.**

### 3. 조사가 찾아낸 CRITICAL 3건 (전부 이미 배포돼 있던 결함)
**C-1 어드민 전체 다운(즉시 수리·배포)** — 서버는 `created_at`인데 어드민 타입이
`requested_at`을 읽어 값이 항상 `undefined`. `Array.sort`는 원소 2개 이상일 때만 비교자를
부르므로 **가입 요청이 2건 되는 순간** `undefined.localeCompare`로 터졌고, `ErrorBoundary`가
`AdminShell` 전체를 감싸 **어드민 앱 통째로** 폴백이 됐다. 큐를 줄이려면 승인해야 하는데
승인 버튼이 있는 화면을 열 수 없는 **데드락**이었다(거절·삭제 API도 없었다). node로 재현 확인.

**C-2 좀비 요청이 회원 기록을 통째로 날린다** — 앱으로 먼저 요청(pending) → 대표가 데스크에서
등록 → 회원이 재인증해 정상 연결(회원권·예약이 붙음) → **①의 pending이 그대로 남음**
(`JoinConfirm`이 큐를 안 건드림) → 며칠 뒤 대표가 큐 정리하다 승인 → `SaveMember`가 빈
레코드를 새로 만들고 `SaveUserIndex`가 신원을 그리로 옮긴다 → **회원권·예약·기록·체형사진
전부 상실**, 되돌릴 API 없음. → A-4(승인 가드) + A-5(연결 시 큐 파기)로 원인·방어선 양쪽.

**C-3 미연결 계정은 자기 이름·전화번호를 지울 수 없다** — 탈퇴가 `p.MemberID == ""`에서 404로
막혀 P53이 만든 `DeleteJoinRequestsByUID`에 도달할 경로가 **회원이 된 사람에게만** 열려 있었다.
`join_requests`에는 이름·전화번호 원본이 담긴다. **가장 오래 남는 개인정보가 가장 덜 관여한
사람의 것**인 상태였다(개인정보보호법 §36).
