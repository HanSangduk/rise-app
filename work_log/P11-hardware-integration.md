# P11 — 하드웨어 실연동

## 목표

화면과 서버 규칙은 이미 다 있는데 **하드웨어만 안 붙어 있던** 세 가지를 실물로 연결한다.
셋 다 "껍데기 UI + TODO 주석" 상태였음을 코드로 확인했다:

| 기능 | 현재 상태(확인됨) | 붙일 것 |
|---|---|---|
| 셀프 체크인 | 버튼을 누르면 **확인 다이얼로그**가 뜬다(코드 주석: *"데모: 실제 스캐너 연동 전"*). 빌드 시 심은 토큰 문자열을 그냥 전송 | `mobile_scanner`로 실제 QR 스캔 + 어드민에 데스크용 QR 인쇄 화면 |
| 체형 촬영 | **카메라 패키지 자체가 없다**(`camera`·`image_picker` 미설치, `CameraController` 사용처 0건). 오버레이 UI만 있고 뒤에 영상이 없다. 사진은 서버로 안 간다 — JSON 메타데이터만 보내고 `storage_path`는 스텁 | `camera` + `firebase_storage`(P09에서 버킷 생성 완료) |
| 수평계 | `sensors_plus` 미설치. 버튼으로 각도를 토글하는 `LevelSimulator` | `sensors_plus` 가속도계 |

서버 쪽은 이미 준비돼 있다 — 셀프 체크인은 토큰 대조 + **예약 시작 ±30분** 시간창 + 본인 확정
예약 자동 탐색까지 구현·검증됨. 즉 스캐너만 붙이면 나머지는 동작한다.

## 결정 사항

### ⚠ 구현 전에 먼저 막은 것 — 내가 P09에서 만든 공개 버킷
체형사진이 올라갈 버킷(`rize-218c1.firebasestorage.app`)이 **익명 전체 공개** 상태였다.
P09에서 트레이너 사진 하나를 앱에 띄우려고 `allUsers:objectViewer`를 버킷 **전체**에 걸었기
때문이다. 그때는 사진 1장뿐이라 무해했지만, **이번 작업이 회원 체형사진(P8 민감정보)을 같은
버킷에 올린다** — 그대로 두면 URL만 알면 남의 체형사진이 열리는 상태가 된다.

균일 버킷 수준 액세스를 켜 둔 탓에 객체별 ACL로 예외를 둘 수도 없어서, **공개 IAM을 걷어내고
트레이너 사진은 Firebase 다운로드 토큰 URL로 바꿨다**(객체 하나에만 유효하고 언제든 회수 가능).
실측: 회수 후 `storage.googleapis.com` 익명 접근 **403**, 토큰 URL **200**.
Firestore의 `profile.photo_url`도 새 URL로 교체 완료.

교훈: "지금 있는 데이터"가 아니라 **"곧 들어올 데이터"** 기준으로 권한을 정해야 한다.

- **버전(2026-08-23 pub.dev·npm API로 확인, 기억 아님)**: `mobile_scanner 7.4.0`(2026-07-20) ·
  `camera 0.12.0+2`(2026-07-13) · `sensors_plus 7.1.0`(2026-06-26) ·
  `firebase_storage 13.4.6`(2026-08-03) · `permission_handler 13.0.1`(2026-08-11) ·
  어드민 `qrcode.react 4.2.0`
- **실기기**: 갤럭시 S21 울트라(SM-G998N) · Android 14 / SDK 34. 실카메라·실센서로 검증한다.
- **Storage 경로·규칙을 내가 먼저 확정했다**(`storage.rules` 신규, 배포 완료).
  구현이 경로를 고른 뒤 규칙을 맞추면 어긋날 때 한 사이클을 버리므로 순서를 뒤집었다.
  - 체형사진 `members/{memberId}/body/{파일}` — **쓰기는 본인 + 민감정보 동의 + image/* + 10MB 미만**,
    읽기는 본인·대표·담당 트레이너(동의 있을 때)로 **백엔드 `checkBodyPhotoAccess`와 같은 조건**,
    **삭제 금지**(파일만 지우면 서버 메타데이터가 가리키는 곳이 비는 고아가 된다).
  - 트레이너 사진 `staff/photos/**` — SDK 접근 전면 차단. 서버가 올리고 클라이언트는
    **다운로드 토큰 URL**로만 읽는다(토큰 URL은 규칙을 거치지 않는다).
  - 신원 매핑: Storage 규칙은 `request.auth.uid`만 알아서 Firestore `users/{uid}`(UserIndex)와
    `centers/rise/members/{id}`를 `firestore.get`으로 건너가 확인한다. 접근마다 읽기가 붙지만
    단일 센터 규모에선 정확성이 우선.

## 사후 발견 — 체형사진이 실제로는 저장되지 않고 있었다 (2026-08-23, 사용자 제보)

람이 앱에서 사진을 찍고 저장했더니 "권한이 없다"며 실패. **P11이 만든 결함이다.**

원인: Storage 규칙이 `firestore.get`으로 Firestore를 건너 읽는데(교차 서비스 규칙),
그러려면 Cloud Storage 서비스 에이전트에 `roles/firebaserules.firestoreServiceAgent`가 필요하다.
Firebase 콘솔·CLI로 배포하면 그 자리에서 권한 부여를 물어보는데, **ADC가 다른 계정에 묶여 있어
firebaserules REST로 직접 배포**했고(P07에서 확인된 제약) 그 단계가 통째로 빠졌다.

**왜 P11 검증을 통과했나** — TestRuleset으로 3건(익명 읽기·미정의 경로·staff SDK 접근) 거부를
확인했지만, TestRuleset은 `firestore.get`을 **functionMocks로 모킹**한다. 즉 시뮬레이터는
"Firestore를 읽을 수 있다"고 가정하고 평가하므로 이 결함을 **원리적으로 못 잡는다.**
게다가 P11 당시엔 버킷에 객체가 사실상 없어 실제 업로드를 한 번도 시도하지 않았다.

조치: 권한 부여 후 실기기에서 촬영→업로드→서버기록 정상 확인(사진 223KB, `storage_path` 일치,
앱이 다음 포즈로 진행). 함정 두 가지(IAM 권한, **평가당 고유 문서 2개 상한**)를 `storage.rules`
헤더 주석에 남겼다.

### 진단 과정의 자기 오류
만료된 ID 토큰(발급 후 2시간 경과)으로 계속 403을 받으며 "교차 서비스 권한 문제"라고 결론 낼
뻔했다. 만료 토큰은 무엇을 해도 403이라 **어떤 가설도 검증하지 못한다.** `firestore.get`을 쓰지
않는 프로브 경로도 403인 것을 보고서야 인증 자체를 의심했다.
교훈: 403을 해석하기 전에 **토큰 exp부터 본다.**

부수 발견: `gcloud storage rm`은 owner 계정으로도 403이 나는데 Storage JSON API DELETE는 204로
성공한다. 삭제 경로가 없는 게 아니라 gcloud 쪽 문제다(원인 미확인).

## 후속 작업

- **실기기 검증에서 새로 찾은 결함**: 셀프 체크인 버튼이 **시간이 지나도 스스로 열리지 않는다**.
  19:00 예약의 창은 18:30에 열리는데, 앱을 켜 둔 채 18:32까지 기다려도 버튼은 회색이고
  **당겨서 새로고침해야** 활성화된다. 회원은 로비에서 기다리다 데스크로 간다 — 셀프 체크인이
  없애려던 왕복 그 자체다. 판정이 홈 로드 시점에 굳는 게 원인이라 같은 클래스(취소 컷오프
  경계·"지남" 판정·자정 넘김)를 함께 조사 중.
- 검증 중 데모 회원(김민지)에게 `2026-08-23 19:00` 확정 예약이 하나 생성됐다. 컷오프 안이라
  취소하면 세션이 차감되고 원장에 남아 그대로 뒀다.

## 실기기 워크스루 — 하네스가 나를 세 번 속였다

검증 자체보다 **하네스의 거짓 성공**이 더 배울 게 많았다. 넷 다 "화면은 멀쩡히 찍히고
로그도 조용해서 성공처럼 보이는" 형태였다 — 결과를 안 열어봤으면 전부 통과로 보고했을 것이다.

| 무엇 | 어떻게 속였나 | 어떻게 막았나 |
|---|---|---|
| **스테일 APK** | 설치본이 `http://localhost:8080`을 보는 로컬 빌드였다. 화면엔 "연결이 불안정해요"만 떠서 **백엔드 회귀처럼** 보였다 | 실행 전 APK의 Dart 스냅샷에서 base URL을 뽑아 운영 URL이 아니면 **중단** |
| **빌드 실패 무시** | `flutter build`가 실패했는데 스크립트가 그대로 진행해 **직전 설치본으로** 워크스루를 돌렸다. "총 캡처 14 · 오류 없음"까지 나왔다 | `PIPESTATUS`로 종료코드를 살려 실패 시 중단 |
| **권한 순서** | `pm grant` → `pm clear` 순이라 clear가 권한을 되돌렸다. 정상 경로를 찍는다고 생각한 실행이 실제로는 권한 요청 화면을 찍고 있었다 | clear **뒤에** grant |
| **BACK이 앱을 나감** | 지난 슬롯엔 시트가 안 열리는데 BACK을 눌러 앱이 백그라운드로 갔고, 이후 캡처가 런처·삼성 카메라였다 | 단계마다 `am start`로 앱을 앞으로 끌어옴 |

탭 좌표도 네 곳이 빗나갔다(버튼 상단 경계·코드 화면 오프셋·CTA 아래 링크 영역·**탭바인 줄 알았던
시스템 내비게이션 바**). 전부 실측 캡처로 보정했다.

### 유령을 쫓을 뻔한 것
모든 화면 오른쪽 가장자리에 **콘텐츠 높이에 맞춰 따라오는 흰 카드**가 잘려 보였다. 로그인 화면은
단순 Column이라 가로 스크롤이 없는데도 그랬고, 앱 루트에도 전역 래퍼가 없었다. UI 결함으로
보고하기 직전에 Chrome을 띄워 같은 자리를 찍어보니 **똑같이 있었다** — 삼성 엣지 패널 핸들
(`com.samsung.app.honeyspace.edge.CocktailBarService`, 윈도우 목록으로 확인)이다.
홈 화면에서만 숨겨져서 처음 대조군으로 쓴 런처 캡처에는 안 나왔고, 그래서 앱 것처럼 보였다.

## 검증

- 네 하드웨어가 껍데기가 아니라 실물 API를 쓰는 것을 확인:
  `MobileScanner`(qr_scan_screen) · `CameraController`(body_camera_provider, camera_preview_layer) ·
  `accelerometerEvent`(level_simulator_provider) · `FirebaseStorage`(body_photo_uploader)
- **경로가 배포된 보안 규칙과 일치한다** — 구현이 경로를 고른 뒤 규칙을 맞추면 어긋날 때 한 사이클을
  버리므로 규칙을 먼저 확정했는데, 실제로 `BodyPhotoStoragePath`가 그 규칙에서 제약을 역산해
  주석으로 남겼다: 세그먼트 정확히 4개(날짜를 폴더로 파면 `{fileName}` 와일드카드가 매칭 실패) ·
  경로 키는 uid가 아니라 **memberId** · `image/*` + 10MB 미만.
  재시도는 같은 경로를 재사용해 실패 조각이 버킷에 유령으로 쌓이지 않게 했다.
- 권한 선언: Android `CAMERA` + `uses-feature required=false`,
  **카메라 플러그인이 딸려 붙이는 `RECORD_AUDIO`를 `tools:node="remove"`로 제거**
  (없으면 스토어 심사에서 쓰지도 않는 마이크 권한을 설명해야 한다).
  iOS `NSCameraUsageDescription`에 두 용도(체크인 QR·체형 촬영)와 열람 범위를 함께 적었다.
