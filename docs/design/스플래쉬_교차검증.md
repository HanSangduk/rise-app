## A-1. 🔴 CRITICAL — 2200ms 타임아웃은 "센터를 찾지 못했어요"를 만든다

### 문서가 주장하는 것

> `/login/center-confirm`인 이유: 새 정책이 아니라 **이미 있는 답이다** — `restoreLandingRoute`가 `RestoreOutcome.unknown`에 대해 고르는 바로 그 라우트(`session_restore.dart:52`).
> — 스플래쉬_모션.md §5-5

### 왜 틀렸는가

`unknown` 착지는 **라우트 하나가 아니라 라우트 + 상태 한 쌍**이다. `session_restore.dart`가 `/login/center-confirm`을 돌려주기 **전에** 세 가지를 더 한다:

```dart
// session_restore.dart:92-102
final record = await store.read();                       // ① 대기 기록 로드
...
if (pending != null) notifier.restorePendingJoinRequest(pending);   // ② 대기 카드 복원
if (result case Err(:final failure) when outcome == RestoreOutcome.unknown) {
  notifier.markConnectionUnknown(failure);               // ③ connectionUnknown = true
}
```

`.timeout(...)`은 **`await restoreLanding!()`이 반환하는 Future만** 대체한다. Dart Future는 취소되지 않으므로 위 ①②③은 **여전히 실행되지 않은 채**이고, 라우터만 먼저 착지한다.

그 상태로 `CenterConfirmScreen`이 그려지면 stage 분기가 이렇게 떨어진다:

```dart
// auth_state.dart:95-101
CenterConfirmStage get centerConfirmStage {
  if (match?.member != null) return CenterConfirmStage.matched;      // match == null      ✗
  if (joinRequestedAt != null) return CenterConfirmStage.pendingApproval; // ①이 안 돌았다 ✗
  if (matchDeclined) return CenterConfirmStage.declined;             // false              ✗
  if (connectionUnknown) return CenterConfirmStage.connectionUnknown;// ③이 안 돌았다      ✗
  return CenterConfirmStage.notFound;                                // ← 여기로 떨어진다
}
```

### 사용자가 실제로 보는 화면

로그인돼 있고 센터에 **정상 연결된** 회원이, 지하철에서 앱을 켠 것뿐인데:

| 요소 | 내용 | file:line |
|---|---|---|
| 부제 | **"이 번호로 등록된 센터를 찾지 못했어요"** | `center_confirm_screen.dart:81` |
| 카드 | **"이 번호로 등록된 회원 정보를 찾지 못했어요. 아래에서 센터를 찾아 가입 요청해보세요."** | `center_confirm_screen.dart:582-584` (`_NotFoundCard`) |
| 그 아래 | `_JoinOtherCenterCard` — **가입 요청 시트로 가는 탭 영역** (stage != connectionUnknown이므로 노출) | `center_confirm_screen.dart:107-110` |
| 주 CTA | **"다른 번호로 다시 시도"** (primary 버튼) | `center_confirm_screen.dart:288-294` |
| 빨간 에러 문구 | **없다** (`state.error == null`) | `center_confirm_screen.dart:112` |

즉 앱이 **"당신은 우리 회원이 아닙니다"라고 단정**하고, **가입 요청을 권하고**, 탈출구로 **로그아웃**을 제시한다.

### 왜 이게 특히 나쁜가 — 이 코드베이스가 이미 고쳤던 버그다

`session_restore.dart:22-32`가 자기 주석으로 정확히 이 사고를 기록하고 있다:

> 예전엔 실패를 전부 같게 봐서, 이미 연결된 회원이 지하철에서 앱을 켜면 "미연결"로 오독돼 승인 대기 화면(또는 온보딩)에 떨어졌다 — 그 화면에서 사용자가 할 수 있는 건 가입 **재요청**뿐이라, **대표 화면에 같은 사람이 한 줄 더 쌓이는 것**으로 끝났다.

`classifyRestore`는 그 버그를 고치려고 쓴 함수다. **`.timeout`을 `restoreLanding` 바깥에 걸면 그 함수를 우회해서 같은 버그를 그대로 재현한다.** 스플래시 작업이 앱에서 제일 신중하게 설계된 부분 하나를 되돌리는 셈이다.

### 2차 피해 두 가지

1. **주 CTA가 로그아웃이다.** `_restart` → `restartWithNewPhone()` → `authRepository.signOut()` (`auth_view_model.dart:381-386`, `center_confirm_screen.dart:167-170`). 네트워크가 느렸을 뿐인 회원이 primary 버튼 한 번에 **Firebase 로그아웃 + SMS 인증 처음부터**로 간다. SMS 비용과 재인증 마찰이 순수 손실이다.
2. **중복 가입 요청이 백엔드에 쌓인다.** `_JoinOtherCenterCard`가 노출되므로 사용자가 그쪽을 누르면 `POST /v1/join/request`가 나간다 — 위 주석이 "대표 화면에 한 줄 더 쌓인다"고 한 바로 그 행위다.

### 늦게 도착하는 결과가 화면을 뒤집는다

`restoreAuthLanding`은 취소되지 않으므로 ~20초 뒤 계속 진행해 ③ `markConnectionUnknown`을 부른다. 그러면 화면이 `notFound` → `connectionUnknown`으로 **사용자 조작 없이 스스로 바뀐다**. 그 전에 사용자가 이미 로그아웃했거나 가입 요청을 보냈으면 되돌릴 수 없다.

> **수정**: §A-11. 타임아웃을 `loadSession()` 한 줄로 내리면 ①②③이 전부 정상 실행되고 이 문단 전체가 사라진다.

## A-2. 🔴 CRITICAL — 라우터 타임아웃은 게이트를 내리지 못한다 (20초 로고)

### 두 코드 조각을 합치면 무슨 일이 벌어지는가

문서가 제안한 두 조각이다:

```dart
// 스플래쉬_모션.md §5-4 — appReady를 finally로 보장
createRouter(restoreLanding: () async {
  try   { return await restoreAuthLanding(ref); }
  finally { ref.read(appReadyProvider.notifier).markReady(); }   // ← F1이 완료될 때 실행
});

// 스플래쉬_모션.md §5-5 — 라우터 예산
final landing = await restoreLanding!()          // ← F1
    .timeout(const Duration(milliseconds: 2200), // ← F2 = F1에 타임아웃을 씌운 별개 Future
             onTimeout: () => '/login/center-confirm');
```

- `F2`는 2200ms에 완료된다 → **라우터는 착지한다.**
- `F1`은 취소되지 않는다(Dart Future는 취소 불가). `finally`는 `restoreAuthLanding`이 **실제로 끝날 때** 실행된다 = dio `connectTimeout 10s + receiveTimeout 10s`(`api_config.dart:11-12`) → **~20초 뒤.**
- 게이트는 `appReady` 하나만 본다(문서 §5-2: "게이트는 `appReady`(= `restoreLanding()`이 반환됐다) 하나만 본다").

**결과: 라우터는 2.2초에 착지했는데 게이트는 20초까지 안 내려간다.**

| | 오늘 | 계획대로 구현했을 때 |
|---|---|---|
| 0 ~ 2.2s | 빈 화면 | 크림 + 마크 (개선) |
| 2.2 ~ 20s | 빈 화면 | **크림 + 마크** (라우터는 이미 착지, 사용자는 못 봄) |
| 20s | 센터 확인 화면 | 센터 확인 화면 |
| **최악 총 대기** | **~20초** | **~20초 — 개선 0** |

문서 §5-3 표의 마지막 줄 **"20초+ → 2.5초"** 는 **성립하지 않는다.** 라우터 예산은 사용자가 볼 수 없는 라우팅 결정만 앞당길 뿐이고, 사용자 체감 대기는 1ms도 줄지 않는다. 문서 전체에서 "이 설계가 혼자서는 못 고치는 것 하나"라며 §5-5를 **선행 조건**으로 못박았는데(§0-5), 그 선행 조건이 실제로는 아무 효과가 없다.

### 그리고 이건 §A-1과 한 쌍이다

이 결함의 **가장 자연스러운 수정**은 `onTimeout`에서 게이트도 같이 내리는 것이다:

```dart
onTimeout: () { markReady(); return '/login/center-confirm'; }   // ← 이걸 하는 순간 §A-1이 켜진다
```

그러면 2.2초에 게이트가 내려가고 — **§A-1의 "센터를 찾지 못했어요" 화면이 그대로 드러난다.** 지금은 20초 로고가 그 화면을 가려주고 있어서(그리고 20초 시점에 ③이 실행돼 화면이 `connectionUnknown`으로 고쳐져서) 우연히 안 보이는 것뿐이다.

> **두 결함은 반드시 함께 고쳐야 한다.** 한쪽만 고치면 다른 쪽이 사용자에게 노출된다. 유일하게 둘 다 닫는 수정이 §A-11이다.

## A-3. 🟢 반박 실패 — `MaterialApp.builder` 오버레이는 실제로 전부 덮는다

람의 질문: *"builder의 오버레이가 정말 다 덮나? 루트 내비게이터에 push된 dialog/route는?"*

**답: 덮는다. SDK 소스로 확인했다.**

```
WidgetsApp                                          (widgets/app.dart:1813~)
 └ RootRestorationScope > SharedAppData > Shortcuts > ... > Localizations   ← Directionality·MediaQuery 제공
    └ Title
       └ Builder → MaterialApp._materialBuilder                             (material/app.dart:1019)
          └ AnimatedTheme
             └ ScaffoldMessenger                                            (material/app.dart:1047)
                └ DefaultSelectionStyle
                   └ Builder → ★ widget.builder(context, child) ★           (material/app.dart:1042)
                                        │
                                        └ child = routing = Router.withConfig(...)   (widgets/app.dart:1715,1725)
                                             └ GoRouterDelegate.build → RouteBuilder (delegate.dart:216)
                                                  └ Navigator (루트) → Overlay → 모든 라우트·다이얼로그·시트
```

따라서 `builder` 안에서 `child` 위에 얹은 위젯은 **루트 Navigator의 Overlay보다 위**에 있다:

| 대상 | 덮이나 | 근거 |
|---|---|---|
| 모든 GoRoute 화면 | ✅ | 전부 `Navigator` 아래 |
| `showDialog(useRootNavigator: true)` — 이 앱이 실제로 쓴다 | ✅ | 루트 Navigator = `child` 안 (`center_confirm_screen.dart:179`) |
| `showModalBottomSheet` | ✅ | 동일 |
| SnackBar | ✅ | `ScaffoldMessenger`는 위지만 **그리는 건 `Scaffold`** = 아래 |
| Flutter 에러 위젯(빨간 화면) | ✅ | ← **부작용**, 아래 참조 |
| 네이티브 다이얼로그(권한·키보드·reCAPTCHA) | ❌ | Flutter 밖. 기동 구간엔 등장하지 않음 |

**게이트에 필요한 InheritedWidget은 전부 위에 있다** — `Theme`(AnimatedTheme), `Directionality`/`MediaQuery`/`Localizations`(WidgetsApp), `ProviderScope`(`main.dart:12`, `runApp`보다 위). 구조적 문제 없음.

### 다만 "다 덮는다"가 곧 리스크다 — 라우팅으로 탈출할 수 없다

게이트가 Router **위**에 있으므로 **어떤 `context.go()`도 게이트를 걷어낼 수 없다.** `/splash` 라우트였다면 라우팅이 곧 탈출구였겠지만, 이 구조에서는 게이트 자신의 상태 기계만이 유일한 출구다.

그런데 문서 §5-5는 **게이트 자체 타임아웃을 명시적으로 금지**하고, 릴리스에는 안전망을 두지 않는다:

> 게이트에 자체 타임아웃을 두면 안 된다. … **디버그 안전망**: 릴리스에 천장을 넣는 대신, 디버그 빌드에서 게이트가 5초 넘게 살아 있으면 `assert`로 알린다.

**`assert`는 릴리스 빌드에서 컴파일 시 제거된다.** 즉 릴리스에는 안전망이 **0개**다. `markReady()`가 어떤 이유로든 안 불리면(§A-2가 바로 그 사례다) 앱은 **브랜드 로고를 띄운 채 영구 정지**한다. `IgnorePointer`까지 걸려 있으면 사용자가 할 수 있는 건 강제 종료뿐이고, 재실행해도 같은 경로를 탄다.

> **권고 (HIGH)**: 게이트에 **릴리스에서도 살아 있는 절대 상한**을 둔다. 미학이 아니라 벽돌 방지용이다 — 예산(2.2s)의 3~4배쯤(예: 8초)에서 무조건 `gone`으로 전이하고, 디버그에서는 `assert`도 함께 남긴다. 문서의 "천장은 빈 화면을 만들 뿐"이라는 논거는 **§A-11 수정 이후에는 애초에 도달할 수 없는 경로**를 막는 이야기이므로, 비용이 0이고 얻는 건 "브랜드 로고에 갇힌 앱"의 제거다.

### 부작용 — 디버그에서 Flutter 에러 화면을 가린다

게이트가 불투명한 동안 `HomeScreen`이 빌드 중 예외를 던지면, 빨간 `ErrorWidget`이 **게이트 아래**에 그려진다. 개발 중 "스플래시가 안 끝나네"의 실제 원인이 빌드 에러인 상황이 생긴다. 심각도 낮음이지만, 위 절대 상한이 있으면 자동으로 드러나므로 같이 해결된다.

## A-4. 🟠 HIGH — 퇴장 트리거가 틀렸다: `appReady`가 아니라 "라우터가 라우트를 가졌다"

`appReady`는 **"복원 함수가 반환했다"** 를 뜻하지 **"목적지가 그려졌다"** 를 뜻하지 않는다. 그 사이에 최소한 이만큼이 남아 있다:

1. `restoreAuthLanding`의 `finally` → `markReady()` (동기)
2. → `redirect`가 값을 반환
3. → `GoRouteInformationParser`의 Future 완료
4. → `Router`가 `setState` → 다음 프레임에 리빌드
5. → `GoRouterDelegate.currentConfiguration`이 채워짐 → `builder.dart:101`의 empty 분기 탈출

**1번과 5번 사이에 최소 1프레임, 스케줄링에 따라 2프레임이 있다.** 그 동안 `child`는 여전히 `SizedBox.shrink()`다. 게이트가 그 시점에 크로스페이드를 시작하면 **크림이 "빈 창"으로 페이드아웃**한다 — 이 설계가 없애려던 바로 그 화면으로.

문서 §6-1은 `addPostFrameCallback`으로 "목적지에 한 프레임을 준다"고 했지만 그건 **프레임 수를 가정**한 것이고, 스케줄링 순서를 보장하지 않는다. 게다가:

```dart
// flutter/packages/flutter/lib/src/scheduler/binding.dart:818-834
void addPostFrameCallback(FrameCallback callback, {String debugLabel = 'callback'}) {
  assert(...);
  _postFrameCallbacks.add(callback);     // ← 리스트에 넣기만 한다. scheduleFrame()을 부르지 않는다.
}
```

**`addPostFrameCallback`은 프레임을 예약하지 않는다.** 다른 무언가가 프레임을 예약해야만 콜백이 돈다. 실무에서는 Router의 `setState`가 예약해 주지만, 그건 **우연히 맞는 것**이지 설계된 보장이 아니다.

### 더 나은 트리거 — 이미 공개 API로 존재한다

```dart
// go_router-16.3.0
class GoRouterDelegate extends RouterDelegate<RouteMatchList> with ChangeNotifier { … }  // delegate.dart:19-20
RouteMatchList currentConfiguration = RouteMatchList.empty;                               // delegate.dart:211
late final GoRouterDelegate routerDelegate;                                               // router.dart:362
```

`GoRouter.routerDelegate`는 `ChangeNotifier`이고 `currentConfiguration`은 공개 필드다. 게이트가 이걸 구독해 **`currentConfiguration.isNotEmpty`** 를 퇴장 조건으로 쓰면:

- **"목적지가 확정됐다"를 직접 관측한다** — 프레임 가정이 사라진다.
- **`appReadyProvider`가 통째로 불필요해진다** — 새 Notifier도, `finally` 계약도, "누가 markReady를 부르는가" 문제도 없다. `app.dart`·`app_router.dart`·`session_restore.dart` **어느 것도 안 고쳐도 된다**(문서 §6-1이 자랑한 성질이 오히려 더 강해진다).
- **§A-2가 구조적으로 불가능해진다** — 라우터가 착지하는 순간이 곧 게이트가 나가는 순간이므로, 어떤 타임아웃 조합에서도 둘이 어긋날 수 없다.
- 기동경로 문서 §10-2의 요구("스플래시의 종료 조건은 시간이 아니라 **착지 라우트 확정**")를 **문자 그대로** 만족한다. `appReady`는 그 요구의 근사치일 뿐이었다.

> 게이트는 `_router` 인스턴스를 생성자로 받으면 된다(`app.dart:40`에 이미 있다). 게이트는 Router **위**에 있어 `GoRouter.of(context)`를 못 쓴다 — 이건 오히려 좋다. "게이트는 절대 내비게이션하지 않는다"가 타입 수준에서 강제된다.

## A-5. 🟢 반박 — 세션 만료 리다이렉트는 이 설계에서 위험하지 않다 (단, 조건부)

람의 질문: *"로그아웃된 사용자가 스플래시 뒤에서 홈에 앉을 수 있나?"*

**기동경로 문서 §6.3이 그린 시나리오는 이 설계에는 적용되지 않는다.** 그 시나리오의 전제는 "스플래시가 **타이머로** 목적지를 정한다"인데, 채택안의 게이트는 목적지를 정하지 않고 가리기만 한다. 실제 순서를 끝까지 따라가 보면:

| t | 일어나는 일 | 근거 |
|---|---|---|
| 0 | 게이트 위, 세션 null | |
| ~0.5s | `/v1/me` Ok → `sessionProvider.set(value)` | `session_restore.dart:83` |
| | `app.dart:56` 리스너: `prev == null` → **무시** (정상) | `app.dart:56` |
| ~0.5s | landing `/home`, 라우터 착지, 게이트 퇴장 시작 | |
| ~0.9s | 홈의 6개 호출 중 하나가 401 → `sessionProvider.clear()` | `dio_client.dart:36-39` |
| | `prev != null && next == null` → `_router.go('/login')` **발동** | `app.dart:55-58` |
| ~0.9s | 라우터가 `/login`으로 이동 — **게이트는 이미 투명해지는 중이거나 사라졌다** | |

게이트는 라우팅에 개입하지 않으므로 **로그아웃된 사용자가 홈에 앉는 일은 없다.** 최악은 퇴장 크로스페이드(280ms) 도중에 아래 화면이 홈→로그인으로 바뀌어 **화면 두 개가 겹쳐 보이는 것**이고, 이건 심각도 LOW다.

**단, 조건이 있다.** 위 결론은 다음 두 가지가 지켜질 때만 성립한다:

1. 게이트가 **절대 `router.go()`를 부르지 않는다** — §A-4의 트리거를 쓰면 게이트에 Router 접근 자체가 읽기 전용이 되어 구조적으로 보장된다.
2. 게이트가 **인위적 최소 노출 시간을 갖지 않는다** — 문서 §8-1이 이미 금지했고, 그 금지가 유지되는 한 §6.3의 경합은 재현 불가능하다.

> **§6.3은 "채택안의 결함"이 아니라 "채택안이 왜 그렇게 설계됐는지의 근거"다.** 문서가 그걸 명확히 하지 않아 실제보다 위험해 보인다.

### 경우 2 — 401은 스플래시와 무관하게 이미 모순된 화면을 만든다

토큰이 폐기된 사용자(계정 삭제·다른 기기 탈퇴)의 경로:

```
GET /v1/me → 401
  → guardApi:24-25   Err(AuthFailure('로그인이 만료됐어요 — 다시 로그인해주세요'))
  → classifyRestore:36  MemberNotLinkedFailure가 아니므로 → RestoreOutcome.unknown
  → restoreLandingRoute:52 → '/login/center-confirm'
  → markConnectionUnknown(failure) → stage = connectionUnknown
```

같은 화면에 서로 모순되는 두 문장이 **동시에** 뜬다:

| 위치 | 문구 | file:line |
|---|---|---|
| 카드(회색) | "연결 상태를 불러오지 못했어요. **네트워크가 돌아오면** 아래에서 다시 확인해주세요. **이미 연결된 회원이라면 그대로 홈으로 들어가요.**" | `center_confirm_screen.dart:617-619` |
| 에러(빨강) | "**로그인이 만료됐어요 — 다시 로그인해주세요**" | `api_result_guard.dart:25` → 표시 `center_confirm_screen.dart:113-117` |
| 주 CTA | "연결됐는지 다시 확인" — **누를 때마다 401, 영원히 실패** | `center_confirm_screen.dart:576-580` |

그리고 dio 인터셉터가 `sessionProvider.clear()`를 부르지만(`dio_client.dart:37`) 복원 중이라 `prev == null`이므로 `app.dart:56`이 무시한다 — **자동 복귀가 발동하지 않는다.**

**스플래시가 만드는 차이**: 이 막다른 화면에 도달하는 시간이 늘어난다(401은 빠르므로 실제로는 등장 350ms + 퇴장 280ms ≈ 630ms). 심각한 악화는 아니지만, **스플래시 작업이 이 화면으로 보내는 사용자 수를 늘리므로**(§A-1의 타임아웃 경로가 추가된다) 함께 고쳐야 한다.

> **수정 (HIGH, 3줄)**: `classifyRestore`에 네 번째 분기를 만든다 — `Err(failure: AuthFailure())` → 새 `RestoreOutcome.expired` → `restoreLandingRoute`가 `'/login'`을 돌려주고 `signOut()`한다. 순수 함수 두 개만 바뀌므로 기존 테스트(`test/features/auth/presentation/session_restore_test.dart`)에 케이스만 추가하면 된다.

### 경우 3 — "죽은 시간 1ms도 만들지 않는다"는 `/home`에서 거짓이다

문서 §5-1의 계약:

> **게이트는 "죽은 시간"을 단 1ms도 만들지 않는다.** — 죽은 시간 = 아무 일도 일어나지 않고 **목적지도 아직 안 보이는** 시간.

`/home` 착지에서 게이트가 퇴장을 끝낸 직후 사용자가 보는 것은 **헤더 + 빨간 `CircularProgressIndicator`** 이고, 그 뒤로 `centerPolicy` + 5개 호출이 **순차로** 이어진다(기동경로 §4.5, `home_repository_impl.dart:39,40,86,137,155` — `Future.wait` 0건).

즉 사용자 관점의 시퀀스는:

```
[고급스러운 크림 마크]  →(280ms 크로스페이드)→  [빨간 스피너]  →(5~6 왕복)→  [내용]
```

**두 번째 로딩 화면이 첫 번째보다 싸구려다.** 스플래시의 유일한 효과가 "예쁜 대기 뒤에 안 예쁜 대기가 온다"가 되면, 람이 처음 말한 "이상하다"의 해결이 아니라 **자리를 옮긴 것**이다.

> **권고 (MEDIUM)**: 스플래시보다 **홈 6왕복 병렬화가 체감 개선이 크다.** `_readStaffMap()`은 나머지와 독립이고 `fetchMyBookings`/`fetchHomeworks`는 `fetchMyPasses`의 `trainerId`에만 의존하므로 `Future.wait` 두 번이면 6왕복이 사실상 2왕복이 된다. 스플래시 작업을 시작하기 전에 이걸 먼저 하면, 스플래시가 크로스페이드로 넘겨줄 화면이 **실제로 완성된 화면**이 된다. 순서를 바꾸는 게 맞다.

## A-7. hot reload · 라이프사이클 · 회전 — 실제로 깨지는 것만

문서가 다루지 않은 세 축을 하나씩 확인했다. **대부분은 안 깨진다.** 과장 없이 실제로 문제인 것만 남긴다.

### 🟢 hot reload — 깨지지 않는다

- `State`가 보존되므로 `AnimationController`도 상태 기계도 그대로다. `gone`이면 계속 `gone`.
- Riverpod provider는 hot reload에서 초기화되지 않으므로 `appReady`(또는 §A-4의 delegate 구독)도 유지된다.
- `_router`는 `late final`(`app.dart:40`)이라 재생성되지 않고, `restoreAttempted` 래치도 true로 유지된다 → 복원이 다시 돌지 않는다.
- 게이트를 **처음 추가하는** 그 한 번의 hot reload에서는 `Router` 엘리먼트의 부모가 바뀌어 서브트리가 재삽입되지만, `_CustomNavigator`가 `GlobalObjectKey`를 쓰므로(`builder.dart:113`) Navigator 상태는 살아남는다.

### 🟡 hot restart — 매번 630ms + `/v1/me` 재요청

hot restart(`R`)는 전부 초기화하므로 개발 중 **재시작마다 스플래시 전체와 네트워크 왕복을 다시 본다.** 버그는 아니지만 개발 마찰이고, 이걸 못 견뎌 `kDebugMode` 예외를 넣으면 디버그와 릴리스의 기동 경로가 갈려서 §A-2 같은 결함을 개발 중에 못 만나게 된다. **예외를 넣지 말 것.**

### 🟠 백그라운드 전환 — 애니메이션이 멈추고, 콜백이 안 돈다

```dart
// flutter/packages/flutter/lib/src/scheduler/binding.dart:424-426
case AppLifecycleState.paused:
  ...
  _setFramesEnabledState(false);

// :947
if (_hasScheduledFrame || !framesEnabled) { return; }   // scheduleFrame이 no-op이 된다
```

스플래시 도중 사용자가 홈 버튼을 누르면 **프레임 생산이 멈춘다** → `AnimationController`가 정지하고 `AnimationStatusListener`의 `completed`도 오지 않고, §A-4에서 본 `addPostFrameCallback`도 실행되지 않는다. 복귀하면 이어서 진행된다.

**실제 증상**: 기동 중 알림을 확인하러 나갔다가 10분 뒤 돌아오면, **10분 전에 멈춰 있던 등장 애니메이션의 뒷부분**을 본다. 그 사이 복원은 이미 끝났을 수 있는데도. 버그로 신고될 만한 인상이다.

> **수정 (MEDIUM)**: §A-4의 트리거(`currentConfiguration.isNotEmpty`)를 쓰면 복귀 시 이미 조건이 참이므로 **첫 프레임에 즉시 퇴장**한다 — 멈춘 애니메이션 뒷부분을 안 본다. 여기서도 `appReady`보다 delegate 구독이 낫다.

### 🟡 회전 — 안드로이드는 안전, iOS는 확인 필요

- 안드로이드는 `configChanges`에 `orientation|screenSize`가 있어(기동경로 §5) Activity가 재생성되지 않는다. 게이트는 `Center` 한 겹이라 회전해도 중앙을 유지한다.
- **iOS는 iPhone에서도 가로 모드를 허용한다**: `ios/Runner/Info.plist:70-75`에 `LandscapeLeft`/`LandscapeRight`가 들어 있고, `lib/` 전체에 `SystemChrome.setPreferredOrientations` 호출이 없다(문서 §6.6에서 확인된 사실). 즉 **가로로 들고 앱을 켜면 가로로 뜬다.**
- 그 경우 `LaunchScreen.storyboard`의 `contentMode: center`와 Flutter의 `Center`가 둘 다 중앙 정렬이므로 §3-3의 픽셀 매칭은 유지될 가능성이 높다 — 다만 **미검증**(§D-3).

## A-9. 🟡 문서의 사실 오류 2건

두 문서 모두 근거 표를 갖춘 정밀한 문서지만, 아래 두 주장은 확인 결과 사실과 다르다.

### 오류 1 — "이 앱은 상태바 스타일을 한 번도 설정하지 않는다" (모션 §7-3, 525행)

> 크림 `#F6F4EF`는 **밝은 배경**이다 → `SystemUiOverlayStyle`의 어두운 아이콘이 필요하다. 지금 앱은 이걸 **한 번도 설정하지 않는다**(검색 결과 0건). 설정을 안 하면 다크모드 안드로이드에서 밝은 아이콘이 크림 위에 올라가 **시계와 배터리가 사라진다**. 게이트 수명 동안 적용하고 퇴장 시 원복

`lib/`에 호출이 0건인 것은 맞다. 하지만 **`MaterialApp`이 대신 부른다**:

```dart
// flutter/packages/flutter/lib/src/material/app.dart:1012-1014  (_themeBuilder 안)
SystemChrome.setSystemUIOverlayStyle(
  theme.brightness == Brightness.dark ? SystemUiOverlayStyle.light : SystemUiOverlayStyle.dark,
);
```

`_themeBuilder`는 `_materialBuilder`의 첫 줄에서 불리고(`:1020`), `_materialBuilder`는 `WidgetsApp.builder`이므로 **첫 프레임부터 매 빌드마다** 실행된다. 그리고 이 앱의 테마는 `brightness: Brightness.light` 고정이다(`app_theme.dart:10`).

**따라서 다크모드 기기에서도 상태바 아이콘은 이미 어둡다.** 시계와 배터리가 사라지는 현상은 발생하지 않는다.

> **권고**: 이 항목을 **삭제한다.** 특히 "퇴장 시 원복"은 위험하다 — 무엇으로 원복할지가 정의되지 않았고, MaterialApp이 다음 빌드에서 다시 `dark`로 덮으므로 두 코드가 프레임마다 경합한다. 정말 명시가 필요하면 명령형 `SystemChrome`이 아니라 선언형 `AnnotatedRegion<SystemUiOverlayStyle>`를 쓴다.

### 오류 2 — "셋 중 유일하게 못 바꾸는 게 안드로이드다" (모션 §3-3)

> 크기: **안드로이드 12의 기본 크기에 iOS와 Flutter를 맞춘다** (셋 중 유일하게 못 바꾸는 게 안드로이드다 — 순서가 이렇게 정해진다)

안드로이드 12+ 시스템 스플래시에서 OS가 고정하는 것은 **아이콘이 놓이는 원형 마스크의 지름**이지 **그 안에 그려지는 마크의 높이**가 아니다. `android_12.image`로 넣는 PNG(960×960)의 **투명 여백을 조절하면 마크의 실제 렌더 높이가 바뀐다.** 즉 자유 파라미터가 하나 있고, 세 플랫폼 모두 조절 가능하다.

**실무상 차이**: 문서의 절차대로 "기기에서 재서 그 값을 Flutter에 하드코딩"하면 **우연히 나온 값**(예: 137.4dp)을 영구히 떠안는다. 대신 **원하는 dp를 먼저 정하고**(예: 132dp) 세 곳의 자산을 거기 맞추는 편이 재현 가능하고 재생성에도 견딘다.

### 그리고 문서가 놓친 것 — Android 11 이하에서는 픽셀 매칭이 성립하지 않는다

`minSdk = flutter.minSdkVersion` = **24**(`android/app/build.gradle.kts:30-31` 주석이 명시). Android 7~11 기기에서는:

- 시스템 스플래시 API 자체가 **없다** → 문서 §1-1 표의 ①단계(런처 아이콘 표시)가 발생하지 않는다.
- `flutter_native_splash`는 `android_12.image`가 아니라 **`image` 키**를 레거시 layer-list로 렌더한다 → 크기 결정 방식이 완전히 다르다(비트맵의 density 버킷).

**하드코딩된 `markHeight` 하나로는 두 경로를 동시에 맞출 수 없다.** 문서 §3-3의 교정 절차(5단계)는 안드로이드 12+에서만 측정하도록 되어 있어 이 갈래를 보지 못한다.

> **수정**: 위의 "원하는 dp를 먼저 정한다" 접근을 쓰면 자연히 해결된다 — 레거시 `image` PNG를 목표 dp에 맞는 density별 크기로 내보내면 두 경로가 같은 dp로 수렴한다.

## B-1. 🔴 CRITICAL — 릴리스 빌드가 `localhost`를 바라볼 수 있고, 그걸 막는 장치가 없다

```dart
// app/lib/core/network/api_config.dart:3-9
/// 로컬 백엔드 기본값 — 실제 배포 시 `--dart-define=API_BASE_URL=https://...`
/// 로 오버라이드(TODO: CI/CD에서 환경별 주입).
static const baseUrl = String.fromEnvironment(
  'API_BASE_URL',
  defaultValue: 'http://localhost:8080',
);
```

**확인한 사실**:
- 올바른 명령은 `app/README.md:178-179, 201-203`에 문서화돼 있다.
- 그러나 저장소에 **CI가 없고**(`.github/workflows` 없음), 빌드 스크립트도 fastlane도 Makefile도 없다. 전수 검색 결과 `--dart-define`이 등장하는 곳은 **README와 work_log 뿐**이다.
- 즉 이 값은 **사람이 매번 손으로 붙여넣는 문자열**이고, 빠뜨렸을 때 경고·assert·빌드 실패가 **하나도 없다.**

**사용자가 겪는 것**: `--dart-define`을 빠뜨린 릴리스 APK/IPA를 받은 회원은 모든 요청이 `http://localhost:8080`으로 나가 실패한다. targetSdk 36이므로 안드로이드는 cleartext HTTP를 기본 차단하고(`AndroidManifest.xml`에 `usesCleartextTraffic` 설정 없음 — 확인함) 즉시 실패한다. 그 실패는 `guardApi:30` → `NetworkFailure('연결이 불안정해요')` → `classifyRestore:36` → `unknown` → **전원이 "센터 선택 / 연결 상태를 확인하지 못했어요"에 착지한다.** 앱이 완전히 죽은 것처럼 보이는데 에러는 "연결이 불안정해요"라 원인 추적이 어렵다.

**수정 (작음)**: `api_config.dart`에 릴리스 가드를 넣는다.

```dart
// kReleaseMode에서 기본값이 그대로면 빌드가 아니라 첫 실행에서 즉시 드러나게 한다.
static void assertConfigured() {
  if (kReleaseMode && baseUrl.contains('localhost')) {
    throw StateError('API_BASE_URL 미주입 — --dart-define으로 운영 주소를 넣어야 합니다');
  }
}
```
또는 더 나은 방법으로, `--dart-define`을 담은 `app/build-prod.sh` 한 장을 커밋해 손입력을 없앤다. **1인 개발 + CI 없음 조합에서 이건 언젠가 한 번은 터지는 종류의 결함이다.**

## B-5. 🔴 CRITICAL — `centerConfirmStage`의 폴백이 "모름"을 "아님"으로 단정한다 (§A-1의 진짜 뿌리)

**폴백이 잘못됐다.** `notFound`는 *"서버가 이 번호로 회원을 못 찾았다고 확답했다"* 는 뜻인데(`auth_state.dart:24-25`가 그렇게 정의한다), 실제로는 **"위 네 가지에 해당하는 정보가 아무것도 없다"** 일 때 여기로 떨어진다. 두 개는 전혀 다른 상태다. 그리고 지금 이 폴백에 도달하는 경로가 **둘** 있다:

| 경로 | 어떻게 도달하나 | 절 |
|---|---|---|
| ① 스플래시 계획의 `.timeout` | ③ `markConnectionUnknown`이 실행되지 않은 채 라우터만 착지 | §A-1 |
| ② 로그아웃 후 다른 사람이 로그인 | `AuthViewModel`이 살아남아 상태가 **섞인다** | §B-6 |

이 화면이 `notFound`로 잘못 그려지면 사용자에게 **"당신은 우리 회원이 아니다"** 라고 단정하고, 가입 요청을 권하고, 주 CTA로 로그아웃을 준다(§A-1 참조).

> **수정 (CRITICAL, 3줄)**: `CenterConfirmStage`에 **`unknown` 폴백을 추가**한다. 확답 없이 도달한 상태는 `notFound`가 아니라 `connectionUnknown`(또는 새 `unknown`)으로 떨어져야 한다. `notFound`는 **서버가 실제로 그렇게 답했을 때만** 세팅되는 명시 플래그가 되어야 한다.
>

**사용자는 "다시 시도"를 눌러서 "새로고침하세요"라는 안내를 받고, 닫으면 제자리다. 무한히 반복 가능하다.** 진짜 복구 경로(pull-to-refresh가 `staffMapProvider`를 invalidate, `home_screen.dart:112`)는 안내되지 않는다.

> **수정**: 문구를 "아래로 당겨 새로고침해주세요"로 바꾸거나(1줄), 카드가 `ref`를 받아 탭에서 실제로 invalidate한다.

## B-14. 🟡 MEDIUM — pull-to-refresh 스피너가 새로고침을 추적하지 않는다

```dart

  ref.invalidate(centerPolicyProvider);
  ref.invalidate(staffMapProvider);
```
