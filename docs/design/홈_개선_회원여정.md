## 0. "허전하다"의 정확한 정체 — 홈에 누를 수 있는 것이 하나도 없다

대표가 본 화면을 코드에서 그대로 재구성하면 이렇다 (`home_screen.dart` 103–226행, 실측값 대입):

```
┌ 헤더 ───────────────────────────────────────────┐
│ 라이즈 컨디셔닝 ▾                  [PT 20회 · 잔여 20] │  ▾ 는 탭 핸들러 없음
│ 김민지 님 · 담당 정혜린 코치                          │
└──────────────────────────────────────────────────┘
( 정혜린 코치 · PT 20회 (활성) )    ← 칩 1개. 이미 선택돼 있어 눌러도 아무 일 없음

┌ 다음 예약 ────────────────────────────────────────┐
│ 이 회원권 담당 코치로 예정된 예약이 없어요 — 예약 탭에서   │  회색 문장 2줄
│ 잡아보세요                                          │  버튼 0개
└──────────────────────────────────────────────────┘

┌ Home Work · 오늘 ─────────────────────────────────┐
│ 오늘 배정된 Home Work가 없어요                        │  회색 문장 1줄
│ 코치가 배정했어요 · 체크하면 코치에게 완료율이 보여요       │  ← 배정이 없는데 "배정했어요"
└──────────────────────────────────────────────────┘

┌ 내 회원권 ───────────────────────────────────────┐
│ (◯ 20회/20회)  PT 20회 · 정혜린                     │
│                유효기간 2026-XX-XX (D-nn)           │
│                [잔여 20회 — 연장 상담 가능]           │  ← 노란 경고 배지가 항상 켜짐
└──────────────────────────────────────────────────┘
```

**이 화면에서 회원이 누를 수 있는 것: 0개.**

- 칩 1개 — 이미 선택된 유일한 패스라 탭해도 같은 화면을 다시 로드할 뿐
- 체크박스 — 배정 0건이라 0개
- 버튼 — 셀프 체크인 버튼은 예약이 없으면 카드 자체가 안 그려지므로 0개
- 링크 — 없음. `▾`도 핸들러 없음

"허전하다"는 여백의 문제가 아니라 **행동 가능한 요소가 0개**라는 문제다. 카드를 더 얹는 것으로는 풀리지 않는다. 지금 있는 4개 표면 중 3개가 "없다"고 말하고 끝나는 구조를 고쳐야 한다.

## 2. 데드엔드 — 회원에게 말은 걸고 행동은 안 주는 자리

데드엔드 = **상태를 알려주지만 다음 행동이 없는 화면.** 현재 문구를 그대로 인용한다.

### DE-1 · 예약 진입이 문장뿐이다 (최대 빈도 × 최대 막힘)

`next_booking_card.dart:71`
```
이 회원권 담당 코치로 예정된 예약이 없어요 — 예약 탭에서 잡아보세요
```
`next_booking_card.dart:141-143`
```
24시간 전까지 취소 가능(예약 탭)
지금 취소하면 세션 1회가 차감돼요(예약 탭)
```

세 문장 모두 **"예약 탭"을 이름으로 부르지만 탭으로 보내주지 않는다.** 이건 홈만의 문제가 아니라 **앱 전체에 탭 이동 수단이 존재하지 않는다**: `goBranch`는 `AppShell._go` 하나뿐이고 private이며, 탭 인덱스 provider도 없다. 기록 탭도 같은 병을 앓는다 — `body_photo_timeline.dart:124`의 "촬영 탭에서 첫 사진을 남겨보세요"도 탭 핸들러가 없다.

> 이게 이 브리프에서 **가장 큰 단일 발견**이다. 홈의 데드엔드 대부분이 이 하나에서 파생된다.

### DE-2 · 헤더의 `▾` 는 아무 것도 아니다

`home_screen.dart:326-337` — `FittedBox > Row[Text('라이즈 '), Text('컨디셔닝'), RiseIcon(chevronDown)]`. `InkWell`도 `GestureDetector`도 없다. **매번 보이는데 매번 안 눌린다.** 단일 센터라 전환할 대상도 없다.

### DE-3 · "연장 상담 가능"은 앱에 경로가 없는 약속이다

`home_screen.dart:209-212` — 조건 없이, 항상 `warn`(노란) 배지로:
```
잔여 20회 — 연장 상담 가능
```
- **항상 켜져 있다.** 잔여 20/20에도 경고색으로 뜬다 → 경고가 배경 소음이 되어 정작 D-3일 때 눈에 안 들어온다.
- **"상담"에 해당하는 것이 서버에 없다.** 상담 요청 엔드포인트 없음. 재등록 요청 엔드포인트 없음(`POST /v1/passes`는 member 403). 앱 안에서 상담을 시작할 방법이 **0개**다.

### DE-4 · 만료가 다가와도 홈은 목소리를 높이지 않는다

`home_screen.dart:194-197`
```
유효기간 2026-09-02 (D-7)
```
11px muted 한 줄. D-30이든 D-1이든 **똑같이 생겼다.** 만료되면 잔여 회차를 예약에 쓸 수 없게 되는데(서버 `EffectiveStatus` → expired → `CreateBooking` 거부), 되돌릴 방법도 없다. 홈에서 가장 돈이 걸린 사실이 가장 조용하게 놓여 있다.

### DE-5 · 퇴사는 표기만 하고 설명하지 않는다

`home_screen.dart:299` / `pass_switcher_chips.dart:42`
```
담당 정혜린 코치 (퇴사)
정혜린 코치 (퇴사) · PT 20회 (활성)
```
홈은 여기서 끝난다. 무슨 뜻인지(= 이 회원권으로 새 예약을 못 잡는다), 뭘 해야 하는지(= 센터에 새 담당 코치 문의)는 **예약 탭과 프로필 시트에만** 있다. 그리고 홈에는 프로필 시트로 가는 입구가 없다.

같은 사실을 예약 탭은 이렇게 말한다(`slot_list.dart:540-543`) — 홈이 재사용해야 할 문장이다:
```
정혜린 코치가 지금은 센터에서 활동하지 않아 새 예약을 잡을 수 없어요 — 새 담당 코치는 센터에 문의해주세요
```

### DE-6 · 빈 회원권 화면의 유일한 버튼이 [새로고침]이다

`home_screen.dart:75-84` / `empty_passes_view.dart:18-19,44`
```
이용 가능한 회원권이 없어요
만료·환불된 회원권만 남아 있어요
센터에서 재등록하면 다시 이용할 수 있어요
[새로고침]
```
```
아직 회원권이 없어요
센터에서 회원권 등록 후 이용할 수 있어요
[새로고침]
```
문구는 이유를 정확히 말한다(이 저장소 규약대로). 문제는 **버튼**이다. 회원권 발급은 `POST /v1/passes` = 스태프 전용이라 **회원이 새로고침을 몇 번 눌러도 상태가 바뀌지 않는다.** 새로고침이 의미 있는 건 "방금 데스크에서 등록해줬다"는 한 경우뿐인데, 그게 primary 자리를 차지하고 있다.

### DE-7 · Home Work가 없는 날 카드가 거짓말을 한다

`homework_checklist_card.dart:55-58, 116-122` — footer가 `if (items.isEmpty)` **바깥**에 있어 항상 렌더된다:

### DE-8 · 다음 예약에 **날짜가 없다**

`next_booking_card.dart:110-113` — `DateFmt.hhmm(b.startAt)`만 쓴다:

## 3. 회원의 한 주 — 홈이 돕는 곳 / 사냥터로 보내는 곳

PT 회원의 루프: **예약 잡기 → 수업 가기 → 체크인 → 기록 보기 → Home Work → 다음 예약**

| 단계 | 지금 홈이 하는 일 | 판정 | 회원이 실제로 가는 곳 |
|---|---|---|---|
| **① 예약 잡기** | 문장 하나 — "예약 탭에서 잡아보세요" | ❌ **사냥** | 하단 탭바 → 예약 탭 → 날짜 스트립에서 날짜 찾기 → 슬롯 찾기. 홈은 코치도 날짜도 넘겨주지 않아 회원이 처음부터 다시 고른다 |
| **② 수업 가기** | 시각만 표기, **날짜 없음** | ⚠️ **반쪽** | 언제인지 확인하러 예약 탭 |
| **③ 체크인** | 창이 열리면 버튼 활성 — 시각 판정도 `TimeBoundaryBuilder`로 살아 있다 | ✅ **홈이 한다** | 데스크 QR 스캔 |
| **④ 기록 보기** | 홈에서 **완전히 부재** | ❌ **사냥** | 기록 탭 → 세그먼트(운동/인바디/체형) 중 고르기. 홈은 "수업이 끝났다"는 사실조차 안 남긴다 |
| **⑤ Home Work** | 체크리스트 카드 — 처방(3×40초)까지 정확히 | ✅ **홈이 한다 (유일한 완성 표면)** | — |
| **⑥ 다음 예약** | ①로 되돌아감 | ❌ **사냥** | — |

### 촬영(체형분석)이 루프에서 떨어져 있다

- 진입점은 **하단 탭바 가운데 빨간 원 하나뿐**이다(`app_shell.dart:44` → `context.push('/camera')`). 앱 전체에서 `/camera`를 부르는 곳이 여기 하나다.
- 기록 탭의 체형 분석 세그먼트는 `'아직 촬영한 사진이 없어요 — 촬영 탭에서 첫 사진을 남겨보세요'`라고 **말만** 하고 탭 핸들러가 없다(DE-1과 같은 병).
- 동의 검사가 **셔터를 누른 뒤에** 일어난다(`camera_view_model.dart:177`) — 회원이 자세를 잡고 프레임을 맞춘 다음에야 "체형 사진 동의가 필요해요 — 마이 탭에서 동의해주세요"를 본다.
- 홈은 촬영에 대해 아무 말도 하지 않는다.

**판정:** 촬영은 회원 루프의 일부가 아니라 **탭바에 붙은 별도 기능**이다. 홈에서 촬영을 밀어 넣는 설계는 하지 않는다 — 루프에 없는 것을 홈에 얹으면 홈이 다시 잡화점이 된다. 대신 동의 게이트를 **셔터가 아니라 진입 시점으로** 옮기는 것이 옳은 수선인데, 이건 홈 밖의 일이라 §7에 별도로 남긴다.

### 기록이 홈에 한 줄도 없다

프로덕션은 수업기록 0건이라 지금 당장의 문제는 아니다. 하지만 루프 ④가 홈에서 통째로 빠져 있는 건 구조적 공백이다. **다만 이번 v1에서는 제안하지 않는다** — `GET /v1/workout-logs`는 홈에 **왕복 1회를 더 붙이고**(홈은 이미 6왕복), 홈의 일은 "지난 것"이 아니라 "다음 것"이다. 대신 Home Work 빈 상태가 기록 탭으로 넘겨주는 다리를 놓는다(§4.3-D).

## 4. 제안

### 4.1 순서 규칙 — 딱 하나

> **되돌리기 어려운 것이 위로 온다.**

1. **알림 스트립** — 기한·차단. 조건부, **최대 1개만**. (여러 조건이 겹치면 우선순위 하나만 — 홈의 "화면당 1~2회" 규약과 같은 정신)
2. **다음 예약 / 예약 잡기** — 회원이 홈에 오는 이유
3. **Home Work** — 오늘 할 일
4. **내 회원권** — 잔여·유효기간
5. **내 코치** — 신규

패스 스위처 칩은 조건부로 1번 위(§4.3-A).

### 4.2 상태별 카드 순서

| 상태 | 카드 순서 |
|---|---|
| **S3 (프로덕션 현재)** | 예약 잡기 → Home Work(빈) → 내 회원권 → **내 코치** |
| S4~S8 (예약 있음) | 다음 예약 → Home Work → 내 회원권 → 내 코치 |
| S17 만료 D-14 이내 | **⚠️ 스트립(만료)** → 예약 잡기 → Home Work → 내 회원권 → 내 코치 |
| S13 퇴사 | **⚠️ 스트립(퇴사)** → (예약 CTA **없음**) → Home Work → 내 회원권 → 내 코치 |
| 잔여 0 | **⚠️ 스트립(잔여 0)** → (예약 CTA **없음**) → Home Work → 내 회원권 → 내 코치 |
| 잔여는 있는데 다 잡아둠 | **⚠️ 스트립(다 잡음)** → 다음 예약 → Home Work → 내 회원권 → 내 코치 |

| S20 scheduled | 예약 잡기(**시작일 프리셀렉트**) → Home Work → 내 회원권 → 내 코치 |

**예약 CTA를 띄우지 않는 규칙:** 서버가 100% 거부할 행동은 권하지 않는다. `BookablePass.canBookNew`(= `isUsable && hasRemaining && !trainerInactive && hasBookingBudget`)와 같은 판정을 쓴다 — 예약 탭이 이미 쓰는 그 함수다. 홈이 자체 판정을 만들면 두 화면이 다른 답을 말한다(이 저장소가 반복해서 겪은 사고).

### 4.3 카드별 정확한 문구

#### A · 패스 스위처 칩 (조건부 렌더)

> **규칙:** 패스가 1개이고 상태가 `active`면 **칩 줄을 그리지 않는다.**
> 근거: 선택지가 없는 선택 UI다. "(활성)"은 헤더 배지와 회원권 카드가 이미 말한다. scheduled("9/1~")·만료·환불은 칩이 그 사실을 말하는 유일한 자리라 개수와 무관하게 유지한다.
> 프로덕션 효과: 칩 줄 한 줄(히트 영역 ≈44dp) 회수 + 아무 일도 일어나지 않는 탭 타깃 제거.

라벨 문구는 변경 없음.

#### B · 예약 잡기 카드 (S3 — 대표가 본 그 자리)

`RiseCard(tinted: true)` — 지금 빈 상태는 tinted가 아니다. 홈에서 유일하게 "다음 행동"인 카드이므로 강조 카드로 승격한다.

**패스 1개, 예약 0건 (프로덕션 현재):**
```
다음 예약
아직 잡아 둔 수업이 없어요
정혜린 코치 · 잔여 20회 · 오늘부터 2주 안에서 시간을 고를 수 있어요
        [ 예약 잡기 ]
```
- "오늘부터 2주"는 검증 가능한 사실이다 — `DateStrip`이 오늘부터 14일을 그린다.
- 버튼: `RiseButton(label: '예약 잡기', small: true)`

**패스 2개 이상:**
```
다음 예약
정혜린 코치로 잡아 둔 수업이 없어요 — 다른 회원권은 위 칩에서 확인할 수 있어요
        [ 예약 잡기 ]
```
(현재 문구가 이미 이 범위를 정확히 밝히고 있다 — 문장은 살리고 버튼만 얹는다)

**S20 scheduled 패스:**
```
다음 예약
9/1부터 쓸 수 있는 회원권이에요 — 9/1 이후 날짜는 지금도 예약할 수 있어요
        [ 9/1 예약 잡기 ]
```
사실 확인 완료: 서버 `BookableStatus()`는 `active`와 `scheduled`를 **둘 다** 통과시키고, 날짜 적합성만 슬롯별로 본다.

**[예약 잡기] 버튼이 하는 일 (서버 작업 0):**
```dart
ref.read(showMyCoachOnlyProvider.notifier).set(true);          // 선택된 패스의 코치로 필터
ref.read(selectedBookingDateProvider.notifier).select(날짜);    // 오늘 / scheduled면 validFrom
context.go('/booking');                                         // 브랜치 전환
```
세 provider 모두 **이미 public**이고, `context.go('/booking')`는 `StatefulShellRoute.indexedStack`이 브랜치를 알아서 전환한다(`center_confirm_screen`이 이미 `context.go('/home')`으로 같은 일을 한다). 날짜 선택은 `selectedBookingDate`가 오늘보다 과거면 자정 롤오버가 오늘로 당긴다 — 그 로직도 이미 있다.

> **선택 날짜 규칙:** 오늘 영업 종료(21시, `BookingRules.closeHour`)를 지났으면 내일을 프리셀렉트한다. 안 그러면 회원이 "지남"으로 채워진 13칸에 착지한다.

#### C · 다음 예약 카드 (S4~S8) — 날짜를 넣고 중복을 뺀다

```
다음 예약                                        [오늘]
19:00 · 1:1 PT
8/27 (수) · 정혜린 코치
    [ 셀프 체크인 ]   [ 내 예약 보기 ]
24시간 전까지는 무료로 취소할 수 있어요
셀프 체크인은 18:30부터 열려요
```

변경점:
1. **둘째 줄 교체** — `'정혜린 코치 · 라이즈 컨디셔닝 센터 (강남)'` → `'8/27 (수) · 정혜린 코치'`.
   `DateFmt.monthDayWeekday`("8/27 (수)")는 이미 있고 예약 탭이 쓴다. 센터명은 헤더가 이미 말하는 중복이라 뺀다. **줄 수 증가 0, 정보 순증 1.**
2. **체크인 버튼 라벨 단축** — `'셀프 체크인 (데스크 QR 스캔)'` → `'셀프 체크인'`. QR이라는 사실은 눌러서 열리는 스캐너 화면이 말한다. 320dp×1.35에서 두 버튼이 한 Wrap 안에 들어가려면 필요한 절약이다.
3. **[내 예약 보기] 추가** — `RiseButton(style: outline, small: true)` → 예약 탭 이동. 취소는 거기서 한다(취소 다이얼로그·컷오프 재평가가 이미 그쪽에 정확히 구현돼 있다 — 홈에 복제하지 않는다).
4. **취소 안내에서 "(예약 탭)" 제거** — 버튼이 생겼으므로 괄호 지시문이 불필요.
   - 무료: `24시간 전까지는 무료로 취소할 수 있어요` (`cutoffHours` 실값 보간)
   - 경과: `지금 취소하면 세션 1회가 차감돼요`
5. **체크인 열림 시각 표기** (`checkInOpensAt` 사용):
   - 오늘 · 창 열리기 전: `셀프 체크인은 18:30부터 열려요`
   - 오늘이 아님: `셀프 체크인은 수업 시작 30분 전부터 열려요` (날짜 없는 시각은 오해를 부른다)
   - 창 닫힘 후: `셀프 체크인 시간이 지났어요 — 데스크에 말씀해주세요`
   세 문구 모두 `TimeBoundaryBuilder`의 기존 경계(`checkInOpensAt`/`checkInClosesAt`)에서 자동으로 갈린다 — 서버 왕복 0.
6. **패스 2개 이상일 때 범위 한 줄** — 지금은 빈 상태에서만 범위를 밝힌다. 예약이 있을 때도 밝힌다:
   `다른 회원권의 예약은 위 칩에서 확인할 수 있어요`

#### D · Home Work 카드

**배정 있음(S9):** 변경 없음. 이 카드는 이미 정확하다.

**배정 없음(S10):**
```
Home Work · 오늘
오늘은 배정된 Home Work가 없어요 — 이번 주에 한 것은 기록 탭에서 볼 수 있어요
        [ 이번 주 기록 보기 ]
```
- footer `'코치가 배정했어요 · 체크하면 코치에게 완료율이 보여요'`를 **이 분기에서 제거**한다(배정이 없는데 배정했다고 말하지 않는다). 배정이 있는 분기에서는 그대로 유지.
- 버튼 → `context.go('/records')` + `ref.read(selectedRecordsTabProvider.notifier).select(RecordsTab.workout)`. 기록 탭의 "운동" 세그먼트에 `HomeworkWeeks`가 이미 있다.

**체크 실패(S11):** 변경 없음.

#### E · 내 회원권 카드

```
내 회원권                                          [자세히]
(◯ 20회 / 20회)   PT 20회 · 정혜린
                  유효기간 2026-09-02  [D-7]
                  [일시정지 중 ~9/10]
```

변경점:
1. **`잔여 20회 — 연장 상담 가능` 배지 삭제.** 잔여는 링이 이미 두 번 말한다(20회 / 20회). "연장 상담"은 앱에 경로가 없는 약속이고(§7-S2), 항상 켜진 warn 배지는 경고를 무의미하게 만든다.
2. **D-day를 배지로 승격하되 조건부로만.**
   - `D-15` 이상 → 배지 없음, 지금처럼 muted 텍스트 `유효기간 2026-09-02 (D-30)`
   - `D-8 ~ D-14` → `RiseBadge('D-14', warn)`
   - `D-0 ~ D-7` → `RiseBadge('D-7', danger)`
   - 만료 → `RiseBadge('만료', muted)`
   경고를 아껴 두면 실제로 경고가 된다.
3. **헤더 trailing `[자세히]`** → `context.go('/my')`. 원장·환불 견적·계약·결제가 전부 마이 탭에 있는데 홈에서 가는 길이 없다.

#### F · 알림 스트립 (신규, 조건부·최대 1개)

`RiseCard(tinted: true)` + `RiseBadge` + 제목 1줄(w800, 12.5) + 본문(11.5, muted, height 1.4) + 버튼 `Wrap`.
새 primitive 없음 — 기존 `RiseCard`/`RiseBadge`/`RiseButton` 조합.

**우선순위 (위에서부터 하나만):**

**1) 담당 코치 퇴사 (S13)**
```
[퇴사]  담당 코치가 바뀌어야 해요
정혜린 코치가 지금은 센터에서 활동하지 않아 이 회원권으로는 새 예약을 잡을 수 없어요 — 새 담당 코치는 센터에 문의해주세요
    [ 센터에 전화 ]   [ 코치 소개 ]
```
문장은 `slot_list.dart:542-543`과 **같은 어휘**를 쓴다. 두 화면이 같은 사실을 다르게 말하면 회원은 어느 쪽이 맞는지 모른다.

**2) 회원권 만료 임박 (S17 — D-14 이내 & 잔여 ≥ 1)**
```
[D-7]  9/2에 유효기간이 끝나요
남은 8회는 그날 이후로는 예약에 쓸 수 없어요 — 남은 기간에 잡으려면 지금 잡아야 해요
    [ 예약 잡기 ]
```
> "사라져요"가 아니라 "예약에 쓸 수 없어요"라고 쓴다. 서버가 하는 일은 `EffectiveStatus → expired` → `CreateBooking` 거부다. 원장이 지워지는 게 아니다. 앱은 서버가 하지 않는 일을 말하지 않는다.

**3) 잔여 0회**
```
[잔여 0회]  이 회원권으로는 더 예약할 수 없어요
PT 20회를 다 쓰셨어요 — 재등록은 센터에서 진행해요
    [ 센터에 전화 ]
```
(패스가 2개 이상이면 한 줄 추가: `다른 회원권이 있으면 위 칩에서 바꿔주세요`)

**4) 잔여는 있는데 예약으로 다 채웠음**
```
[예약 다 잡음]  남은 3회를 예약 3건으로 다 잡아 두셨어요
새로 잡으려면 기존 예약을 먼저 취소해주세요
    [ 내 예약 보기 ]
```
> 서버 판정 `remaining − openBookings <= 0`(P13 H1)의 거울. 홈은 이미 `GET /v1/bookings`를 받고 있으므로 `BookingRules.countOpenBookings(bookings, passId)`를 그대로 부르면 된다 — **추가 왕복 0, 서버 작업 0.** 지금은 홈이 이 값을 계산하지 않아 예약 예산이 0인데도 [예약 잡기]를 권하게 될 수 있다.
> **"잔여 0"과 이 상태를 반드시 구분한다** — 예약 탭이 이미 구분한다(`NoRemainingSessions` vs `AllRemainingBooked`). 전자는 재등록, 후자는 취소. 다음 행동이 정반대다.

**5) 일시정지 중 (S19)**
```
[일시정지 중]  9/10까지 쉬는 중이에요
이 기간엔 예약을 잡을 수 없고, 쉰 날짜만큼 유효기간이 뒤로 밀려요 — 일찍 나오려면 마이 탭에서 재개할 수 있어요
    [ 마이 탭에서 재개 ]
```

**6) 선택 패스가 만료·환불 (S18 — 회원이 칩으로 직접 고른 경우)**
```
[만료]  이 회원권은 8/20에 끝났어요
남은 회차가 있어도 예약에는 쓸 수 없어요 — 재등록은 센터에서 진행해요
    [ 센터에 전화 ]
```

**[센터에 전화] 버튼의 근거:** `GET /v1/center` 응답에 `business.phone`이 들어 있다(`domain/business.go:42`, `service.go:3127-3129` — "사업자 정보는 역할별로 가리지 않는다"). 앱은 **이 응답을 이미 받고 있고**(`centerPolicyProvider`) `business`만 파싱하지 않을 뿐이다.
→ **DTO에 필드 추가 = 클라이언트 작업. 서버 작업 0, 추가 왕복 0.**
→ `business.phone`이 비어 있으면 **버튼을 띄우지 않는다.** 없는 번호를 지어내지 않는다. 대신 문장으로: `센터 데스크에서 도와드려요`. (프로덕션 값 채워짐 여부는 **실측 필요** — §7 확인 항목)

## 5. 내 코치 — 홈에서 담당 코치 보기

### 5.1 스태프 레코드에 실제로 있는 것 / 없는 것

`domain.Staff` (`backend/internal/domain/staff.go:12`)와 `ListStaff`의 member 응답(`service.go:2969`)을 그대로 옮긴 것:

**있는 것**

| 필드 | 값 | 프로덕션 실측 |
|---|---|---|
| `uid` `role` `name` `color` | owner\|trainer, 이름, `#f43f5e` 같은 hex | 채워짐 |
| `status` `left_at` | active\|inactive, 퇴사 시각 | active |
| `offdays[]` | "YYYY-MM-DD" 목록 | **빈 배열** |
| `profile.photo_url` | http(s) URL (≤2048자) | **채워짐** (Firebase Storage 토큰 URL) |
| `profile.title` | 직함 (≤40자) | "헤드 트레이너" |
| `profile.career_years` | 0~50 (0=미표기) | 8 |
| `profile.specialties[]` | ≤20개, 각 ≤80자 | 3개 (체형교정·근력강화·재활운동) |
| `profile.certifications[]` `awards[]` | 자격증 / 수상·선수경력 | 채워짐 |
| `profile.bio` | 소개문 (≤500자) | 채워짐 |

**없는 것 (설계에서 절대 약속하면 안 되는 것)**

- **평점·리뷰** — v1.6이 의도적으로 뺐다("마켓플레이스 맥락 — 단일 센터 CRM 부적합")
- **가격·상품** — 가격은 `Pass.paid_amount`에 있고 발급은 스태프 전용이다
- **근무 가능 시간대** — `offdays`(부정형 날짜 목록)뿐이고 **프로덕션은 비어 있다**. "정혜린 코치는 화·목 저녁이 잘 비어요" 같은 안내는 지금 데이터로 만들 수 없다
- **담당 회원 수·인기도** — 없다(회원 목록은 member 스코프에서 본인 1건만)
- **SNS·연락처** — 없다
- **회원 목표(goal)** — `Member`에 그런 필드가 없다. "목표까지 N회" 류 위젯은 전부 서버 신규 작업

### 5.2 가장 중요한 정직성 — **다른 코치는 발견해도 예약할 수 없다**

`POST /v1/bookings {slot_key, member_id, pass_id}` — **트레이너를 직접 받지 않는다.** 코치는 `Pass.trainer_id`가 정한다. 그리고:

- 새 패스 발급(`POST /v1/passes`) = **member 403**
- 담당 코치 변경 요청 엔드포인트 = **없음**
- 상담 요청 엔드포인트 = **없음**

즉 **"코치 둘러보기 → 이 코치로 예약"이라는 흐름은 서버에 존재하지 않는다.** 이걸 UI로 만들면 회원을 막다른 길로 데려간다. 코치 발견의 정직한 종착점은 **"센터에 문의"** 하나뿐이다.

### 5.3 그래서: 목록 탐색이 아니라 "내 코치 1명을 제대로"

프로덕션 트레이너는 **1명**이다. "코치 둘러보기" 목록을 만들면 행이 1개인 목록이 된다. 마켓플레이스 패턴을 끌어오지 않는다.

**내 코치 카드 (카드 5번, 항상 렌더):**

```
┌ 내 코치 ─────────────────────────────── [ 코치 소개 ] ┐
│ ( 사진 56 )   정혜린 코치                                │
│               헤드 트레이너 · 8년차                       │
│               [체형교정] [근력강화] [재활운동]             │
└──────────────────────────────────────────────────────┘
```

- 아바타: `TrainerAvatar(name:, photoUrl: profile.photoUrl, colorHex: staff.color, size: 56, inactive:)` — **실사진이 뜬다.** 로드 실패 시 `errorBuilder`가 이니셜 원으로 폴백(이미 구현됨).
- 둘째 줄: `[title, '{career_years}년차']`를 `' · '`로 조인. 둘 다 없으면 역할명(`코치`/`관장`)으로 폴백 — 프로필 시트가 쓰는 규칙 그대로(`trainer_profile_sheet.dart:51-54`).
- 전문분야: `profile.specialties` **최대 3개**를 `RiseChip(label:)`으로. 4개 이상이면 잘라낸다(칩 줄이 두 줄 넘으면 홈에서 코치 카드가 회원권 카드보다 커진다).
- 카드 전체 + 헤더의 `[코치 소개]` 둘 다 → **`showTrainerProfileSheet(context, staff: …)`**.
  - **이 함수는 이미 있다**(`booking/presentation/widgets/trainer_profile_sheet.dart`). 데이터는 `staffMapProvider` 캐시에서 즉시 조회 — **네트워크 호출 0, 서버 작업 0.**
  - 홈은 이미 `staffMapProvider`를 pull-to-refresh에서 invalidate하고 있다(`home_screen.dart:82,113`). 캐시를 이미 알고 있다는 뜻이다.
  - `_withDomainStatus` 보정도 그대로 이식한다 — 홈이 아는 퇴사 여부(도메인 플래그)를 시트에 넘겨야 카드·헤더·시트가 한 답을 말한다. 예약 탭이 겪었던 "라벨은 (퇴사)인데 아바타는 총천연색" 사고를 반복하지 않는다.
- 시트를 여는 위치가 홈이라는 것만 다르고 시트 자체는 손대지 않는다.

**미해석/미배정/퇴사 분기 (S23) — 프로필 시트의 3분기 어휘를 그대로 재사용:**

| 조건 | 카드 문구 |
|---|---|
| 퇴사 | (알림 스트립이 이미 말했다) 카드는 이름+사진(흑백)+`[코치 소개]`만. **같은 화면에서 퇴사를 두 번 말하지 않는다** |
| `staffMap == null` (미로드) | `담당 코치 정보를 불러오지 못했어요 — 아래로 당겨 새로고침해주세요` |
| 담당 미배정 (`trainerId` 빈 값) | `아직 담당 코치가 지정되지 않았어요 — 센터에서 지정하면 여기에 표시돼요` |
| 현직인데 `profile.isEmpty` | 이름 + 역할명만. 소개 없는 코치도 카드에서 빼지 않는다(이름과 얼굴만으로도 "내 코치가 누구인가"의 답이다) |

**센터에 코치가 2명 이상이 되면 (데이터가 만들면 나타나는 줄):**
```
─────────────────────────────
센터 코치 3명                    [ 둘러보기 ]
```
- 조건: `staffMap`에서 `role == 'trainer' && !isInactive` 개수 ≥ 2일 때**만** 렌더. 현재는 1명이므로 **이 줄은 나타나지 않는다.**
- `[둘러보기]` 시트: 현직 트레이너 목록을 `RiseRow(minHeight: 44)`로. 각 행 = 아바타 28 + 이름/직함·연차. 행 탭 → 같은 `showTrainerProfileSheet`.
- 정렬: `profile.isEmpty == false`인 코치를 앞으로(볼 게 있는 사람부터), 그다음 이름순.
- 시트 하단 정직성 문구 — §5.2를 UI로 옮긴 것:
  ```
  예약은 내 회원권의 담당 코치로만 잡을 수 있어요 — 담당 코치를 바꾸려면 센터에 문의해주세요
      [ 센터에 전화 ]
  ```
- 서버 작업 0, 추가 호출 0 (`GET /v1/staff`가 이미 센터 전원을 내려주고 앱이 캐시하고 있다 — `service.go:2969`는 member에게 **필터링을 전혀 하지 않는다**).

### 업그레이드 옵션 — "홈에서 바로 시간 고르기" (1번의 확장)

브리프의 "예약을 편하게"를 문자 그대로 읽으면 이것이다: 예약 잡기 카드에 **오늘/내일의 빈 시간 3칸**을 칩으로 띄우고, 탭하면 기존 `showBookingConfirmSheet`가 바로 열린다.

| | 내용 |
|---|---|
| 가능한가 | **가능하다.** `BookingRules.mergeWithOpenHours`(09~21시 합성) + `BookingRules.evaluate`(13가지 상태 판정) + `showBookingConfirmSheet` 전부 이미 있다. 홈이 **같은 함수를 그대로 호출하면** 두 화면의 답이 갈릴 수 없다 |
| 비용 | **왕복 +2.** `showBookingConfirmSheet` 내부가 `bookingViewModelProvider.notifier.book(...)`을 쓰는데, 예약 탭을 한 번도 안 열었으면 홈이 그 VM을 깨우게 되고 = `GET /v1/slots` + `GET /v1/bookings`. 홈은 이미 6왕복이다 |
| 위험 | 홈이 슬롯을 스스로 판정하기 시작하면 **판정 중복 지점이 하나 는다**. `BookingRules`를 반드시 경유해야 한다는 규약을 코드 주석으로 못박지 않으면 다음 사람이 홈에 자체 판정을 넣는다 |

## 9. 자문자답

**Q. 카드를 늘리면 홈이 더 복잡해지는 것 아닌가?**
카드 순증은 **1개**(내 코치)다. 알림 스트립은 조건부이고 **한 번에 하나만** 뜬다. 프로덕션 회원 기준으로 세면 화면 표면은 **4개 → 4개**(칩 줄 −1, 코치 카드 +1)로 같고, 누를 수 있는 요소는 **0개 → 4개**(예약 잡기 · 코치 소개 · 자세히 · 이번 주 기록 보기)가 된다. 늘어난 건 카드가 아니라 **행동**이다.

**Q. `context.go('/booking')`이 정말 브랜치를 바꾸나?**
`StatefulShellRoute.indexedStack`은 위치를 브랜치에 매칭해 전환한다. `center_confirm_screen`이 이미 `context.go('/home')`으로 같은 일을 한다. 다만 그 브랜치의 네비게이터 스택이 초기 위치로 리셋되는데, 예약 브랜치는 라우트가 **1개뿐**이라 시각적 차이가 없다. 더 정밀한 제어가 필요하면 `AppShell.build`에서 `navigationShell`을 provider로 노출하는 방법이 있지만, 지금은 필요 없다.

**Q. 홈이 예약 가능 여부를 판정하기 시작하면 예약 탭과 답이 갈리지 않나?**
갈린다 — 그래서 **판정 함수를 새로 만들지 않는다.** 예약 CTA 노출 판정은 `BookablePass.canBookNew`와 같은 규칙을, 슬롯 판정(업그레이드 옵션)은 `BookingRules.evaluate`를 그대로 부른다. 이 저장소가 반복해 겪은 사고(같은 사실을 두 곳에서 읽어 화면끼리 모순)의 재발 방지선이다. 코드 주석에 못박아야 한다.

**Q. 예약 0건인 회원에게 [예약 잡기]를 큼직하게 띄우는 게 압박으로 읽히지 않나?**
문구가 압박하지 않으면 된다. `아직 잡아 둔 수업이 없어요 / 잔여 20회 · 오늘부터 2주 안에서 시간을 고를 수 있어요`는 사실과 선택지만 말한다. 압박은 `잔여 20회 — 연장 상담 가능`을 **항상 노란 경고로** 띄우는 지금 쪽이다. 그건 삭제한다.

**Q. 만료 임계를 D-14/D-7로 잡은 근거는?**
근거는 데이터가 아니라 **회복 가능성**이다. D-14면 주 2회 기준 4회를 더 쓸 수 있고, D-7이면 남은 회차를 다 쓰는 게 대체로 불가능해져 재등록·홀딩이 유일한 선택지가 된다. **이 임계는 전환 렌즈 팀이 실제 잔여 소진 속도로 검증해야 한다** — 내 렌즈에서는 "경고를 아껴야 경고가 된다"까지가 근거다.

**Q. 코치가 1명뿐인데 "센터 코치 N명" 줄을 설계에 넣는 게 낭비 아닌가?**
조건부라 지금은 렌더되지 않는다(`trainer && active` ≥ 2). 데이터가 만들면 나타나고 없으면 없다. 대신 **v1 구현에서 이 줄을 빼도 무방하다** — 카드의 본체는 담당 코치 1명이다. 넣어 둔 이유는 코치가 늘었을 때 홈에 손대지 않아도 되게 하려는 것이고, 뺀다면 그때 추가하면 된다.

**Q. 회원권 만료 후 "남은 회차가 사라진다"고 말해도 되나?**
안 된다. 서버가 하는 일은 상태를 `expired`로 계산해 예약 생성을 거부하는 것이고, 원장은 append-only라 기록이 지워지지 않는다. 그래서 `예약에 쓸 수 없어요`로 쓴다. 앱은 서버가 하지 않는 일을 말하지 않는다.

**Q. 홈이 `checkedInBookingId`를 세션 메모리로만 들고 있어 앱을 껐다 켜면 [셀프 체크인]이 다시 활성화된다.**
사실이다(`CheckedInBookingId`는 `build() => null`). 다만 서버 체크인은 **멱등 upsert**(계약 v1.3)라 재스캔이 무해하고, 회원 입장에서는 "다시 눌러도 되나?"가 잠깐 헷갈릴 뿐이다. 고치려면 `GET /v1/checkin` 같은 조회가 필요한데 **없다**. 우선순위 밖으로 두되 §7에 올려 둘 만한 갭이라 여기 기록한다.

**Q. 다른 두 렌즈와 충돌할 만한 지점은?**
① **홈에 "최근 수업 기록"을 넣자**는 제안이 전환 렌즈에서 나올 수 있다 — 나는 왕복 비용(+1)과 "홈은 다음 것"이라는 이유로 뺐다. 종합 패스에서 판단할 것.
② **경쟁 제품 렌즈가 "코치 목록/추천"을 가져올 수 있다** — §5.2가 그 벽을 명시한다: **다른 코치로는 예약이 성립하지 않는다.** 서버에 담당 변경·상담 요청 채널이 생기기 전에는 목록 UI가 데드엔드를 만든다.
③ **만료 임계값(14/7)**은 내 근거가 정성적이라 전환 렌즈 수치로 덮어써야 한다.
