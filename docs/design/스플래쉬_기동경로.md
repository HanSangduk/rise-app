# 스플래시 — 기동 경로 실측 지도 (설계 전제)

- 작성: 2026-08-28 · 렌즈: **실제 기동 경로 · 타이밍 · 실패 모드**
- 이 문서는 모션을 설계하지 않는다. 모션을 설계하기 **전에** 깔아야 할 지형도다.
- 모든 주장은 읽은 코드에 근거한다. 근거 파일:행은 §9.
- **코드는 한 줄도 고치지 않았다.** 네이티브 리소스·pubspec도 그대로다.

---

## 0. 세 줄 요약

1. **네이티브 스플래시는 Flutter 3.44 템플릿 그대로다.** 안드로이드 4개 파일 + iOS 스토리보드가 SDK 템플릿과 **바이트 단위로 동일**하다(§3.1 diff 결과). 로고 0개, 브랜드 색 0개. iOS 런치 이미지는 **1×1 투명 PNG**다.
2. **Flutter의 첫 프레임은 아무것도 그리지 않는다.** go_router의 최상위 `redirect`가 `GET /v1/me`를 `await`하는 동안 `RouteBuilder`가 `SizedBox.shrink()`를 돌려준다(go_router 16.3.0 `builder.dart:101-104`). 그 시각에 네이티브 스플래시는 **이미 제거된다** — 첫 프레임이 렌더된 시점이 곧 제거 시점이기 때문이다.
3. 그래서 "뚝 끊긴다"의 정체는 색 불일치가 아니라 **네이티브 스플래시가 사라진 뒤의 빈 창**이다. 진짜 색 불일치는 **안드로이드 다크모드에서만** 존재한다(#000000 → #FFFFFF). iOS는 양쪽 다 흰색이라 색은 맞는다.

> **가장 중요한 한 가지** — 이 앱은 **세션을 디스크에 저장하지 않는다**(`session_provider.dart:14`, `build() => null`). 콜드 스타트마다 "내가 누구인지"를 네트워크로 다시 물어야 하고, 그 답이 오기 전에는 **착지할 화면조차 정해지지 않는다**. 스플래시 애니메이션은 이 대기를 장식할 뿐 줄이지 못한다. §7에서 이 가정을 정면으로 다룬다.

## 3. 지금 경험이 깨지는 곳 — 증거

### 3.1 네이티브 스플래시는 손댄 적이 없다 (diff로 확인)

Flutter 3.44.0 SDK 템플릿(`packages/flutter_tools/templates/app/`)과 실제 프로젝트 파일을 그대로 `diff` 한 결과:

| 파일 | 결과 |
|---|---|
| `android/app/src/main/res/values/styles.xml` | **템플릿과 동일** |
| `android/app/src/main/res/values-night/styles.xml` | **템플릿과 동일** |
| `android/app/src/main/res/drawable/launch_background.xml` | **템플릿과 동일** |
| `android/app/src/main/res/drawable-v21/launch_background.xml` | **템플릿과 동일** |
| `ios/Runner/Base.lproj/LaunchScreen.storyboard` | **템플릿과 동일** |
| `ios/Runner/Assets.xcassets/LaunchImage*.png` | 1×1 8-bit gray+alpha — Flutter가 배포하는 기본 플레이스홀더와 동일 규격 |

`pubspec.yaml`에 **`flutter_native_splash`는 없다**(전체 의존성 확인). `lib/` 어디에도 splash·로고 위젯이 없다.

> 요컨대 지금 상태는 "스플래시 디자인이 나쁘다"가 아니라 **스플래시 디자인이 존재하지 않는다**이다. 브랜드 자산은 있는데(`assets/brand/appicon-fg.png`, 크림 `#F6F4EF`) 런치 화면은 그중 아무것도 쓰지 않는다. 유일한 예외가 안드로이드 12+ 시스템 스플래시가 자동으로 얹는 **런처 아이콘**인데, 이건 우리가 배치한 게 아니라 OS가 아이콘을 가져다 쓴 결과다.

### 3.2 색 대조표 — 양쪽 실제 값

| 플랫폼 / 모드 | 네이티브 스플래시 배경 | Flutter 빈 프레임 | Flutter 첫 화면 | 일치? |
|---|---|---|---|---|
| **iOS 라이트** | `#FFFFFF` (스토리보드 하드코딩 `red=1 green=1 blue=1`) | 미측정 (§3.3) | `#FFFFFF` (로그인·센터확인) / `#F7F7F8` (홈) | 색은 **일치** |
| **iOS 다크** | `#FFFFFF` — 스토리보드에 다크 변형이 없다 | 미측정 | `#FFFFFF` / `#F7F7F8` — 앱은 항상 라이트 | 색은 **일치** |
| **Android 라이트** | `#FFFFFF` (`Theme.Light.NoTitleBar` → `colorBackground` = `@android:color/background_light` = `#ffffffff`) | 미측정 | 동일 | 색은 **일치** |
| **Android 다크** | `#000000` (`Theme.Black.NoTitleBar` → `colorBackground` = `@android:color/black` = `#ff000000`) | 미측정 | `#FFFFFF` | **불일치 — 검정에서 흰색으로 튄다** |

AOSP 값은 로컬 SDK(`~/Library/Android/sdk/platforms/android-36/data/res/values/`)에서 직접 확인했다: `themes.xml:612-615`가 `Theme.Black`의 `colorBackground`를 `@color/black`으로, `:507-510`이 `Theme.Light`의 것을 `@color/background_light`로 지정하고, `colors.xml:39`/`:46`이 각각 `#ff000000` / `#ffffffff`다.

**결론 — "색 불일치가 원인인가?" 에 대한 정확한 답:**

- **iOS에서는 아니다.** 양쪽 다 흰색이고, 앱에 `darkTheme`도 `themeMode`도 없어서(`app.dart:60-77`에 `theme:` 하나뿐) 다크모드에서도 흰색으로 통일된다. iOS의 "뚝 끊김"은 색 때문이 아니다.
- **안드로이드 다크모드에서는 맞다.** 검정 → 흰색 전환이 실제로 일어난다. 다만 이건 **다크모드 기기에서만** 나타나는 별개 결함이지, 대표가 본 현상 전체를 설명하지 못한다.
- `#FFFFFF` → `#F7F7F8`(홈 배경)의 차이는 명도 약 3% 차이다. 이건 눈에 띄지 않는다. **이 이론은 기각한다.**

### 3.3 진짜 원인 — 네이티브 스플래시가 사라진 뒤 아무것도 없다

세 개의 사실이 겹친다.

**① 첫 프레임에는 위젯이 없다.**
`app_router.dart:36-42`의 최상위 `redirect`는 `async`이고 `await restoreLanding!()` 안에서 네트워크 왕복을 한다. 그동안 `GoRouterDelegate.currentConfiguration`은 `RouteMatchList.empty`이고(go_router `delegate.dart:211`), `RouteBuilder.build`가 이렇게 답한다:

```dart
if (matchList.isEmpty && !matchList.isError) {
  // The build method can be called before async redirect finishes. Build a
  // empty box until then.
  return const SizedBox.shrink();
}
```
(`go_router-16.3.0/lib/src/builder.dart:101-104`)

`MaterialApp` / `WidgetsApp`은 배경을 칠하는 위젯이 아니다(배경은 `Scaffold`가 칠한다). 그래서 이 구간에는 **페인트 명령 자체가 없다.**

**② 네이티브 스플래시는 그 빈 프레임에 의해 제거된다.**
iOS `FlutterViewController.h`의 `splashScreenView` 문서 주석: *"The splash screen view will be used as a replacement until the first frame is rendered."* 안드로이드도 같은 원리로 런치 배경이 서피스에 덮인다. **"첫 프레임"의 판정에 "무언가를 그렸는가"는 들어 있지 않다.** 빈 씬도 프레임이다.

**③ 그 결과 순서가 이렇게 된다.**

```
[네이티브 스플래시: 흰색]  →  [빈 창: ???]  →  [완성된 화면: 딱]
       0.5~1초                0.3~20초           전환 0프레임
```

빈 창이 **무슨 색으로 보이는지는 이 저장소만으로 결정할 수 없다.** 엔진이 서피스를 투명으로 클리어하고 뷰가 opaque(`FlutterViewController.viewOpaque` 기본 `YES`)이므로 **검정으로 합성될 가능성이 가장 높지만**, 렌더러·기기·OS 버전에 따라 갈릴 수 있다. **§8의 1번 측정 항목**이 이걸 확정하는 일이다. 어느 쪽이든 **브랜드 색은 아니다.**

그리고 마지막 전환에는 애니메이션이 **하나도 없다.** `landing`이 정해지는 순간 go_router가 새 `RouteMatchList`를 세우고 완성된 화면이 즉시 나타난다. 페이드도 크로스디졸브도 없다. "뚝 끊긴다"는 말은 정확한 관찰이다.

**④ 다만 이 현상은 로그인한 회원에게만 온다.**
`restoreAuthLanding`은 `currentUser == null`이면 네트워크를 타지 않고 즉시 `null`을 돌려준다(`session_restore.dart:69-72`). 이 경로는 마이크로태스크 한 번이라 워밍업 프레임 이전에 해소될 가능성이 높다 — 즉 **첫 설치·로그아웃 상태에서는 빈 창이 거의 안 보인다.** 대표가 본 현상은 **재실행하는 기존 회원**의 경로다. 그게 일상 사용의 100%다. (이 "거의 안 보인다"도 §8에서 측정으로 확인할 것.)

### 3.4 목적지가 3개다 — 같은 탭이 매번 같은 곳으로 가지 않는다

```
                       ┌─ Ok ──────────────────────────→ /home
GET /v1/me ────────────┼─ MemberNotLinkedFailure ──┬─ 대기기록 O → /login/center-confirm
                       │                           └─ 대기기록 X → null → /login 유지
                       └─ 그 외 전부(네트워크·5xx·4xx·401) → /login/center-confirm
                                                              + "연결 상태를 확인하지 못했어요"
```

이건 버그가 아니라 의도된 설계다 — `session_restore.dart:22-32`의 주석이 "지하철에서 앱을 켠 회원을 미연결로 오독해 온보딩으로 떨어뜨리던" 과거를 명시적으로 고친 것이라고 적고 있다. 방향은 옳다.

**하지만 스플래시 설계 관점에서는 이게 치명적이다.** 애니메이션의 착지점이 네트워크 결과에 종속되면:
- "로고가 홈 헤더로 변형되는" 류의 **연속성 모션을 쓸 수 없다.** 착지점이 로그인 화면일 수도 있기 때문이다.
- 최소 지속시간을 걸면, 그 시간이 끝난 뒤에도 **어디로 갈지 아직 모를 수 있다.**

## 4. 타이밍 예산

### 4.1 `/v1/me` 한 번에 실제로 붙어 있는 것

| 단계 | 비용 | 비고 |
|---|---|---|
| `getIdToken()` (`dio_client.dart:47`) | 캐시 히트 ≈0ms / 만료 시 왕복 | **우리 타임아웃 밖**. Firebase SDK 자체 정책만 적용 |
| DNS 조회 | 모바일망에서 50~300ms | 콜드 |
| TCP + TLS 핸드셰이크 | 100~400ms | 첫 연결. dio 인스턴스는 provider 수명 = 앱 수명이라 이후 요청은 연결 재사용 |
| Cloud Run 콜드 스타트 | **380~525ms (실측)** | `work_log/P12-audit-sweep.md:33` — 24시간 로그 17회 실측. uptime check가 2분마다 때려 대체로 살아 있다 |
| 서버 처리 | 20~60ms | `VerifyIDToken`(JWKS 캐시, 인프로세스) + Firestore 2읽기(`GetUserIndex` + `GetMember`) |
| 응답 수신 | ≈0 | 페이로드 5개 필드 |

서버 쪽은 싸다. **변동성은 전부 모바일 무선 구간에 있다.** 헬스장 지하 · 엘리베이터 · 지하철이 이 앱의 실사용 환경이라는 점이 중요하다.

### 4.2 타임아웃과 재시도 — 전수 확인

| 항목 | 값 | 근거 |
|---|---|---|
| `connectTimeout` | **10,000ms** | `api_config.dart:11` |
| `receiveTimeout` | **10,000ms** | `api_config.dart:12` |
| `sendTimeout` | 미설정 | GET이라 무관 |
| **재시도** | **0회** | `dio_client.dart:25-61`에 `onRequest`/`onError` 두 개뿐 — 재시도 인터셉터 없음. `guardApi`(`api_result_guard.dart:7-42`)도 예외를 `Failure`로 매핑만 하고 재호출하지 않는다 |
| 백오프 | 없음 | 위와 동일 |
| 스플래시 쪽 최소 지속시간 | **없음** | `lib/` 전체에 `Future.delayed` 0건 |

### 4.3 최악 케이스

```
getIdToken (상한 없음, 토큰 만료 + 망 불안정 시)        …  ? 초
  + connectTimeout                                    … 10.0초
  + receiveTimeout                                    … 10.0초
──────────────────────────────────────────────────────────────
  ≈ 20초 + α  동안 빈 창.  재시도가 없으므로 여기서 한 번에 끝난다.
```

- **p50 추정** ≈ 0.8~1.5초 (엔진 부트 포함, 정상 LTE/Wi-Fi)
- **p95 추정** ≈ 2.5~4초
- **최악** ≈ 20초+

p50/p95는 추정이다 — 이 저장소에 앱 기동 계측이 없다(§8-3). Cloud Run 콜드 스타트만 실측값이 있다.

> **재시도가 없다는 사실이 스플래시 설계에 주는 함의**: "실패하면 스플래시를 유지한 채 한 번 더 시도한다"는 흔한 패턴을 쓰려면 재시도 로직을 **새로 만들어야** 한다. 지금 코드에는 없다.

### 4.4 실패하면 사용자가 보는 화면 — 대표가 본 그 화면

`GET /v1/me`가 네트워크 실패하면 `guardApi`가 `NetworkFailure('연결이 불안정해요')`로 매핑하고(`api_result_guard.dart:30`), `classifyRestore`가 `RestoreOutcome.unknown`으로 분류하며(`session_restore.dart:36`), `restoreLandingRoute`가 `/login/center-confirm`을 돌려준다(`:52`). 동시에 `markConnectionUnknown(failure)`가 실패 사유를 화면 상태에 심는다(`:101`).

코드에서 그대로 재구성한 화면:

```
│  │    네트워크가 돌아오면 아래에서 다시     │  │     본문 :617-619
│  │    확인해주세요. 이미 연결된 회원이라면  │  │

```

**대표가 본 "센터 선택 + 에러 카드"는 이 경로다.** 관찰과 코드가 정확히 맞는다.

이 화면이 나오는 트리거는 세 가지고, 셋 다 같은 곳으로 간다:

| 트리거 | 실제 상황 | 옳은 목적지 |
|---|---|---|
| 네트워크 실패 | 지하·비행기모드·서버 다운 | 홈(캐시) 또는 재시도 |
| **401** | 토큰 폐기·계정 삭제 | **`/login`** ← 지금 여기로 안 간다 |
| 5xx / 기타 4xx | 서버 장애 | 재시도 |

**401이 `/login`으로 가지 않는 것은 결함이다.** `guardApi:24-26`이 401을 `AuthFailure`로 매핑하는데, `classifyRestore`는 `MemberNotLinkedFailure`만 골라내고 나머지 `Err`를 전부 `unknown`으로 묶는다(`session_restore.dart:36`). 동시에 dio 인터셉터가 `sessionProvider.clear()`를 호출하지만(`dio_client.dart:37`), `app.dart:56`의 리스너는 `prev == null`이면 무시하도록 되어 있고 — 복원 중에는 세션이 아직 `null`이므로 — **로그인 복귀가 발동하지 않는다.** 결과: 토큰이 폐기된 사용자가 "네트워크가 돌아오면 다시 확인해주세요"를 보며 영원히 재확인을 누른다.

> 이건 스플래시 작업의 범위 밖이지만, **스플래시를 붙잡는 설계를 하면 이 결함이 더 오래 보인다.** 목록에 남긴다.

### 4.5 `/home`에 착지해도 아직 "사용 가능"이 아니다

`HomeViewModel.build`가 먼저 `await ref.watch(centerPolicyProvider.future)`(`home_view_model.dart:45`)를 하고, 그다음 `loadHome`이 **다섯 번을 순차로** 부른다.

| # | 호출 | 엔드포인트 | 근거 |
|---|---|---|---|
| 0 | `centerPolicy` | `GET /v1/center` | `center_policy_provider.dart` → `center_api.dart:16` |
| 1 | `_readStaffMap()` | `GET /v1/staff` | `home_repository_impl.dart:39` |
| 2 | `fetchMyPasses` | `GET /v1/passes` | `:40` |
| 3 | `fetchMyBookings` | `GET /v1/bookings` | `:86` |
| 4 | `fetchHomeworks` | `GET /v1/homeworks` | `:137` |
| 5 | `fetchHwChecks` | `GET /v1/hw-checks` | `:155` (best-effort, try/catch) |

`Future.wait`는 **한 곳도 없다.** 1번은 나머지와 완전히 독립적이고, 3·4번은 2번의 `trainerId`에만 의존해 서로 독립이다 — 즉 **병렬화 가능한데 지금은 순차다.** 그동안 화면은 헤더 + 빨간 `CircularProgressIndicator`다(`home_screen.dart:85`).

**즉 회원이 실제로 보는 대기는 두 번이다:**

```
빈 창 (0.3~20초)   →   홈 헤더 + 스피너 (5~6 왕복)   →   내용
    ↑ 세션 복원              ↑ 홈 데이터
```

스플래시를 아무리 예쁘게 만들어도 **두 번째 대기는 그대로 남는다.** 캐시(`centerPolicy`는 성공 시 `keepAlive`, `staffMap`은 15분 TTL)가 있어도 콜드 스타트에는 전부 미스다.

## 5. 콜드 vs 웜 스타트

| 구분 | 정의 | `main()` 재실행 | 네이티브 스플래시 | 세션 복원 | 일상 빈도 |
|---|---|---|---|---|---|
| **Cold** | 프로세스 없음 | O | O | O (`/v1/me`) | 하루 첫 실행, OOM 킬 후, 재부팅 후 |
| **Warm** | 프로세스는 있고 Activity 파괴 | O | O (짧게) | O | 드묾 |
| **Hot** | Activity·프로세스 살아 있음 | **X** | **X** | **X** | **일상의 대부분** |

안드로이드는 `launchMode="singleTop"` + 광범위한 `configChanges`(`orientation|…|uiMode|density|…`)를 선언해(`AndroidManifest.xml:36,39`) 회전·다크모드 전환·글꼴 배율 변경으로도 Activity가 재생성되지 않는다. 즉 홈 버튼 → 다시 아이콘 탭은 **hot start**이고, `main()`도 라우터 redirect도 돌지 않는다.

### 최소 지속시간 애니메이션에 주는 함의

1. **Dart로 만든 스플래시는 cold/warm에서만 뜬다.** 이건 좋은 성질이다 — "하루에 한 번만 본다"는 뜻이라 조금 길어도 용서된다. 반대로 hot start를 커버하려면 라이프사이클 옵저버를 따로 붙여야 하는데, **그건 하지 말아야 한다**(하루에 열 번 보는 애니메이션은 장애물이다).

2. **최소 지속시간은 p50을 늘리고 최악을 못 가린다.**
   - p50 0.8~1.5초 구간에 1.8초 바닥을 깔면 빠른 기기·따뜻한 캐시에서 **일부러 기다리게** 만든다.
   - 최악 20초에서는 애니메이션이 1.8초에 끝나고 **다시 빈 화면 18초**가 된다. 최소값은 최악을 못 덮는다.
   - 최악을 덮으려면 상한 없는 hold가 필요한데, 그건 §6의 리스크를 전부 켠다.

3. **따라서 바닥(floor)과 천장(ceiling)을 함께 둬야 한다.** 예: floor ≈ 800~900ms(전환이 뚝 끊기지 않을 최소), ceiling ≈ 2.5초. 천장을 넘어가는 대기는 **스플래시가 아니라 착지 화면 안의 스켈레톤**이 받아야 한다. 그러려면 착지 화면이 **복원 완료 전에 정해져야** 한다 — §7로 이어진다.

4. **웜 스타트에서 애니메이션이 잘릴 수 있다.** 프로세스가 살아 있어 복원이 100ms에 끝나면, floor가 없을 때 애니메이션이 시작하자마자 끝난다. floor는 이 경우를 위해 필요하다 — 최악을 가리기 위한 게 아니라.

## 6. 스플래시를 붙잡으면 깨지는 것 — 구체적 리스크

### 6.1 딥링크 — 지금 없다. 그리고 지금 구조는 딥링크를 삼킨다

**현재 상태**: `AndroidManifest.xml:50-53`에 `MAIN`/`LAUNCHER` 인텐트 필터 **하나뿐**이다. `VIEW` 액션도 `android:scheme`도 App Links 설정도 없다. `Info.plist`에 `CFBundleURLTypes`도 associated domains도 없다. **딥링크는 존재하지 않는다.**

**하지만 만드는 순간 지금 코드가 깨진다.** `app_router.dart:36-42`:

```dart
redirect: (context, state) async {
  if (restoreAttempted) return null;
  restoreAttempted = true;
  final landing = await restoreLanding!();
  return landing == state.matchedLocation ? null : landing;
},
```

첫 내비게이션이 **딥링크로 들어온 `/booking`이든 런처로 들어온 `/login`이든** 이 래치는 한 번만 돌고, `state.matchedLocation`을 **루프 방지 비교에만** 쓴 뒤 `landing`을 그대로 돌려준다. 로그인된 회원이 예약 딥링크를 타면 `landing = '/home'`이 되어 **딥링크 목적지가 통째로 사라진다.**

스플래시를 여기에 얹으면 이 문제가 한 겹 더 감춰진다. **딥링크를 도입할 계획이 있다면 이 redirect를 먼저 고쳐야 한다.**

### 6.2 알림 탭 — 지금 없다. 그러나 곧 생긴다

`pubspec.yaml`에 `firebase_messaging`도 로컬 알림 패키지도 없다. 지금은 리스크가 아니다.

다만 예약 리마인더·승인 알림은 이 제품에서 자연스러운 다음 기능이고(§4.4의 "대표가 승인해도 앱은 알 방법이 없다" — `center_confirm_screen.dart:628-633` 주석이 직접 인정한다), 그때 "알림 탭 → 특정 예약"이 필요해진다. **스플래시를 "무조건 N초 재생 후 `/home`"으로 만들면 그 시점에 다시 뜯어야 한다.** 스플래시의 종료 조건은 시간이 아니라 **"착지 라우트가 확정됐다"**여야 한다.

### 6.3 세션 만료 리다이렉트 — 경합이 실재한다

`app.dart:55-58`:
```dart
ref.listen(sessionProvider, (prev, next) {
  if (prev == null || next != null) return;
  _router.go('/login');
});
```

세션이 있다가 사라지면(주로 dio 인터셉터의 401 — `dio_client.dart:36-39`) 라우터가 즉시 `/login`으로 간다. **이건 `redirect` 밖에서, 래치와 무관하게, 언제든 발동한다.**

스플래시를 오버레이로 띄우고 타이머로 내리는 구조라면:
```
t=0.0s  스플래시 시작 (최소 1.8초 예정)
t=0.6s  /v1/me 성공 → 세션 set → /home 착지 결정
t=1.2s  홈이 부르는 다른 API에서 401 → sessionProvider.clear()
        → app.dart 리스너가 _router.go('/login')  ← 스플래시 뒤에서 조용히 일어남
t=1.8s  스플래시가 "예정대로" /home으로 내비게이트   ← ★ 로그아웃된 사용자를 홈에 세운다
```

**타이머가 라우팅 결정을 덮어쓰는 순간 세션이 없는 사용자가 홈에 앉는다.** 스플래시는 목적지를 **스스로 정하면 안 되고**, "이미 정해진 목적지가 그려질 때까지 가린다"로만 동작해야 한다.

### 6.4 `flutter_native_splash`의 `preserve`/`remove`를 쓰면

이 패키지는 지금 없다. 도입해서 `preserve()`로 네이티브 스플래시를 유지하면, **첫 프레임이 렌더돼도 스플래시가 안 내려간다.** 그러면:
- §3.3의 빈 창 문제는 사라진다(스플래시가 계속 덮으므로). **이건 실제 이득이다.**
- 대신 `remove()`를 부르는 코드 경로가 **모든** 실패 경로를 커버해야 한다. `restoreAuthLanding`은 `try/catch`가 `FirebaseAuth` 접근 한 곳뿐이고(`session_restore.dart:68-72`), `loadSession`은 `guardApi`가 삼키지만 그 바깥에서 예외가 나면 `remove()`가 영영 안 불린다 → **앱이 스플래시에 갇힌다.** 안전장치로 무조건 해제하는 타임아웃이 필요하다.
- 안드로이드 12+에서는 시스템 스플래시 API가 별도 규약(`setKeepOnScreenCondition` + exit 애니메이션 슬롯)을 갖는다. 도입 전에 **2026-08 시점 기준 최신 버전과 Android 12+ 동작을 실기기에서 확인**할 것 — 이 문서는 그 검증을 하지 않았다.

### 6.5 6.4MB 가변폰트

`assets/fonts/PretendardVariable.ttf`는 **6,739,336 바이트**다(`pubspec.yaml:143`에서 번들). 첫 텍스트 페인트에 로드·파싱 비용이 붙는다.

스플래시가 **텍스트를 쓰면**(예: "RISE CONDITIONING" 워드마크) 그 비용이 스플래시 첫 프레임으로 앞당겨진다. **벡터/이미지 기반 스플래시가 더 안전하다** — 폰트 로드는 그 뒤 첫 실제 화면으로 미룬다. 반대로 "스플래시에서 미리 로드해 두면 다음 화면이 빨라진다"는 논리도 성립하니, **어느 쪽이 나은지는 측정으로 정할 일**이다(§8-5).

## 7. 반박 — 검증되지 않은 가정들

### ❌ "네이티브 스플래시와 Flutter 첫 화면의 색이 안 맞아서 번쩍인다"

**부분적으로만 맞다.** iOS는 양쪽 다 `#FFFFFF`로 일치하고 앱에 다크 테마가 없어 모드와 무관하게 일치한다. 안드로이드 라이트도 일치한다. **불일치는 안드로이드 다크모드 하나뿐**이고, 그건 별개로 고쳐야 할 결함이지 "뚝 끊긴다"의 주원인이 아니다. 주원인은 §3.3의 **빈 프레임**이다.

### ❌ "스플래시 애니메이션을 넣으면 체감이 나아진다"

**빈 창을 브랜드 화면으로 바꾸는 것까지는 확실한 개선이다.** 그 너머는 아니다. 착지점이 `/home`·`/login/center-confirm`·`/login` 셋 중 하나로 **네트워크에 따라 갈리는 한**(§3.4), 애니메이션은 "예쁜 대기"일 뿐 "짧은 대기"가 되지 못한다. 그리고 최소 지속시간을 넣으면 p50은 **더 길어진다**.

### ❌ "세션 복원은 원래 앱마다 하는 것이니 어쩔 수 없다"

**이 앱의 구조가 유별나게 취약하다.** `sessionProvider`는 `build() => null`이고(`session_provider.dart:14`) 디스크에서 아무것도 읽지 않는다. 앱 전체에서 디스크에 남기는 건 **가입 요청 기록 하나뿐**이다(`join_request_store_impl.dart`). 즉:

> **콜드 스타트마다, 네트워크가 성공해야만, "내가 누구인지"를 알 수 있다.**

`/v1/me`가 돌려주는 건 `{uid, role, center_id, member_id, name}` 다섯 필드다. 민감정보가 아니고, 회원 한 명이 하루에 바뀔 값도 아니다. 이걸 로컬에 저장하면:

- 착지 라우트가 **네트워크 이전에** 정해진다 → 스플래시가 **결정적 길이**를 가질 수 있다.
- `/v1/me`는 백그라운드 재검증으로 내려간다 → 실패해도 회원은 홈에 있다.
- §4.4의 "지하철에서 켰더니 센터 선택 화면" 이 사라진다.
- §5-3의 floor/ceiling 설계가 성립한다.

**이게 "프리미엄 스플래시"의 실제 전제 조건이다.** 애니메이션보다 먼저다. 저장을 도입한다면 `shared_preferences`가 이미 있으니 새 의존성도 필요 없다 — 다만 `session_restore.dart:22-32`가 세운 "모르는 걸 미연결로 단정하지 않는다" 원칙을 캐시 만료·불일치 처리에 그대로 이어가야 한다(캐시가 있다고 무기한 신뢰하면 폐기된 계정이 홈에 남는다).

### ❌ "hot start에서도 스플래시를 보여줘야 브랜드가 산다"

hot start는 `main()`을 다시 돌리지 않는다(§5). 억지로 라이프사이클 훅으로 띄우면 **하루에 열 번 보는 장애물**이 된다. 하지 말 것.

### ❌ "타임아웃이 10초니까 최악은 10초다"

`connectTimeout`과 `receiveTimeout`은 **더해진다**(연결 9.9초 → 무응답 10초). 게다가 그 앞에 `getIdToken()`이 우리 타임아웃 **바깥**에 있다(`dio_client.dart:46-53`의 `try/catch`는 예외를 삼킬 뿐 시간을 제한하지 않는다). 최악은 **20초 + α**다. DNS 지연이 `connectTimeout`에 온전히 포함되는지도 확인하지 않았다.

## 8. 설계 전에 측정해야 할 것

번호 순서가 곧 우선순위다.

1. **빈 프레임의 실제 색.** 240fps(또는 기기 화면 녹화 + 프레임 추출)로 안드로이드 라이트/다크, iOS 라이트/다크 4조합을 찍는다. `#000000`인지 `#FFFFFF`인지 `NormalTheme` 배경인지 확정한다. §3.3의 유일한 미확정 항목이고, 이 값이 **네이티브 스플래시 배경색을 무엇으로 정할지**를 결정한다.
2. **각 구간의 실제 길이.** 아이콘 탭 → 네이티브 스플래시 제거 → 첫 실제 페인트 → 홈 스피너 종료. 같은 녹화에서 프레임 번호로 뽑으면 된다. 릴리스 빌드, 실기기(P11에서 쓴 갤럭시 S21 울트라), 운영 백엔드로.
3. **로그아웃 상태에서 빈 창이 실제로 보이는가.** §3.3-④의 "마이크로태스크라 워밍업 프레임 이전에 해소될 것" 은 추론이다. 로그아웃 상태와 로그인 상태를 각각 녹화해 비교한다. 결과에 따라 "첫 설치 경험"과 "재방문 경험"의 설계가 갈린다.
4. **저품질 망에서의 p95.** 안드로이드 개발자 옵션의 네트워크 스로틀 또는 Charles로 지연을 넣고 `/v1/me` 왕복을 잰다. §4.3의 추정치를 실측으로 대체한다.
5. **폰트 로드 비용.** 스플래시에 텍스트를 넣은 버전과 벡터만 넣은 버전의 첫 페인트 시각 차이(§6.5).
6. **다크모드 안드로이드의 검정→흰색 전환.** 실제로 몇 프레임인지, 눈에 띄는지. 이건 스플래시 작업과 별개로 지금 고칠 수 있다(`values-night/styles.xml`의 부모 테마 교체).
