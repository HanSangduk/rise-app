# 스플래시 모션 — 라이즈 컨디셔닝 회원 앱 (설계)

- 작성: 2026-08-28 · 렌즈: **모션 자체와 브랜드 표현**
- 이 문서의 모든 현재 동작 주장은 **읽은 코드의 파일:라인**, **설치된 Flutter 3.44.0 SDK 소스**, **pub.dev 1차 조회(2026-08-28)**, **직접 계산한 명암비**에 근거한다. 근거 목록은 §10.
- **코드는 한 줄도 고치지 않았다.** 설계만.

## 0. 요청과 답 — 다섯 문장

> "스플래쉬 화면도 로고로 짧은 영상을 만들어서 고급스러운 앱처럼 만들어줘. 지금은 너무 앱 로고 나오고 바로 나오니까 이상하잖아?" — 람

1. **"로고가 나오고 바로"가 아니다.** 로고가 나온 뒤 **아무것도 없는 화면이 한 번 더** 끼어 있고(§1-2), 그게 최대 20초까지 갈 수 있다(§1-4).
2. Flutter 쪽 스플래시는 **존재하지 않는다.** 안드로이드·iOS 네이티브 설정도 전부 **Flutter 템플릿 기본값 그대로**다 — 아무도 손댄 적이 없다(§1-1).
3. **로고 영상은 틀린 처방이다.** targetSdk 36이라 안드로이드 12+ OS가 **Flutter가 무엇을 그리기도 전에 이미 로고를 완성된 형태로** 보여 준다. 그 뒤에 로고 등장 애니메이션을 또 트는 건 같은 배우를 두 번 소개하는 것이고, 지금의 "이상함"을 **키운다**(§2-1).
4. 그래서 채택안은 **등장이 아니라 퇴장**이다 — 네이티브 마지막 프레임과 **픽셀 단위로 같은** Flutter 첫 프레임에서 시작해, 마크의 **베이지 점 하나만** 도착시키고(260ms), 크림 바탕을 앱으로 녹여 내보낸다(280ms). 최대 630ms, 그마저도 앱이 **실제로 일하고 있을 때만**(§3·§4).
5. 이 설계가 **혼자서는 못 고치는 것이 하나** 있다: 라우터가 세션 복원을 무한정 기다린다(§1-4). 게이트를 먼저 내보내 봐야 그 아래는 여전히 빈 화면이라 소용이 없다 — **라우터 예산 2200ms가 선행 조건이다**(§5-5).

## 1. 지금 실제로 일어나는 일

### 1-1. 4단계 — 그리고 그중 둘은 아무도 손대지 않은 템플릿이다

| # | 단계 | 무엇이 그린다 | 실제 내용 | 근거 |
|---|---|---|---|---|
| ① | OS 런처 아이콘 | Android `SplashScreen` API / iOS 아이콘 줌 | 적응형 아이콘 = 크림 `#F6F4EF` 배경 + 네이비 R 마크 | `mipmap-anydpi-v26/ic_launcher.xml:3-8` · `values/colors.xml:3` |
| ② | 네이티브 런치 화면 | Android `windowBackground` / iOS `LaunchScreen.storyboard` | **로고 없음.** iOS는 흰 배경 + **1×1픽셀 빈 PNG**. Android는 `?android:colorBackground` 단색 | iOS `LaunchScreen.storyboard:19,22` · `drawable-v21/launch_background.xml:4` |
| ③ | Flutter 첫 프레임 ~ 라우터 결정 | `GoRouterDelegate` | **`SizedBox.shrink()` — 즉 아무것도 안 그린다** | `go_router-16.3.0/lib/src/builder.dart:101-105` |
| ④ | 착지 화면 | `PhoneScreen` / `HomeScreen` / `CenterConfirmScreen` | 전환 없이 **툭** 나타난다 | `app_router.dart:44-78` |

②와 ③이 **둘 다 빈 화면**이다. 그리고 ①→②, ②→③, ③→④ **세 번 다 하드컷**이다. 람이 느낀 "이상함"의 정체는 로고가 짧아서가 아니라 **이음매가 세 개고 그 사이가 비어 있어서**다.

②의 근거를 정확히:

```
LaunchScreen.storyboard:19   <imageView ... image="LaunchImage" ...>
LaunchScreen.storyboard:22   <color key="backgroundColor" red="1" green="1" blue="1" alpha="1" .../>
```

그 `LaunchImage`는 `Assets.xcassets/LaunchImage.imageset/LaunchImage@{1,2,3}x.png` — 셋 다 **1×1 크기, 68바이트**(직접 헤더 파싱으로 확인). Flutter 템플릿이 넣어 주는 빈 자리표시자 그대로이고, 주석 `<!-- You can insert your own image assets here -->`(`launch_background.xml:6-11`)도 **주석 처리된 채 남아 있다**.

### 1-2. ③에서 왜 아무것도 안 보이는가 — 원문 그대로

```dart
// go_router-16.3.0/lib/src/builder.dart:101-105
if (matchList.isEmpty && !matchList.isError) {
  // The build method can be called before async redirect finishes. Build a
  // empty box until then.
  return const SizedBox.shrink();
}
```

`createRouter`의 리다이렉트가 **`async`**이고(`app_router.dart:36-42`) 그 안에서 `restoreLanding()`을 `await` 한다(`:39`). 그동안 라우트가 하나도 확정되지 않으므로 매치 리스트가 비어 있고, go_router는 위 분기를 탄다.

그리고 `MaterialApp`은 배경을 칠하지 않는다 — 배경을 칠하는 건 `Scaffold`다(`flutter/lib/src/material/scaffold.dart:3237`, `themeData.scaffoldBackgroundColor`). 라우트가 없으니 `Scaffold`도 없다. **결과: 이 구간에 앱이 칠하는 픽셀이 0개**이고, 화면에는 네이티브 윈도 배경이 그대로 남는다.

### 1-3. 다크모드 안드로이드에서는 여기가 **검정**이다

| 파일:라인 | 내용 |
|---|---|
| `values-night/styles.xml:4` | `LaunchTheme` parent = `@android:style/Theme.Black.NoTitleBar` |
| `values-night/styles.xml:15-16` | `NormalTheme` → `windowBackground` = `?android:colorBackground` |
| `app.dart:60-63` | `MaterialApp.router(theme: buildAppTheme(), ...)` — **`darkTheme`도 `themeMode`도 없다** |
| `app_theme.dart:7-10` | `buildAppTheme()`는 `brightness: Brightness.light` 고정 |

즉 시스템이 다크모드인 기기에서 이 앱은:

**크림 원 위 네이비 R(①) → 검정 화면(②·③) → 흰 화면(④)**

앱 자체는 다크모드를 **지원하지 않는데** 런치 화면만 다크모드를 따라가고 있다. 이건 취향 문제가 아니라 **버그**다. 스플래시 작업에서 반드시 같이 고쳐야 한다(§6-3).

### 1-4. 최악의 경우 — 빈 화면이 20초 이상 지속될 수 있다

③의 길이는 `restoreAuthLanding`의 소요 시간과 정확히 같다. 그 경로를 끝까지 따라가면:

| 단계 | 파일:라인 | 비용 |
|---|---|---|
| `FirebaseAuth.instance.currentUser` | `session_restore.dart:69` | 동기 · 0ms |
| 미로그인이면 즉시 반환 | `session_restore.dart:73` | **await 0개 → ~0ms** |
| `loadSession()` | `session_restore.dart:76` → `auth_repository_impl.dart:206-230` | 아래 둘 |
| ↳ ID 토큰 확보 (인터셉터) | `dio_client.dart:47` `await ...getIdToken()` | 캐시 유효(1시간 이내)면 0ms, **만료면 네트워크 왕복 1회** |
| ↳ `GET /v1/me` | `me_api.dart` · `guardApi` | 네트워크 왕복 1회 |
| dio 타임아웃 | `api_config.dart:11-12` | `connectTimeout` **10000ms** + `receiveTimeout` **10000ms** |
| `store.read()` / `store.clear()` | `session_restore.dart:85,92` | shared_preferences 디스크 · 1~5ms |

**네트워크 왕복이 0회 · 1회 · 2회로 갈린다.** 지하철·엘리베이터처럼 연결이 끊기는 상황에서 dio가 두 타임아웃을 다 소진하면 **20초 넘게 빈 화면**이다. 게다가 토큰 갱신까지 걸리면 그 앞에 Firebase SDK의 자체 타임아웃이 더 붙는다.

**복원 실패 자체는 이미 잘 처리돼 있다.** `guardApi`가 타임아웃을 `NetworkFailure`로 매핑하고(`api_result_guard.dart:30`), `classifyRestore`가 그걸 `RestoreOutcome.unknown`으로 분류하며(`session_restore.dart:36`), `restoreLandingRoute`가 재확인 화면으로 착지시킨다(`session_restore.dart:52`). **결론은 옳은데 그 결론에 도달하는 데 20초가 걸리고, 그동안 화면이 비어 있다.** 이게 시작 경험에서 제일 나쁜 하나다.

### 1-5. 지금 런타임에 **로고 이미지가 아예 없다**

`pubspec.yaml:127-143`의 `flutter:` 섹션에는 `uses-material-design`과 `fonts`뿐 — **`assets:` 키가 없다.** 따라서 `assets/brand/appicon-{master,fg,mono}.png`는 **앱 번들에 들어가지 않는다.** 이 파일들은 `flutter_launcher_icons`가 빌드 타임에 디스크에서 읽어 갈 뿐이다(`pubspec.yaml:111-125`).

Flutter가 현재 그릴 수 있는 브랜드 요소는 로그인 화면의 **텍스트 워드마크** 하나다 — `RichText`로 `RISE` + 레드 `CONDITIONING`(`phone_screen.dart:54-62`, `AppTypography.logo` = 24px/w900, `app_typography.dart:69-73`).

이 사실이 §6-2의 설계를 결정한다: **자산을 추가하지 않고 `Path`로 그린다.**

### 1-6. 브랜드 팔레트가 둘로 갈라져 있다 (모션 설계의 핵심 제약)

| 팔레트 | 값 | 근거 |

그리고 `design/brand/README.md:15-16`이 명시한다:

> 앱 테마의 `AppColors.red`와는 **다른 팔레트**다 — 마크는 브랜드 보드의 원색을 그대로 쓴다. **마크를 앱 색으로 다시 칠하지 말 것.**

## 2. "로고 영상"은 왜 틀린 처방인가

### 2-1. 결정적 이유 — OS가 이미 로고를 다 보여 준 뒤다

`android/app/build.gradle.kts:32`가 `targetSdk = flutter.targetSdkVersion`이고, Flutter 3.44의 그 값은 **36**이다(`flutter/packages/flutter_tools/gradle/src/main/kotlin/FlutterExtension.kt:34`, `val targetSdkVersion: Int = 36`).

targetSdk ≥ 31이면 **안드로이드 12+ 시스템 스플래시가 강제로 적용된다.** OS가 런처 아이콘을 화면 중앙에 **완성된 형태로** 띄우고, 자체 진입·퇴장 애니메이션을 돌린다. 앱이 끌 수 없다. iOS도 홈 화면에서 실행하면 **앱 아이콘이 런치 화면으로 줌인**되는 시스템 전환이 항상 붙는다.

그리고 그 위에 `main.dart:10`의 `await Firebase.initializeApp(...)`이 **`runApp` 앞에** 있다 — Firebase 초기화가 끝날 때까지 Flutter는 첫 프레임을 **그리지 못한다.**

정리하면, **Flutter가 무엇이든 그릴 수 있게 되는 시점에는 이미**:

- 로고가 완성된 형태로 화면에 있었고 (①)
- 사용자는 그걸 최소 수백 ms 봤다

이 상태에서 "로고가 그려지는 애니메이션"을 트려면 **먼저 로고를 지워야 한다.** 완성된 로고 → 사라짐 → 다시 그려짐. 사용자에게는 **깜빡임 = 버그**로 읽힌다. 지금의 이상함을 고치는 게 아니라 **하나 더 만드는 것**이다.

> **그러므로 이 화면에 필요한 건 등장 연출이 아니라 퇴장 연출이다.** 이게 이 문서 전체의 축이다.

### 2-2. 비디오 파일의 나머지 비용

로고 영상을 정말 넣는다면 대가는 이렇다.

| 비용 | 내용 |
|---|---|
| **첫 프레임이 늦다** | `video_player`는 플랫폼 코덱 초기화 + 디코더 워밍업이 필요하다. 지금 문제인 **빈 구간을 더 길게** 만든다 |
| **끊을 수 없다** | 비디오는 고정 길이다. 복원이 200ms에 끝나도 영상은 자기 길이를 다 쓴다 — §5의 조정 규칙을 **구조적으로** 못 만든다 |
| **이음매가 보인다** | 영상의 배경색은 인코딩된 값이고 기기 배경은 렌더된 값이다. 크림 대 크림이라도 색공간·감마 차이로 **가장자리 선**이 남는다 |
| **해상도가 고정** | 3x 기기에서 1080p 영상은 흐리고, 세로/가로 비율마다 별도 파일이 필요하다 |
| **용량** | 1초 1080p ≈ 200KB~1MB. §6-2의 벡터 경로는 **Dart 코드 30줄 미만, 자산 0바이트** |
| **의존성** | `video_player`는 런타임 플러그인이다. 반면 §6-3의 `flutter_native_splash`는 **`dev_dependencies`로 끝나고 런타임에 남지 않는다** |
| **접근성** | 영상은 `disableAnimations`(§7-1)를 존중할 방법이 없다 — 정지 프레임을 따로 만들어야 한다 |

Lottie·Rive도 같은 문제를 대부분 공유한다(고정 길이 + 런타임 의존성 + 자산). 둘 다 현재 `pubspec.lock`에 **없다**(직접 조회).

### 2-3. 그러면 "고급스러운"은 어디서 나오는가

브랜드 모션에서 고급스러움은 **길이**가 아니라 **연속성**에서 나온다. 지금 이 앱에 없는 것 셋:

| 없는 것 | 지금 | 채택안 |
|---|---|---|
| **연속성** | ①→②에서 로고가 사라진다. ②→③→④가 전부 하드컷 | 네이티브 마지막 프레임 = Flutter 첫 프레임 (§3-3) |
| **생명감** | ③이 완전히 정지한 빈 화면 | 지각 임계 바로 아래의 느린 드리프트 (§4-1 "호흡") |
| **의도된 퇴장** | 착지 화면이 툭 나타난다 | 마크가 지나가고 앱이 그 뒤에서 올라온다 (§4-3) |

세 개 다 **시간을 쓰지 않고** 얻을 수 있다. 그게 이 설계의 전제다.

## 3. 채택안 — 「점이 도착한다」

### 3-1. 한 줄 정의

> **네이티브 스플래시는 점 없는 R 마크를 보여 준다. Flutter가 이어받아 베이지 점 하나를 제자리에 도착시키고, 크림 바탕을 앱으로 녹인다.**

마크가 **앱이 열리는 순간에 스스로 완성된다.** 이게 이 화면의 이야기 전부다.

### 3-2. 왜 하필 점인가 — 다섯 가지 근거

1. **분리 가능하다.** `rise-mark.svg:20-26`이 네이비 획 3개의 `<g>`, `:27`이 베이지 원 하나 — 파일 구조상 이미 별개 요소다.
2. **끊겨도 안 망가진다.** 점 없는 R은 그 자체로 완결된 마크다(획 3개로 R이 다 읽힌다). 어느 프레임에서 잘라도 **깨진 로고가 되지 않는다** — §5의 조정 규칙이 성립하는 이유.
3. **브랜드 규칙을 안 어긴다.** `rise-mark.svg:18`이 금지한 건 요소를 **옮기는** 것이다. 점은 `(287, 284.5)`에서 **한 번도 움직이지 않는다** — 제자리에서 반지름과 불투명도만 변한다.
4. **원래 마크에서 유일한 악센트다.** 셋 중 혼자만 베이지고, 혼자만 획이 아닌 도형이고, 위치도 우하단 마침표 자리다. **하나만 움직이고 나머지는 가만히 있는 것** — 고급 브랜드 모션의 기본형이다.
5. **가장 싸다.** `Canvas.drawCircle` 하나의 반지름과 알파. `saveLayer` 없음, 자산 없음.

### 3-3. 정렬 — 이 설계에서 **1순위**

> **네이티브 스플래시의 마지막 프레임과 Flutter의 첫 프레임이 픽셀 단위로 같아야 한다.** 여기가 어긋나면 그 뒤 모든 모션이 무의미하다. 이음매를 감추려고 만든 애니메이션이 이음매를 강조하게 된다.

## 4. 모션 명세

### 4-1. 타임라인 — `t = 0`은 Flutter 첫 프레임

| 구간 | t (ms) | 대상 | from → to | 커브 |
|---|---|---|---|---|
| **정합** | 0 | 크림 바탕 + 네이비 획 3개 | (정지) | — |
| **정지** | 0 → 90 | 전부 | 변화 없음 | — |
| **등장** | 90 → 350 | 베이지 점 **반지름 계수** | 0.86 → 1.00 | `easeOutCubic` |
| | 90 → 250 | 베이지 점 **불투명도** | 0 → 1 | `easeOut` |
| **호흡** | 0 → 1400 | 마크 전체 `scale` | 1.000 → 1.014 | `linear` |
| **대기** | ≥ 350 | 호흡만 지속 | — | — |
| **퇴장** | +0 → +180 | 마크(획+점) 불투명도 | 1 → 0 | `easeIn` |
| | +0 → +280 | 마크 `scale` | 1.014 → 1.052 | `easeInCubic` |
| | +0 → +280 | 크림 바탕 불투명도 | 1 → 0 | `easeInOutCubic` |
| | +0 → +280 | 앱 콘텐츠 `scale` | 0.985 → 1.000 | `easeOutCubic` |
| | +0 → +200 | 앱 콘텐츠 불투명도 | 0 → 1 | `easeOut` |

**Flutter 쪽 최대 노출 = 350 + 280 = 630ms.** 그마저도 앱이 실제로 일하고 있을 때만 다 쓴다(§5-2).

전부 Flutter 기본 커브다 — `Curves.easeOutCubic` / `easeOut` / `easeIn` / `easeInCubic` / `easeInOutCubic` / `linear`. **커스텀 `Cubic`을 만들지 않았다.**

### 4-2. 각 숫자의 근거

| 값 | 왜 |
|---|---|
| **0→90ms 정지** | 이 90ms가 §3-3의 픽셀 매칭을 **눈에 증명**한다. 첫 프레임에서 뭔가 즉시 움직이면 뇌가 "장면이 바뀌었다"로 읽고, 그 순간 이음매가 드러난다. 정지가 "같은 화면이 계속되고 있다"를 확정한 뒤에 움직여야 한다 |
| **반지름 0.86 → 1.00** | 0에서 키우면 "뿅" 하고 튀어나온다(장난스럽다). 86%에서 시작하면 **이미 거기 있던 것이 또렷해지는** 느낌 — 훨씬 비싸 보인다 |
| **오버슈트 없음** | `easeOutBack`을 **의도적으로 배제**했다. 바운스 = 친근함/장난. 고급 = 단호함. `easeOutCubic`은 끝에서 완전히 멎는다 |
| **불투명도가 반지름보다 먼저 끝난다** (160 vs 260ms) | 점이 **선명해진 뒤에 자리를 잡는다.** 반대면 흐릿한 것이 커지는 = 초점이 안 맞는 인상이 된다 |
| **호흡 1.4%/1400초** | 초당 1%가 안 되는 드리프트. 개별로는 지각 임계 이하지만 **없으면 화면이 "멈췄다"로 읽힌다.** 스피너를 쓰지 않고 "살아 있다"를 말하는 유일한 방법 |
| **호흡이 `linear`** | 이징을 넣으면 "동작"으로 인지되고, 그 순간 드리프트가 아니라 애니메이션이 된다. 등속이라야 배경에 머문다 |
| **마크가 바탕보다 먼저 나간다** (180 vs 280ms) | 같이 나가면 반투명 마크가 앱 콘텐츠 위에 **280ms 동안 겹쳐** 지저분해진다. 마크를 먼저 비우면 마지막 100ms는 **깨끗한 크림→흰색**만 남는다 |
| **크림 → 흰색 명암비 1.10:1** | §7-2 실측. 이 전환은 **거의 보이지 않는다** — 바탕이 "바뀌는" 게 아니라 "확정되는" 느낌. 이게 이 설계에서 제일 고급스러운 디테일이고, 브랜드 팔레트가 둘로 갈린 §1-6 문제의 해답이기도 하다 |

### 4-3. 퇴장의 깊이 — 여기가 실제 트릭이다

두 요소가 **반대 속도로 같은 방향**을 향한다.

- **마크**: `1.014 → 1.052`, `easeInCubic` (가속하며 멀어짐) + 불투명도 소멸 → **카메라를 스쳐 지나간다**
- **앱 콘텐츠**: `0.985 → 1.000`, `easeOutCubic` (감속하며 정착) → **뒤에서 앞으로 올라온다**

둘 다 관찰자 쪽으로 오지만 속도가 달라 **평면을 통과하는** 감각이 생긴다. 단순 크로스페이드와 비용은 같은데(레이어 2장) 인상은 전혀 다르다.

`saveLayer` 예산: 퇴장 280ms 동안만 콘텐츠에 `FadeTransition` + `ScaleTransition`이 걸린다.

> **퇴장이 끝나면 게이트는 `child`를 그대로 반환해야 한다.** `Transform.scale(scale: 1.0, ...)`이나 `Opacity(opacity: 1.0, ...)`을 **남겨 두면 안 된다** — 앱 수명 내내 매 프레임 합성 비용이 붙는다. 상태가 `gone`이면 래퍼 없이 `return child`.

### 4-4. 검토했지만 채택하지 않은 모션

| 안 | 왜 안 쓰는가 |
|---|---|
| **획 그리기 (`PathMetric` stroke-draw)** | §2-1. OS가 완성된 마크를 이미 보여 준 뒤라 먼저 지워야 한다. 그리고 획 3개를 다 그리려면 최소 450ms가 필요한데, **중간에 못 끊는다** — 반쯤 그려진 로고를 잘라 내면 렌더 실패로 보인다. §5의 조정 규칙과 정면으로 충돌 |
| **마크 → 목적지 UI로 공유 요소 전환** | 착지가 셋인데(`/home`·`/login`·`/login/center-confirm`, `app_router.dart:36-42`) 워드마크가 있는 건 `/login` 하나뿐이다(`phone_screen.dart:54-62`). 홈 헤더는 센터명이라 마크가 갈 자리가 없다. **셋 중 하나만 되는 전환은 나머지 둘에서 부자연스럽고, 착지가 늘 때마다 깨진다** |
| **크림 배경의 그라디언트·글로우** | 마크는 크림 **단색** 위에 놓이도록 만들어졌다(`design/brand/README.md:13`, `pubspec.yaml:117-118`의 `adaptive_icon_background: "#F6F4EF"`). 그라디언트를 깔면 §3-3의 픽셀 매칭이 즉시 깨진다 — 네이티브 쪽은 단색만 지원한다 |
| **워드마크(`RISE CONDITIONING`) 페이드인** | §8-7 |
| **파티클·빛 스윕** | 이 브랜드가 아니다. 마크는 손그림 획 3개 + 점 하나로, 절제가 성격이다 |

## 5. 하드 제약 — 스플래시가 시작을 늦추면 안 된다

> 실제 시작 작업보다 오래 사는 스플래시는 앱을 **고급스럽게** 만드는 게 아니라 **느리게** 만든다. 그리고 그 대가는 앱을 자주 켜는 사람 — 즉 가장 좋은 사용자 — 이 치른다.

### 5-1. 이 설계가 지키는 계약

> **게이트는 "죽은 시간"을 단 1ms도 만들지 않는다.**
> — 죽은 시간 = 아무 일도 일어나지 않고 목적지도 아직 안 보이는 시간.

주의해서 구분할 것: **크로스페이드 280ms는 죽은 시간이 아니다.** 그동안 목적지가 화면에 있고 점점 또렷해진다. 아래 규칙이 상한을 두는 건 오직 **죽은 시간**이다.

### 5-2. 조정 규칙

게이트는 `appReady`(= `restoreLanding()`이 **반환됐다**) 하나만 본다.

**커밋 체크 — `t = 0` 다음 프레임(≈16ms)에 한 번**

- `appReady == true` → **등장을 아예 시작하지 않는다.** 즉시 퇴장.
- 이게 §8-1(인위적 최소 노출)의 정반대다. 최소가 아니라 **적응적 최대**를 건다.

**퇴장 시작 시점**

| `appReady` 발생 시각 | 퇴장 시작 | 추가된 **죽은 시간** |
|---|---|---|
| `t ≤ 16ms` (웜스타트 + 미로그인) | `16ms` | **+0ms** — 등장 자체가 없다 |
| `16 < t < 350ms` | `min(350, t + 120)` | **≤ +120ms** — 점 도착을 압축해 마무리 |
| `t ≥ 350ms` (콜드스타트 + 네트워크) | `t`의 다음 프레임 | **+0ms** — 등장은 이미 공짜로 끝났다 |
| 끝내 안 옴 | §5-5 참조 | **−17초 이상** (개선) |

**`t ≤ 16ms`가 왜 실재하는 경로인가**: `session_restore.dart:73`의 `if (user == null) return null;`은 `await`을 **하나도 지나지 않는다**. 미로그인 사용자는 복원 결정이 첫 마이크로태스크에 끝난다. 지금 이 사용자에게 스플래시를 630ms 보여 주면 **없던 대기 630ms를 새로 만드는 것**이다. 커밋 체크가 이걸 막는다.

**"점 도착을 압축한다"의 정확한 뜻**: 남은 시간을 `min(remaining, 120ms)`로 줄여 재생을 **가속**한다. **거꾸로 돌리거나 중간에 자르지 않는다.** §3-2의 2번(어느 프레임에서 잘라도 안 깨진다) 덕분에 이 압축이 안전하다.

### 5-3. 네 가지 시작 시나리오

| 시나리오 | 복원 비용 | `appReady` | Flutter 노출 | 오늘 대비 |
|---|---|---|---|---|
| **웜 · 미로그인** | 0회 왕복 (`session_restore.dart:73`) | ~0ms | **~296ms** (16 + 280 퇴장) | 죽은 시간 +0. 하드컷이 크로스페이드로 바뀐 것뿐 |
| **웜 · 로그인 · 토큰 유효** | 1회 왕복 (~150ms) | ~120ms | **~520ms** (240 + 280) | 죽은 시간 **+120ms** (최대치) |
| **콜드 · 로그인 · 토큰 만료** | 2회 왕복 (~500ms) | ~450ms | **~730ms** (450 + 280) | 죽은 시간 **+0** — 그 450ms는 오늘 **빈 화면**이던 시간이다 |
| **콜드 · 네트워크 불량** | 타임아웃 (`api_config.dart:11-12`) | 안 옴 | §5-5의 **2200ms**에서 종료 | **20초+ → 2.5초** |

콜드스타트 총합(네이티브 포함) 추정: ①②가 700~1200ms(엔진 로드 + `main.dart:10` Firebase 초기화) + Flutter 730ms ≈ **1.4~1.9초**. 프리미엄 앱의 정상 범위다.

**세 번째 줄이 이 설계의 정당성 전부다.** 콜드스타트에서 등장 350ms는 **이미 존재하던 빈 화면 시간을 채운 것**이지 새로 만든 시간이 아니다.

### 5-4. 복원이 실패하면

**게이트 쪽은 한 가지만 지키면 된다 — `finally`.**

```dart
// app.dart:40-41 의 콜백을 감쌀 때
createRouter(restoreLanding: () async {
  try {
    return await restoreAuthLanding(ref);
  } finally {
    ref.read(appReadyProvider.notifier).markReady();   // ← 반드시 finally
  }
});
```

`catch`가 아니라 `finally`인 이유: `restoreAuthLanding`은 네트워크 실패를 이미 `Result`로 삼키지만(`api_result_guard.dart:30`), **`store.read()`/`store.clear()`(`session_restore.dart:85,92`)의 shared_preferences 예외는 그대로 던져진다.** `catch`로 잡으면 그 경우 게이트가 영원히 안 열린다.

**착지 판정 자체는 손댈 게 없다.** 이미 옳게 설계돼 있다:

| 상황 | 판정 | 착지 | 근거 |
|---|---|---|---|
| 복원 성공 | `connected` | `/home` | `session_restore.dart:34,47` |
| 서버가 확답한 미연결 | `notLinked` | 대기 기록 있으면 `/login/center-confirm`, 없으면 온보딩 | `:35,48` |
| **네트워크·타임아웃** | `unknown` | `/login/center-confirm` (재확인 화면) | `:36,52` · `api_result_guard.dart:30` |

`unknown`이 재확인 화면으로 가는 건 **이 설계가 §5-5에서 그대로 재사용하는 결론**이다.

### 5-5. 게이트 혼자서는 못 고치는 것 — **선행 조건**

**게이트에 자체 타임아웃을 두면 안 된다.** 게이트가 먼저 나가 봐야 그 아래는 여전히 `SizedBox.shrink()`(`builder.dart:101-105`) — **빈 화면**이다. 천장은 "의도된 정지 화면"을 "빈 화면"으로 바꾸는 것 말고 하는 일이 없다.

**상한은 라우터가 가져야 한다.**

```dart
// app_router.dart:39 — 현재
final landing = await restoreLanding!();

// 필요한 것: 전송 타임아웃과 별개인 "시작 예산"
final landing = await restoreLanding!()
    .timeout(const Duration(milliseconds: 2200),
             onTimeout: () => '/login/center-confirm');
```

- **2200ms인 이유**: 콜드 + 2회 왕복(~500ms)의 4배 이상 여유. 정상 경로에서는 절대 안 걸린다.
- **`/login/center-confirm`인 이유**: 새 정책이 아니라 **이미 있는 답이다** — `restoreLandingRoute`가 `RestoreOutcome.unknown`에 대해 고르는 바로 그 라우트(`session_restore.dart:52`). 앱은 "아직 모름"의 정답을 이미 알고 있었고, **제때 도달하지 못했을 뿐이다.**
- **`api_config.dart:11-12`를 낮추면 안 되는 이유**: 그건 사진 업로드·인바디 OCR 등 **모든 요청의 전송 타임아웃**이다. 시작 예산과 전송 예산은 다른 축이다.

**남는 문제(이 문서 범위 밖, 후속으로 이관)**: `.timeout`은 진행 중인 dio 요청을 취소하지 않는다. 늦게 도착한 `Ok`가 `sessionProvider.set(value)`(`session_restore.dart:83`)를 호출하면 사용자는 유효한 세션을 들고 재확인 화면에 남는다. `app.dart:55-58`의 리스너는 `next != null`이면 무시하므로 **아무 일도 안 일어난다** — 위험하진 않지만 이상하다. §9-2.

**디버그 안전망**: 릴리스에 천장을 넣는 대신, 디버그 빌드에서 게이트가 5초 넘게 살아 있으면 `assert`로 알린다. 조용히 잘못되지 않게.

### 6-1. 게이트는 **라우터 위**여야 한다

```dart

  return MediaQuery(
    data: mq.copyWith(textScaler: mq.textScaler.clamp(...)),  // 기존 그대로

  );

```

**여기여야만 하는 이유**: 덮어야 할 빈 화면이 **라우터가 만드는 것**이다(`builder.dart:101-105`). 스플래시를 `/splash` 라우트로 만들면 그 구멍 **안쪽**에 놓이게 되어 아무것도 못 덮는다. `MaterialApp.builder`는 `Router`의 **바깥**이라 첫 프레임부터 존재한다.

부수 효과로 **`app_router.dart`도 `session_restore.dart`도 고칠 필요가 없다** — `restoreLanding` 콜백을 감싸는 것(§5-4) 하나뿐이다.

**상태 기계** (4개, `AnimationController` 1개 + `AnimationStatusListener`):

```
matched ──(커밋 체크: appReady?)──┬─→ leaving        (t≈16ms)
                                  └─→ arriving ─→ holding ─→ leaving ─→ gone
```

`appReady`는 `keepAlive` `Notifier<bool>` 하나면 충분하다(`session_provider.dart:11-14`과 같은 패턴). 게이트는 `ref.listen`으로 한 번만 받는다.

**목적지에 한 프레임을 준다**: `appReady`가 뜬 뒤 `WidgetsBinding.instance.addPostFrameCallback`으로 한 프레임 넘기고 퇴장을 시작한다. 그래야 `HomeScreen`이 최소 한 번 빌드된 상태에서 페이드인이 시작된다(안 그러면 첫 60ms가 빈 프레임이다). 퇴장 280ms = 약 17프레임이라 레이아웃 시간은 충분하다.

## 7. 접근성 · 모션 감소

### 7-1. `MediaQuery.disableAnimationsOf(context)`

Flutter 3.44에 존재한다 — `flutter/lib/src/widgets/media_query.dart:1950` (`static bool disableAnimationsOf`), 데이터 필드는 `:628`. iOS **동작 줄이기**, 안드로이드 **애니메이션 제거 / 애니메이션 기간 배율 0**일 때 `true`.

현재 이 앱은 **이 값을 어디서도 읽지 않는다** — `lib/` 전체에서 `disableAnimations` 검색 결과 0건(`SystemUiOverlayStyle`·`SystemChrome`도 0건).

**대체 동작 = "이동은 전부 제거, 크로스페이드는 유지".** Apple의 Reduce Motion이 슬라이드를 크로스디졸브로 바꾸는 것과 같은 원칙이다 — 모션 감소는 *전환을 없애라*가 아니라 *움직이지 마라*다. 하드컷으로 되돌리면 §1-1의 문제로 되돌아간다.

| 대상 | 기본 | `disableAnimations == true` |
|---|---|---|
| 0→90ms 정지 | 유지 | **0ms** (정합 확인이 이미 정적이므로 불필요) |
| 점 도착 | 반지름 0.86→1.00 + 불투명도 | **불투명도만**, 0→1, 200ms, `easeOut` |
| 호흡 (1.000→1.014) | 있음 | **없음** (`scale` 고정 1.000) |
| 퇴장 · 마크 | 불투명도 + `scale` 1.014→1.052 | **불투명도만**, 180ms |
| 퇴장 · 크림 바탕 | 불투명도, 280ms | **동일** (이동이 아니다) |
| 퇴장 · 앱 콘텐츠 | 불투명도 + `scale` 0.985→1.000 | **불투명도만**, 200ms |
| **총 길이** | ≤ 630ms | **≤ 400ms** |

§5-2의 커밋 체크·조정 규칙·§5-5의 라우터 예산은 **그대로 적용된다.** 모션 감소는 짧게만 만들 뿐 로직을 바꾸지 않는다.

### 7-2. 명암비 실측 — **베이지 점은 1.69:1이다**

WCAG 2.x 상대 휘도로 직접 계산했다.

| 조합 | 비 | 판정 |
|---|---|---|
| 네이비 획 `#3B4C60` / 크림 `#F6F4EF` | **8.00 : 1** | 비텍스트 3:1 기준 대폭 통과 |
| **베이지 점 `#CEBBAA` / 크림 `#F6F4EF`** | **1.69 : 1** | **3:1 미달** |
| 네이비 / 앱 흰 배경 `#FFFFFF` | 8.79 : 1 | 통과 |
| **크림 `#F6F4EF` / 흰 `#FFFFFF`** | **1.10 : 1** | 거의 동일 → §4-2의 바탕 전환 근거 |
| 크림 / `AppColors.page` `#F7F7F8` | 1.03 : 1 | 사실상 같은 색 |
| 앱 레드 `#E11D48` / 크림 | 4.27 : 1 | (참고 — §8-6에서 사용) |

**여기서 나오는 설계 결론 두 가지:**

1. **점은 의미를 혼자 지면 안 된다.** 실제로 그렇지 않다 — 점 없는 R은 이미 완결된 마크다(§3-2의 2번). 브랜드 보드 원색이라 바꿀 수도 없다(`design/brand/README.md:15-16`).
2. **그래서 "호흡"을 빼면 안 된다.** 만약 점의 도착이 화면의 **유일한** 모션이면, 저시력 사용자에게는 **모션이 하나도 없는 것과 같다**(1.69:1은 거의 안 보인다). 8.00:1인 네이비 획 전체가 움직이는 호흡이 있어야 **어떤 시력에서도** 지각 가능한 신호가 남는다. §4-1의 호흡은 미학이 아니라 **접근성 요구사항**이다.

### 7-3. 스크린리더 · 상태바 · 글꼴 배율

| 항목 | 규칙 |
|---|---|
| **스크린리더** | 게이트가 불투명한 동안 `child`를 `ExcludeSemantics`로 감싼다. 안 그러면 TalkBack/VoiceOver 포커스가 **아직 안 보이는** 목적지 화면에 내려앉는다. 퇴장 시작과 함께 해제 |
| **게이트 자체의 레이블** | `Semantics(label: '라이즈 컨디셔닝', ...)` 하나. 진행 상황을 읽어 주지 **않는다** (`liveRegion` 금지) — 알림이 아니라 앱 식별이다 |
| **터치** | 게이트가 살아 있는 동안 `IgnorePointer`로 아래를 막는다. 안 보이는 버튼을 누르면 안 된다 |
| **상태바** | 크림 `#F6F4EF`는 **밝은 배경**이다 → `SystemUiOverlayStyle`의 어두운 아이콘이 필요하다. 지금 앱은 이걸 **한 번도 설정하지 않는다**(검색 결과 0건). 설정을 안 하면 다크모드 안드로이드에서 밝은 아이콘이 크림 위에 올라가 **시계와 배터리가 사라진다**. 게이트 수명 동안 적용하고 퇴장 시 원복 |
| **글꼴 배율** | 스플래시에 **텍스트가 없다.** 따라서 `app.dart:28-29`의 `_maxTextScale = 1.35`가 영향을 주지 않는다 — 이건 우연이 아니라 §8-7의 이유다 |
| **화면 회전** | 게이트는 `Center` 하나로 배치한다. 회전 중 실행되면 마크가 중앙을 유지해야 한다 |

## 9. 남는 것 · 후속

1. **§3-3의 교정이 실기기 없이는 안 끝난다.** 안드로이드 12 시스템 스플래시의 아이콘 크기는 OS가 정하고 기기·런처마다 미세하게 다르다. 5단계 절차의 프레임 단위 녹화 검증을 **모션 튜닝보다 먼저** 통과시킬 것.
2. **`.timeout` 이후 늦게 도착하는 복원 결과**(§5-5). 위험하진 않지만 유효 세션을 들고 재확인 화면에 남는다. 별도 작업으로 분리 — 취소 가능한 복원, 또는 늦은 `Ok`에 대한 재라우팅.
3. **`main.dart:10`의 `await Firebase.initializeApp`이 `runApp` 앞에 있다.** 첫 프레임을 그만큼 늦춘다. 이 게이트가 생기고 나면 초기화를 임계 경로에서 빼는 게 **순수 이득**이 된다(지금은 빼면 빈 화면이 더 빨리 나올 뿐이라 이득이 없다). 게이트 이후에 검토.
4. **마크가 세 곳에 중복 정의된다**(§6-2). `design/brand/README.md`의 재생성 표에 Dart 페인터를 추가할 것.
5. **`values-night/styles.xml`의 다크모드 처리**(§1-3)는 스플래시와 무관하게도 버그다. `flutter_native_splash` 생성이 이걸 덮으면 함께 해결되지만, **생성 결과를 `git diff`로 확인**해야 한다.
6. **웹**: `flutter_native_splash`는 웹도 지원하지만 이 앱은 모바일 전용이다(`pubspec.yaml`의 camera·mobile_scanner·permission_handler). 웹 설정은 넣지 않는다.
