# 세션 캐시 — 콜드 스타트에서 "내가 누구인지"를 네트워크 없이 아는 설계

- 작성: 2026-08-29 · 렌즈: **인증/세션 영속 · 개인정보(개인정보보호법) · 실패 모드**
- **코드는 한 줄도 고치지 않았다.** 이 문서는 설계안이고, 구현은 별건이다.
- 현행 동작에 대한 모든 주장은 읽은 코드에 `파일:행`으로 근거를 단다(색인 §10).
- 확인하지 못한 것은 **⚠️ 미검증**으로 표시했다. 추측은 결론에 넣지 않는다.
- 백엔드(`ptdesk/backend`)와 API 계약(`docs/API계약_v1.md`)도 함께 읽었다 — 앱만 보면
  §3의 핵심 실패(탈퇴 회원)를 정반대로 설계하게 된다.

---

## 0. 네 줄 요약

1. **저장해도 된다.** 다만 `flutter_secure_storage`가 아니라 **이미 있는
   `shared_preferences`**로. 이 세션 5개 필드에 자격증명이 하나도 없고, 실제 열쇠인
   Firebase 리프레시 토큰은 안드로이드에서 **이미 평문으로** 같은 디렉토리에 있다.
   가장 값싼 물건에만 금고를 다는 건 보안이 아니라 연출이다.

2. **어려운 건 저장이 아니라 정정이다.** 그런데 이 앱은 다행히 **신원만** 캐시하면
   된다 — 회원권·예약·코치·정책은 지금도 화면 진입마다 새로 받는다
   (`home_view_model.dart:35-46`, `staff_directory.dart:70-95`, `center_policy_provider.dart:22-44`).
   "환불됐는데 예전 잔여가 보인다"는 이 설계에서 **애초에 생길 수 없다.**

3. **가장 비싼 실패는 탈퇴한 회원이 동작하는 홈을 보는 것**이고, 지금 서버는 그
   상황에서 **401을 주지 않는다.** UserIndex가 지워져 `member_id`가 빈 200을 준다
   (`backend/internal/api/auth.go:139-152` + `service.go:72-85`). 그래서
   **dio의 401 인터셉터(`dio_client.dart:36-38`)는 이 경우를 못 잡는다.**
   재검증 설계의 중심은 401이 아니라 **`MemberNotLinkedFailure`** 다.

4. **스플래시는 할 일이 없어지지 않는다** — 오히려 이 캐시가 스플래시를
   "네트워크 대기 커튼"에서 "전환 연출"로 강등시킨다. 그리고 캐시된 홈은
   **내용이 아니라 골격**이라(본문은 여전히 스피너, `home_screen.dart:85`),
   "완성된 홈을 보여줬다 뺏는" 장면은 이 설계에서 나오지 않는다.

## 2. 질문 1 — 저장해도 안전한가, 어디에

### 2.1 무엇을 저장하는가 — 실물 실사

```jsonc
{
  "uid":        "AbCd1234...",   // Firebase uid. 앱에서 안 읽음(§1.2). 오직 캐시 키 대조용
  "role":       "member",        // 이 앱은 항상 이 값. 서버가 UserIndex로 재판정한다
  "centerId":   "rise",          // v1 단일 센터. 앱에서 안 읽음
  "memberId":   "m_9f3...",      // Firestore 문서 ID. 서버 스코프의 **입력이 아니다**(§2.4)
  "memberName": "김민지"          // ★ 유일한 실질 개인정보(성명)
}
```

**자격증명이 없다.** 이 다섯 개 중 어떤 것도 API 호출을 인증하지 못한다. 인증은
전적으로 `Authorization: Bearer <Firebase ID token>`(`dio_client.dart:47-50`)이 하고,
그 토큰은 Firebase SDK가 **자기 저장소**에 따로 들고 있다.

### 2.2 `shared_preferences`가 실제로 쓰는 저장소 (통념 교정)

과제 설명의 "안드로이드에서 평문 XML"은 **레거시 API 기준**이다. 이 프로젝트는
이미 `SharedPreferencesAsync`를 쓴다(`join_request_store_impl.dart:18`, 주석 7-9행에
그 선택 이유가 적혀 있다) — 그 API의 실제 백엔드는 다르다.

| 플랫폼 | `SharedPreferencesAsync` 백엔드 | 형태 | 암호화 |
|---|---|---|---|
| Android | **DataStore Preferences**(플러그인 기본값) | 앱 전용 디렉토리의 바이너리 파일 | **없음** |
| iOS | NSUserDefaults | `Library/Preferences/*.plist` | **없음** |

출처: pub.dev `shared_preferences` 문서 — *"The SharedPreferencesAsync and
SharedPreferencesWithCache APIs can use DataStore Preferences or Android
SharedPreferences… In most cases you should use the default option of DataStore
Preferences"* (2026-08-29 확인).

**결론은 안 바뀐다.** XML이든 protobuf든 **평문이고 앱 전용 디렉토리**다. 바뀌는 건
"XML을 텍스트 에디터로 연다"는 그림이 정확하지 않다는 것뿐이다. 이 문서는 이후
"평문 · 앱 전용"으로만 말한다.

### 2.3 `flutter_secure_storage`와의 비교

| | `shared_preferences` (SharedPreferencesAsync) | `flutter_secure_storage` |
|---|---|---|
| Android 저장 | DataStore Preferences, 평문 | EncryptedSharedPreferences(Keystore 파생 키) |
| iOS 저장 | NSUserDefaults plist, 평문 | Keychain |
| 루팅/탈옥 기기 | 그대로 읽힘 | Android는 Keystore가 막음 / iOS는 Keychain 덤프로 뚫림 |
| **앱 삭제 시** | **함께 삭제됨** | **iOS는 남는다** (아래) |
| 기기 백업 포함 | Android Auto Backup ✅ · iOS 백업 ✅ | Keychain 항목은 `ThisDeviceOnly` 지정 시 제외 가능 |
| 이 프로젝트 도입 비용 | **0** — 이미 의존성 | 새 의존성 + 플랫폼 설정 + major 마이그레이션 |
| 실패 모드 | 읽기 실패 = 캐시 미스 | 키 로테이션·기기 이전 시 **복호화 실패** 처리 필요 |

#### `flutter_secure_storage`를 안 고르는 결정적 이유는 "귀찮아서"가 아니다

**(a) iOS Keychain은 앱을 지워도 남는다.** 다수의 이슈로 확인된 동작이다
([#371](https://github.com/juliansteenbakker/flutter_secure_storage/issues/371),
[#660](https://github.com/juliansteenbakker/flutter_secure_storage/issues/660)).
회원이 "앱 지우면 내 정보도 지워지겠지"라고 믿는 바로 그 행동이 **이름을 남긴다.**
회원탈퇴 화면이 "체형사진·인바디·수업 기록이 모두 삭제되고"라고 약속하는 앱
(`account_deletion_screen.dart:120`)에서, 보안 저장소가 프라이버시를 **악화**시키는
경로다. 우회하려면 "설치 후 첫 실행에 secure storage를 비운다" 같은 플래그를
`shared_preferences`에 또 둬야 한다 — 그러면 저장소가 둘이 된다.

**(b) 실제 열쇠는 이미 평문 옆에 있다(안드로이드).** Firebase Auth는 안드로이드에서
ID 토큰과 **리프레시 토큰**을 `com.google.firebase.auth.api.Store` 계열 SharedPreferences에
**평문으로** 보관한다([firebase-android-sdk #2388](https://github.com/firebase/firebase-android-sdk/issues/2388)).
파일을 꺼낼 수 있는 공격자는 이미 그 토큰을 꺼낼 수 있고, 토큰은 **실제로 모든
데이터에 접근한다**. 그 옆에서 `{"memberName":"김민지"}`만 Keystore로 감싸는 건
가장 값싼 물건에 금고를 다는 일이다.

> **정직하게 짚을 비대칭**: iOS에서는 Firebase가 Keychain을 쓴다
> ([firebase-ios-sdk #5595](https://github.com/firebase/firebase-ios-sdk/issues/5595) —
> 다만 접근성 속성이 느슨하다는 지적이 열려 있다). 그래서 (b) 논거는 안드로이드에서
> 강하고 iOS에서 약하다. iOS에서 유효한 논거는 (a)와 (c)다.

**(c) 이건 자격증명이 아니라 "표시용 신원"이다.** 위협 모델이 다르다.
토큰은 **접근**을 보호하고, 이 캐시는 **성명 노출**을 보호한다. 성명 노출에 맞는
통제는 암호화가 아니라 ① 저장 범위 최소화 ② 삭제 시점 보장 ③ 백업 제외다.
그 셋 중 어느 것도 `flutter_secure_storage`가 대신 해주지 않는다.

### 2.4 파일을 손에 넣은 공격자는 무엇을 얻는가 — 정면으로

**얻는 것**: `김민지`라는 실명, 그 사람이 라이즈 컨디셔닝 센터 회원이라는 사실,
그리고 두 개의 불투명 식별자(`uid`, `memberId`).

**얻지 못하는 것 — 이게 중요하다**:

- **API 접근**: `memberId`를 쿼리에 실어도 소용없다. 백엔드는 role=member의
  `member=` 파라미터를 **무시하고 토큰에서 온 `p.MemberID`로 강제**한다
  (`backend/internal/api/service.go:400-408` `memberScopeID` — 미연결이면 `""`가
  필터를 지워 센터 전체가 새는 걸 막으려 403). 쓰기 경로도 `checkMemberScope`가
  `mem.ID != p.MemberID`를 403으로 막는다(`service.go:411-427`).
- **체형사진**: Storage 규칙이 경로의 `{memberId}`를 **Firestore `users/{uid}.member_id`에서
  다시 뽑아 대조**한다(`body_photo_storage_path.dart:15-20, 28-29`). 남의 `memberId`를
  경로에 넣으면 읽기도 쓰기도 403이다.
- **로그인**: 이 파일로는 아무 세션도 못 만든다. 앱은 `FirebaseAuth.currentUser`가
  없으면 즉시 온보딩으로 간다(`session_restore.dart:72-76`).

**즉 유출 피해 = 성명 + 회원이라는 사실의 노출.** 접근 권한 상승은 **0**이다.
성명은 개인정보보호법상 개인정보이지만 **민감정보(§23)는 아니다** — 이 앱의
민감정보는 체형사진이고, 그건 디스크에 **애초에 안 쓴다**
(`body_photo_loader.dart:62-63`: *"업로드가 `no-store`로 올린 민감정보를 앱이 디스크에
남기면 그 의도가 무의미해진다"*). 세션 캐시는 그 선을 넘지 않는다.

### 2.5 그래서 실제로 손봐야 할 것은 암호화가 아니라 **백업**

이건 이 조사에서 나온 **기존 코드의 실제 갭**이다.

`android/app/src/main/AndroidManifest.xml`에 `android:allowBackup` 선언이 **없고**
(기본값 `true`), `dataExtractionRules`/`fullBackupContent` 파일도 **없다**(찾은 결과 0건).
targetSdk는 `flutter.targetSdkVersion`(`android/app/build.gradle.kts:32`, 주석상 36).
즉 **Auto Backup이 켜져 있고 앱의 prefs/DataStore가 Google 계정으로 올라간다.**

그리고 지금 그 백업에 들어가는 것 중에는 **이미 전화번호가 있다** —
`auth.join_request` 키(`join_request_store_impl.dart:16`)에 E.164 번호가 담긴다
(`join_request_store.dart:17, 23-26`). 세션 캐시를 추가하면 **성명**이 하나 더 얹힌다.

> **권고 (세션 캐시와 별개로 지금도 유효)**: `dataExtractionRules`로 이 앱의
> prefs/DataStore를 백업·D2D 전송에서 제외한다. 캐시는 "다시 만들 수 있는 것"이라
> 백업할 이유가 없고, 빠져도 잃는 건 재설치 후 로그인 한 번이다.
> iOS도 NSUserDefaults plist가 기기 백업에 포함되지만, iOS에는 파일 단위 제외 수단이
> 없다 — 대신 §4의 **탈퇴/로그아웃 시 즉시 삭제**가 그 자리를 메운다.
> ⚠️ **미검증**: 실제 백업 산출물에 이 키들이 들어가는지 실기기로 확인하지 않았다.

### 2.6 결정

> **`shared_preferences`(`SharedPreferencesAsync`)에 저장한다. 새 패키지를 추가하지 않는다.**
> 대신 ① `memberName`은 저장 여부를 한 번 더 따지고(§2.7) ② Android 백업에서 제외하고
> ③ §4의 무효화 트리거를 **하나도 빠짐없이** 건다.

**버전 확인 (2026-08-29 pub.dev API 실조회)**

| 패키지 | 최신 stable | 게시일 | 환경 제약 | 비고 |
|---|---|---|---|---|
| `shared_preferences` | **2.5.5** | 2026-03-25 | `sdk ^3.9.0` / `flutter >=3.35.0` | `pubspec.yaml:70`의 `^2.5.5`가 **이미 최신**. 변경 불필요 |
| `flutter_secure_storage` | **11.0.0** | 2026-08-06 | `sdk >=3.8.0` / `flutter >=3.19.0` | 직전 stable 10.3.1(2026-05-27). **major 승격 23일차** |

`flutter_secure_storage`를 굳이 도입한다면 10.x→11.x breaking change를 먼저 조사해야
한다 — **이 문서는 그 조사를 하지 않았다(⚠️ 미검증).** 채택하지 않기로 했으므로
불필요하다고 판단했다.

### 2.7 `memberName`을 저장할 것인가 — 별도 판단

저장하지 않아도 **기능은 온전하다.** 홈 헤더는 이름이 비면 센터명으로 떨어지도록
이미 설계돼 있다(`app_session.dart:19-25`, `home_screen.dart:66`).
반대로 저장하면 얻는 건 "재실행 직후 헤더가 센터명 → 이름으로 한 번 바뀌지 않는다"는
**미세한 연출**이다.

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| A. 저장한다 | 헤더가 처음부터 "김민지 님" | 디스크에 성명. 백업에 성명 |
| B. 저장 안 함 | 디스크에 **개인 식별 정보 0** — 남는 건 불투명 ID뿐 | 헤더가 센터명 → 이름으로 한 번 교체 |

**권고: B로 시작한다.** 근거는 균형이 명확해서다 — 저장으로 얻는 건 300ms짜리
헤더 깜빡임 제거이고, 잃는 건 "이 앱은 성명을 디스크에 안 쓴다"는 **말할 수 있는
문장**이다(개인정보 처리방침에 그대로 적힌다). 그리고 §1.2대로 `uid`·`role`·`centerId`도
앱이 안 읽으므로, 남는 저장 대상은 **`memberId` + `uid`(키) 둘뿐**이 된다.

교체 깜빡임이 실제로 거슬린다고 판단되면 그때 A로 올리면 된다 — 되돌릴 수 있는
방향의 결정이다. **반대 방향(저장했다가 빼기)은 이미 깔린 기기의 파일을 청소해야
해서 훨씬 비싸다.**

## 3. 질문 2 — Staleness (여기가 어렵다)

### 3.1 먼저: 무엇이 정말 stale일 수 있는가

과제가 든 네 가지를 §1.3(캐시 안 하는 것들)과 대조하면 절반이 사라진다.

| 변한 사실 | 캐시 때문에 틀려지나? | 이유 |
|---|---|---|
| 회원권이 환불됨 | **아니오** | 패스는 매번 새로 받는다. 전부 만료·환불이면 홈이 본문을 통째로 빼고 전용 빈 상태를 그린다(`home_screen.dart:49, 72-77`) |
| 담당 코치가 바뀜 | **아니오** | `trainer_id`는 패스에서 오고, 이름은 15분 TTL 캐시 + pull-to-refresh(`staff_directory.dart:41, 60-68`) |
| 센터가 바뀜 | **아니오(현재)** | `centerId`를 앱이 안 읽는다(§1.2). v1은 단일 센터고 회원 이관 API가 계약에 없다. ⚠️ 멀티 센터 전환 시 재검토 |
| **회원이 탈퇴함** | **예 — 이게 전부다** | 신원 자체가 사라진 경우. 캐시가 유일하게 거짓말하는 지점 |
| memberId 재배정 | **⚠️ 미검증, 사실상 없음** | `POST /v1/join/confirm`이 1회 연결하고, 되돌리는 API가 계약에 없다(계약 1284행: *"되돌리는 API도 없다"*) |

> **캐시하는 것이 신원뿐이면, stale해질 수 있는 것도 신원뿐이다.**
> 이 설계의 재검증은 "모든 화면을 검증"이 아니라 **"이 사람이 아직 이 센터의 회원인가"
> 한 가지 질문**이다.

### 3.2 서버가 실제로 뭘 돌려주는가 — 401이 아니다

**이 절이 이 문서에서 가장 실무적으로 중요한 부분이다.**

탈퇴(`DELETE /v1/me`)는 UserIndex(uid→member_id)와 Firebase Identity Platform 계정을
**둘 다 삭제**한다(계약 1298행, 삭제 순서 1349행: *"⑤ UserIndex 삭제 — 호출자의 권한
자체를 없애므로 반드시 마지막"*). 그 뒤 이 기기가 `GET /v1/me`를 부르면:

```
경로 A — 캐시된 ID 토큰이 아직 유효 (최대 1시간)
  dio onRequest: getIdToken() → 캐시 토큰 반환 (네트워크 X)   dio_client.dart:47
  backend resolveFirebase: VerifyIDToken 성공                 auth.go:109
     ※ VerifyIDTokenAndCheckRevoked가 아니다 — 폐기 검사를 하지 않는다
  backend enrich: GetUserIndex 실패 → 기본 센터 + role=member + MemberID=""  auth.go:139-152
  Me(): MemberID 빈 채로 200 OK                               service.go:72-85
  앱: me.memberId == null → Err(MemberNotLinkedFailure)       auth_repository_impl.dart:211-214
  → classifyRestore = notLinked                               session_restore.dart:38

경로 B — 토큰 갱신이 필요한 시점
  getIdToken()이 계정 삭제로 실패 → dio가 조용히 삼키고 헤더 없이 전송  dio_client.dart:51-52
  backend: errMissingToken → 401                              auth.go:107 → Middleware auth.go:90
  → dio 401 인터셉터가 세션 clear                              dio_client.dart:36-38
```

**그래서**:

- **`dio_client.dart:36`의 401 인터셉터는 탈퇴를 신뢰성 있게 잡지 못한다.**
  경로 A에서는 401이 아예 안 온다. 그리고 그건 버그가 아니라 **의도된 설계**다 —
  같은 파일 30-31행이 *"403은 건드리지 않는다: 신원은 멀쩡한데 권한이 없다는 뜻"*
  이라고 명시한다.
- **탈퇴를 잡는 실제 신호는 `MemberNotLinkedFailure`다.** 그리고 지금 이 신호는
  `RestoreOutcome.notLinked`로 분류돼(`session_restore.dart:38`) 온보딩으로 착지시킨다
  (`session_restore.dart:51`). **캐시가 생기면 이 자리에서 캐시도 함께 버려야 한다.**
- 최악의 지연은 **약 1시간**(Firebase ID 토큰 수명) + 재검증 왕복이다.
  ⚠️ **미검증**: firebase_auth Flutter SDK가 계정 삭제 후 `currentUser`를 언제
  비우는지는 실기기로 확인하지 않았다. SDK가 갱신 실패 시 자동 signOut한다면 경로 B가
  더 빨리 온다.

### 3.3 설계 — Stale-While-Revalidate, 단 "정정 등급"을 나눈다

```
콜드 스타트
  │
  ├─[동기] FirebaseAuth.currentUser  ── null ─→ 캐시 폐기 + '/login'          ← 게이트 ①
  │        (session_restore.dart:72)
  │
  ├─[동기] 캐시 읽기 + uid 대조 ────── 미스/불일치 ─→ 현행 그대로(네트워크 대기)  ← 게이트 ②
  │
  ├─[즉시] sessionProvider.set(캐시)  → 라우터가 '/home'으로 착지
  │        홈 헤더 렌더 · 탭 뷰모델이 memberId로 정상 네트워크 시작
  │        SplashGate 걷힘 (ready = true)
  │
  └─[배경] GET /v1/me 재검증 (await 하지 않음)
           ├ Ok(같은 memberId)       → 무음. 이름만 다르면 조용히 갱신           [등급 0]
           ├ Ok(다른 memberId)       → 세션 교체 + 데이터 provider 무효화        [등급 1]
           ├ MemberNotLinkedFailure  → 캐시 폐기 + 세션 clear → '/login'         [등급 2] ★
           ├ AuthFailure(401)        → 동일(401 인터셉터가 이미 clear)           [등급 2]
           └ Network/Unknown         → **아무것도 하지 않는다**                  [등급 0]
```

#### 즉시 렌더되는 것 / 되지 않는 것 — 오해를 먼저 없앤다

**"캐시된 홈"은 캐시된 콘텐츠가 아니다.** 캐시하는 건 `memberId` 하나이고, 그걸 받은
홈 뷰모델은 **평소처럼 네트워크를 시작한다**(`home_view_model.dart:34-46`).
회원이 실제로 보는 것:

| 영역 | 캐시 있을 때(첫 프레임) | 근거 |
|---|---|---|
| 하단 탭바 · 홈 골격 | 즉시 | 라우터가 `/home`에 착지 |
| 홈 헤더 이름 | (§2.7 B안이면) 센터명 → 도착 후 이름 | `home_screen.dart:66` |
| 홈 본문(패스·예약·홈워크) | **스피너** — 네트워크 대기 | `home_screen.dart:85` |
| 잔여 링·다음 예약 | 데이터 도착 후 | `home_screen.dart:102-` |

**얻는 것은 "빈 창 → 골격"이지 "빈 창 → 완성 화면"이 아니다.** 이게 §6의 "뺏김" 위험을
크게 낮춘다.

#### 등급별 사용자 경험

**[등급 0] 조용한 확인 — 아무 일도 일어나지 않는다**

같은 사람이 확인되면 화면은 그대로다. **네트워크 실패도 여기다.** 지하철에서 앱을
켜면 캐시로 홈에 착지하고, 재검증은 실패하고, **세션은 그대로 남는다.**
이건 현행 동작보다 **명백히 낫다** — 지금은 같은 상황에서 `unknown`으로 분류돼
`/login/center-confirm`(재확인 화면)에 떨어진다(`session_restore.dart:55`).
연결된 회원이 오프라인에서 로그인 화면 계열을 보는 건 오분류다.

> 다만 **무기한 신뢰는 안 된다.** §3.4의 상한을 둔다.

**[등급 1] 조용한 교체 — memberId가 달라졌다**

계약상 도달 경로가 없다(§3.1). 그래도 **분기를 둔다**: 이 상황이 실제로 오면
캐시된 ID로 이미 남의 데이터를 요청하고 있다는 뜻이다. 세션을 새 값으로 갈아끼우고
데이터 provider를 무효화한다 — `sessionProvider`가 바뀌면 홈/기록/예약/마이 뷰모델은
`ref.watch(sessionProvider)`로 **자동 재빌드된다**(`home_view_model.dart:35` 등).
추가로 **체형사진 바이트 캐시를 비워야 한다**(§5).

**[등급 2] 정정 — 이 사람은 더 이상 회원이 아니다 ★**

여기서만 화면을 뺏는다. 그리고 **뺏는 방식이 중요하다.**

```
캐시 폐기 → sessionProvider.clear()  ← 체형사진 캐시도 함께 비워진다(session_provider.dart:26-29)
   └ app.dart:73-76의 ref.listen이 발화 → _router.go('/login')
```

이 경로는 **이미 존재한다.** `app.dart:66-72` 주석이 정확히 이 상황을 위해 쓰였다
(*"② dio 인터셉터의 401 — 토큰이 폐기돼 신원이 사라진 경우. ②가 이 리스너의 존재
이유다"*). 세션 캐시는 그 리스너에 **새 발화 사유 하나를 추가할 뿐**이다.

**단, 지금 이 경로는 말없이 화면만 바꾼다.** 캐시가 생기면 그게 문제가 된다 —
회원 입장에서는 "홈이 뜨다가 갑자기 로그인 화면"이고, 이유를 아무도 말해주지 않는다.
**정정에는 반드시 문장이 붙어야 한다**: 로그인 화면 도착 시 스낵바로
*"이 계정은 더 이상 센터에 연결되어 있지 않아요"* 급의 한 줄.
(⚠️ **문구는 미확정** — 탈퇴/미연결/권한 상실을 앱이 구분할 수 없으므로 원인을
지목하지 않는 표현이어야 한다. 이 저장소의 규약이기도 하다:
`account_deletion_screen.dart:204-205` *"원인을 지목하지 않는다 — 모르는 것을 아는
것처럼 말하지 않는다"*.)

### 3.4 "탈퇴한 회원이 동작하는 홈을 본다" — 구체적으로 어떤 실패인가

**나이브하게 구현하면 이렇게 된다:**

```
1. 회원이 다른 기기(또는 데스크 요청)로 탈퇴 → UserIndex·Firebase 계정 삭제
2. 이 기기: 앱 실행. FirebaseAuth.currentUser는 여전히 살아 있다(로컬 영속)
3. 캐시 히트 → sessionProvider.set(memberId: m_9f3) → '/home' 착지
4. 홈 뷰모델이 GET /v1/passes?member=m_9f3 발사
5. ★ 서버는 memberScopeID로 p.MemberID("")를 보고 403을 준다 (service.go:404-406)
6. guardApi가 403 → RejectedFailure (api_result_guard.dart:27-28)
7. 401이 아니므로 dio 인터셉터는 세션을 안 비운다 (dio_client.dart:36, 의도된 설계)
8. 홈은 RiseErrorView("요청을 처리할 수 없어요") + [다시 시도]  (home_screen.dart:94-101)
```

**결과**: 탈퇴한 회원이 **자기 이름이 박힌 홈 헤더**와 **누르면 계속 실패하는
재시도 버튼**을 마주한다. 로그아웃 버튼은 마이 탭 안에 있는데 마이 탭도 같은 403으로
죽는다(`my_view_model.dart:35`). **탈출구가 없다.**
이건 `auth_expiry_test.dart` 헤더가 기록한 P29 이전 상태의 재현이다 —
*"회원은 모든 화면에서 '요청을 처리할 수 없어요'만 보고 로그인으로 돌아갈 길도
안내받지 못했다."* **세션 캐시는 그 결함을 되살릴 수 있는 변경이다.**

**그래서 재검증은 선택이 아니라 캐시의 일부다.** 5번의 403을 기다리는 게 아니라,
3번과 **동시에** 출발한 `GET /v1/me`가 등급 2로 끊어낸다.

**추가로 두 개의 안전장치를 둔다:**

1. **캐시 TTL / 절대 상한.** 재검증이 계속 실패해도(네트워크 없음) 캐시를 무기한
   신뢰하면 안 된다. 마지막 **성공적 재검증** 시각을 함께 저장하고, 그로부터 일정
   기간이 지나면 캐시를 "쓰되 홈 착지에는 못 쓰는" 상태로 강등한다.
   **후보: 7일.** 근거 — Firebase 리프레시 토큰이 살아 있는 한 이 기기는 언제든
   재검증할 수 있고, 7일 내내 한 번도 성공 못 한 기기라면 신원 판정을 캐시에 맡길
   근거가 이미 없다. ⚠️ **미결정**: 이 값은 제품 판단이고 실측 근거가 없다.
   (비교: 스태프 캐시는 15분 — `staff_directory.dart:41`. 신원은 스태프 목록보다
   훨씬 덜 변하므로 훨씬 길어도 된다.)
2. **재검증은 콜드 스타트에만이 아니라 포그라운드 복귀에도.** 앱을 3일 만에
   백그라운드에서 꺼내는 경로는 콜드 스타트를 안 탄다. ⚠️ 현재 앱에는
   `AppLifecycleListener` 계열이 없다(`grep` 결과 0건) — **새로 만들어야 하는 부분**이고,
   이 문서의 범위 밖이지만 **없으면 구멍이 남는다**는 사실은 기록해 둔다.

## 4. 질문 3 — 무효화 트리거 (전수)

### 4.1 지금 세션을 비우는 곳 — 정확히 세 곳

`Session.clear()`는 이미 **단일 지점**으로 설계돼 있다(`session_provider.dart:20-29`
주석: *"세 경로가 전부 이 메서드를 지난다"*).

| # | 경로 | 위치 | 현행 동작 |
|---|---|---|---|
| ① | 로그아웃 | `my_screen.dart:367-375` | `restartWithNewPhone()`(Firebase signOut + 인증 상태 초기화, `auth_view_model.dart:381-386`) → `clear()`(:373) → `context.go('/login')`(:374) |
| ② | 회원탈퇴 | `account_deletion_screen.dart:138-145` | `FirebaseAuth.signOut()`(:140) → `clear()`(:144). 호출부(:99-101)가 `/login`으로 |
| ③ | 401 만료 | `dio_client.dart:35-40` | `statusCode == 401`이면 `clear()`(:37). `app.dart:73-76` 리스너가 `/login` |

> **설계 결론: 캐시 삭제를 세 곳에 각각 붙이지 않는다.**
> `Session.clear()` **안에** 넣는다 — 체형사진 캐시가 정확히 그렇게 붙어 있고
> (`session_provider.dart:27`), 그 이유가 주석에 명문화돼 있다.
> 세 호출부에 흩는 순간 네 번째 경로가 생겼을 때 조용히 빠진다.

### 4.2 캐시가 생기면 추가로 필요한 트리거

| # | 트리거 | 어디에 | 왜 필요한가 |
|---|---|---|---|
| ④ | **재검증이 `MemberNotLinkedFailure`** | `session_restore.dart:112 부근`(현행 Err 분기) | §3.2 — **401이 안 오는 유일한 경로.** 이게 없으면 §3.4의 데드엔드가 그대로 발생 |
| ⑤ | **`uid` 불일치** | 캐시 읽기 시점 | §5 — 다른 사람이 로그인한 기기. **읽기 자체가 미스여야 한다** |
| ⑥ | **`FirebaseAuth.currentUser == null`** | `session_restore.dart:76`의 조기 반환 직전 | Firebase만 로그아웃되고 캐시가 남으면 "세션은 있는데 토큰이 없는" 좀비 상태 |
| ⑦ | **재검증이 다른 `memberId`** | 등급 1 처리 | 캐시를 새 값으로 **덮어쓴다**(비우는 게 아니라) |
| ⑧ | **TTL 만료** | 캐시 읽기 시점 | §3.4 안전장치 1 |

### 4.3 하나씩 빠뜨리면 무엇이 깨지나

| 빠진 것 | 결과 |
|---|---|
| **① 로그아웃** | **최악.** 로그아웃하고 앱을 껐다 켜면 **다시 로그인된다.** 센터 태블릿에서 A가 로그아웃 → B가 앱 재실행 → **A의 홈**. `my_screen.dart:357-366`이 인증 상태를 지우는 이유(*"다음 사람이 남의 번호가 채워진 걸 보고… 인증 문자가 그 사람 폰으로 간다"*)와 정확히 같은 계열의 사고이고, **더 나쁘다** — 번호가 채워지는 게 아니라 **세션이 통째로 살아난다** |
| **② 탈퇴** | 앱이 "모두 삭제됐어요"라고 말한 뒤(`account_deletion_screen.dart:120`) 재실행하면 **탈퇴한 신원이 디스크에서 되살아난다.** 개인정보보호법 §21① "지체 없이 파기" 약속을 앱이 어긴다. 게다가 그 신원으로는 아무 API도 안 되므로 §3.4의 데드엔드 |
| **③ 401** | 토큰 폐기 후에도 캐시가 홈으로 착지시킨다. 매 요청이 401 → `clear()`로 세션은 비지만 **캐시는 남아** 다음 콜드 스타트마다 같은 일이 반복. "재실행하면 잠깐 홈이 뜨고 로그인으로 튕기는" 무한 루프 |
| **④ notLinked** | §3.4 데드엔드 그대로. **잡을 방법이 이것뿐이라 대체 경로가 없다** |
| **⑤ uid 불일치** | §5 — B가 A의 신원으로 앱을 쓴다. 서버 스코프가 막아 데이터는 안 새지만 **B의 화면에 A의 이름이 뜨고 모든 탭이 403으로 죽는다** |
| **⑥ currentUser null** | `restoreAuthLanding`이 캐시로 `/home`에 착지시켰는데 Bearer 헤더가 안 붙는다(`dio_client.dart:47-50`) → 전 화면 401 → 즉시 튕김. 스플래시 → 홈 → 로그인의 3단 점멸 |
| **⑦ memberId 변경** | 새 신원으로 옛 `memberId`를 계속 씀 → 403 데드엔드 |
| **⑧ TTL** | 신원 판정을 무기한 오프라인 캐시에 맡긴다. 오래 안 쓴 기기가 탈퇴 후에도 홈에 착지 |

## 5. 질문 4 — 다중 사용자 기기 (센터 태블릿 · 가족 공용폰)

이 앱은 이 시나리오를 **이미 진지하게 다루고 있다.** 두 곳에 명문화돼 있다:

- `my_screen.dart:357-366` — 로그아웃이 인증 상태까지 지우는 이유:
  *"다음 사람이 로그인 화면에서 남의 번호가 채워진 걸 보고, 그대로 누르면 인증
  문자가 그 사람 폰으로 간다… (한 기기를 두 회원이 쓰는 센터 태블릿·가족 공용폰)"*
- `body_photo_loader.dart:39-42` — 사진 캐시를 세션 종료 시 비우는 이유:
  *"다음 회원 화면에 이전 회원의 P8 민감정보가 그려질 수 있다."*

세션 캐시는 **이 계열의 세 번째 항목**이다.

### 5.1 B가 A의 신원을 절대 못 보게 하려면 무엇이 참이어야 하나

세 가지가 **전부** 참이어야 한다. 하나라도 빠지면 구멍이다.

1. **캐시는 `uid`로 키잉되고, 읽을 때 `FirebaseAuth.currentUser.uid`와 대조한다.**
   불일치는 미스 + 즉시 삭제(트리거 ⑤).
2. **로그아웃/탈퇴가 캐시를 지운다**(트리거 ①②) — 대조에만 의존하지 않는다.
3. **`Session.clear()`가 체형사진 바이트 캐시를 함께 비운다** — 이미 그렇다
   (`session_provider.dart:27`). 캐시 도입이 이 순서를 흐트러뜨리면 안 된다.

### 5.2 `uid` 키잉은 충분한가 — 그렇다. 그리고 **올바르다.**

**충분한 이유**: Firebase uid는 계정의 영구 식별자다. B가 자기 번호로 로그인하면
`currentUser.uid`가 다르므로 A의 레코드는 **읽히기 전에** 미스가 된다.
그리고 이건 이 저장소가 이미 쓰는 패턴이다 — `JoinRequestRecord.matches()`가
정확히 같은 판단을 **전화번호**로 한다(`join_request_store.dart:21`,
`session_restore.dart:109-115`: *"대기는 기기가 아니라 **번호**의 상태라, 다른 번호로
로그인한 사용자에게 남의 대기 카드가 뜨면 안 된다"*).

**`uid`가 전화번호보다 올바른 키인 이유**:
`memberId`로 키잉하면 안 된다 — 캐시를 읽기 **전에는** 이 기기의 `memberId`를 모른다
(그걸 알려고 캐시를 읽는 것이다). 순환이다.
전화번호로 키잉해도 안 된다 — 번호는 이동·재사용되고
(`join_request_store.dart:19-21`이 정규화까지 하는 이유), `/v1/me` 응답에도 없다
(`service.go:56-65` `MeResponse`에 phone 필드가 없다).
**`uid`는 콜드 스타트 시점에 네트워크 없이 동기로 알 수 있는 유일한 신원**이다
(`session_restore.dart:72`). 그래서 정확히 맞다.

### 5.3 단, `uid` 대조는 **2차 방어선이지 1차가 아니다**

이 구분이 중요하다.

**1차는 삭제다**(트리거 ①②). 대조는 "지우는 걸 깜빡했을 때"를 위한 그물이다.
대조에만 의존하면 A의 레코드가 **B가 로그인할 때까지 디스크에 남는다** — 그 사이
기기가 분실되거나 백업되면(§2.5) A의 정보가 A의 통제 밖에 있다.
개인정보보호법 §21① "지체 없이 파기"의 문자 그대로의 문제다.

### 5.4 Storage 규칙과 서버 스코프는 3차 방어선이다 — **여기에 기대면 안 된다**

§2.4에서 확인했듯 스코프 우회는 서버가 막는다. 하지만:

- **막는 건 데이터 유출이지 오작동이 아니다.** B의 화면에 "김민지 님"이 뜨고 모든 탭이
  403으로 죽는 건 서버가 못 막는다.
- **실패가 조용하다.** 403은 `RejectedFailure`가 되고(`api_result_guard.dart:27-28`),
  세션을 끊지 않으므로(`dio_client.dart:30-31`, 의도) B는 탈출구 없이 갇힌다 —
  §3.4와 같은 데드엔드다.
- **dev 모드는 그 방어선이 없다.** `DevSession.uid`가 고정값이라
  (`dev_session.dart:18`) 디버그 빌드는 항상 같은 신원으로 붙는다.
  ⚠️ 캐시가 dev 모드에서 어떻게 동작해야 하는지는 **미결정** — 최소한 dev 세션과
  운영 세션의 캐시 키가 섞이지 않아야 한다.

## 6. 질문 5 — 스플래시와의 상호작용

### 6.1 스플래시는 덮을 게 없어지나 — **아니다**

`SplashGate`가 존재하는 이유는 "예쁘라고"가 아니라 **go_router의 async redirect가
`await`하는 동안 `SizedBox.shrink()`만 그려지는 빈 창을 덮으려고**다
(`splash_gate.dart:8-22`, `app.dart:92-95`).

캐시가 있어도 그 구간은 **사라지지 않고 짧아진다**:

| 구간 | 캐시 없음 | 캐시 있음 |
|---|---|---|
| Firebase 초기화 | 그대로 (`main.dart:10`) | 그대로 |
| `currentUser` 조회 | 동기, ~0ms | 동기, ~0ms |
| **캐시 디스크 읽기** | — | **비동기 1회** (`SharedPreferencesAsync`는 인메모리 캐시가 없다 — `join_request_store_impl.dart:7-9`) |
| `joinRequestStore.read()` | 디스크 1회 (`session_restore.dart:78`) | 캐시 히트면 **불필요** (연결된 회원이면 대기 기록을 볼 이유가 없다) |
| **`GET /v1/me`** | **블로킹, 최대 6초** (`session_restore.dart:10, 91-96`) | **블로킹 아님** |
| 첫 유의미 프레임 | 실측 1.3초(`splash_gate.dart:69`) ~ 6초 | **디스크 1회 ≈ 수~수십 ms** |

**결론: 스플래시는 "네트워크 대기 커튼"에서 "전환 연출"로 강등된다.**
그건 `SplashGate`가 **이미 대비한 상태**다 — `fadeOut`에 hold 구간을 **일부러 두지
않았고**, 그 이유가 *"로그아웃 상태처럼 복원이 즉시 끝나는 경로에서는 그 시간이
통째로 순수 대기가 된다"*(`splash_gate.dart:53-58`)이다. 캐시 히트 경로가 정확히
그 "즉시 끝나는 경로"에 합류한다.

**그래서 스플래시는 손대지 않는다.** `_start()`가 `didChangeDependencies`에서
`widget.ready`를 보고 즉시 시작하는 경로가 이미 있다(`splash_gate.dart:120-124`,
주석이 *"첫 프레임에 이미 ready인 경우(웜 스타트에서 복원이 즉시 끝나는 경로)"*라고
그 경로를 명시한다).

> ⚠️ **한 가지 확인 필요**: 320ms 페이드아웃(`splash_gate.dart:59`)이 **유일하게
> 남은 대기**가 되면, 캐시 히트 경로에서 그게 "장식용 지연"으로 느껴질 수 있다.
> 실기기로 봐야 한다 — 이 문서는 판단하지 않는다.

### 6.2 "홈을 보여줬다 뺏는" 위험 — 생각보다 작지만, 0은 아니다

**작은 이유** (§3.3에서 확인): 캐시는 **콘텐츠가 아니라 신원**이다. 등급 2 정정이
일어날 때 회원이 보고 있는 건 **스피너가 도는 홈 골격**이지 완성된 홈이 아니다.
`GET /v1/me` 재검증과 `GET /v1/passes` 데이터 로드가 **동시에 출발**하므로,
정상적인 경우 재검증이 먼저 끝나거나 비슷하게 끝난다.

**0이 아닌 이유** — 세 가지 실제 위험:

1. **`SplashGate`는 다시 안 뜬다.** `_gone = true`가 되면 트리에서 영구히 빠진다
   (`splash_gate.dart:83-86`: *"세션이 만료돼 `ready`가 false로 돌아가도 스플래시가
   다시 뜨면 회원은 앱이 재시작한 줄 안다"*). 옳은 설계지만, 정정 순간을 **덮어줄
   층이 없다**는 뜻이기도 하다. 정정은 날것으로 보인다.
2. **정정에 문장이 없다.** `app.dart:75`의 `_router.go('/login')`은 말없이 화면만
   바꾼다. 캐시 이전에는 이 경로가 "이미 여러 화면이 에러를 보여준 뒤"에 왔지만,
   캐시 이후에는 **아무 설명 없이 홈 → 로그인**이 된다. §3.3의 스낵바가 필수인 이유.
3. **느린 회선에서 순서가 뒤집힌다.** 재검증(6초 예산 없음, 배경 호출)이 데이터
   로드보다 늦게 끝나면, 홈이 **완성된 뒤** 정정이 온다. 이때가 진짜 "뺏김"이다.

**완화 — 다만 "홈을 늦게 보여준다"로 돌아가지는 않는다:**

- 재검증에 **짧은 예산**을 준다. 그 시간 안에 답이 오면 **정정이 홈 완성보다 먼저**
  일어날 확률이 높아진다. 넘기면 등급 0(무음)으로 둔다 — 등급 2 정정은 **확답에만**
  건다. 이건 `classifyRestore`가 이미 세운 원칙이다(`session_restore.dart:32-35`:
  *"미연결로 단정하는 건 서버가 그렇게 답한 경우뿐"*).
- **정정은 되돌릴 수 없으므로 확답에만.** 네트워크 실패로 세션을 끊으면 지하철에서
  앱을 켠 정상 회원을 로그아웃시킨다 — `session_restore.dart:27-30`이 기록한
  바로 그 과거 결함의 재발이다.

> **트레이드오프 요약**: 캐시는 "빈 창 6초"를 "골격 즉시 + 드문 정정"으로 바꾼다.
> 정정이 드물고(탈퇴는 종단 상태다) 그때 문장이 붙는다면, 이 교환은 남는 장사다.
> **문장이 없으면 남는 장사가 아니다.**

## 7. 질문 6 — 잠글 계약 (테스트 목록)

이 저장소의 테스트 서술 규약을 따랐다 — **"무엇을 호출하면 무엇이 반환된다"가 아니라
"이게 깨지면 회원에게 무슨 일이 일어나는가"**로 적는다
(`session_clears_photo_cache_test.dart:43` `reason: '남의 사진이 프로세스에 남는다'`
같은 스타일).

### 7.1 무효화 — 가장 비싼 회귀

| # | 잠그는 계약 | 깨지면 회원에게 |
|---|---|---|
| T1 | 로그아웃하면 캐시가 지워진다 | 로그아웃하고 앱을 껐다 켜면 **다시 로그인돼 있다.** 태블릿에서는 남의 계정으로 |
| T2 | 회원탈퇴하면 캐시가 지워진다 | "모두 삭제됐어요"라고 듣고 나간 사람의 이름이 **디스크에서 되살아난다** |
| T3 | 401 인터셉터가 캐시도 지운다 | 재실행마다 홈이 잠깐 떴다 로그인으로 튕기는 게 무한 반복 |
| T4 | **`Session.clear()` 한 번이 세션·사진캐시·디스크캐시 셋을 모두 비운다** | 네 번째 경로가 생기면 조용히 빠진다. `session_clears_photo_cache_test.dart`의 확장 |
| T5 | 세션을 **set**하는 것만으로는 아무것도 안 지운다 | 복원 직후 방금 받은 사진까지 날아가 같은 바이트를 다시 받는다(기존 테스트의 대칭) |

### 7.2 신원 격리 — 다중 사용자

| # | 잠그는 계약 | 깨지면 회원에게 |
|---|---|---|
| T6 | 캐시된 `uid` ≠ 현재 `currentUser.uid`면 **읽지 않고 지운다** | B의 화면에 **A의 이름**이 뜨고, 모든 탭이 403으로 죽어 탈출구가 없다 |
| T7 | `currentUser == null`이면 캐시가 있어도 `/login`으로 간다 | Bearer 없이 홈에 착지 → 전 화면 401 → 스플래시·홈·로그인 3단 점멸 |
| T8 | 손상·구버전 캐시 문자열은 **조용히 미스**(예외 X) | 저장소 한 줄 때문에 앱이 켜지지 않는다. `JoinRequestRecord.decode`의 규약과 동일(`join_request_store.dart:28-41`) |
| T9 | 저장소 예외(플랫폼 채널 없음 등)가 기동을 막지 않는다 | 위젯 테스트·저장소 없는 환경에서 앱이 죽는다. `join_request_store_impl.dart:11-12`의 규약과 동일 |

### 7.3 Staleness — 재검증

| # | 잠그는 계약 | 깨지면 회원에게 |
|---|---|---|
| T10 | **`MemberNotLinkedFailure` 재검증은 캐시를 폐기하고 `/login`으로 보낸다** | **§3.4 데드엔드** — 탈퇴한 회원이 자기 이름이 박힌 홈과 영원히 실패하는 재시도 버튼을 본다. **401이 안 오므로 이걸로만 잡힌다** |

## 8. 구현 스케치 (인터페이스만 — 코드 아님)

기존 `JoinRequestStore`와 **같은 형태**로 만든다. 새 패턴을 만들지 않는다.

```

    - isFresh(Duration ttl)

  abstract interface class SessionCache { read() / save() / clear() }

  모든 호출 try/catch (join_request_store_impl.dart:11-12와 동일 관용)
```

**붙는 자리 세 곳:**

## 9. 남은 질문 · 미검증 목록

이 설계를 구현으로 옮기기 전에 답해야 할 것들. **답을 지어내지 않았다.**

1. **`Session.set()`은 동기다**(`session_provider.dart:18`). 캐시 저장은 비동기다.
   `set()` 안에서 `unawaited(save())`를 하면 저장 실패가 조용히 사라지고(허용 가능 —
   `join_request_store_impl.dart:34` 규약), 시그니처를 `Future`로 바꾸면 호출부 3곳
   (`session_restore.dart:103`, `auth_view_model.dart:274, 336`)이 전부 바뀐다.
   **미결정.**
2. **포그라운드 복귀 재검증**: `AppLifecycleListener` 계열이 앱에 **없다**(grep 0건).
   콜드 스타트만 재검증하면 오래 백그라운드에 있던 앱은 구멍이다(§3.4).
3. **TTL 7일은 근거 없는 후보값**이다. 제품 판단이 필요하다.
4. **dev 모드 동작 미결정**: `DevSession.uid`가 고정값이라(`dev_session.dart:18`)
   dev/운영 캐시가 섞일 수 있다(§5.4).
5. **⚠️ 미검증 — firebase_auth SDK**: 서버에서 계정이 삭제된 뒤 Flutter SDK가
   `currentUser`를 언제 비우는지 실기기로 확인하지 않았다. §3.2 경로 A/B의 실제
   비중이 여기에 달렸다.
6. **⚠️ 미검증 — Android 백업**: `allowBackup` 미선언(기본 true)과 백업 규칙 파일
   부재는 확인했지만, 실제 백업 산출물에 prefs/DataStore가 들어가는지는 실측하지
   않았다(§2.5).
7. **⚠️ 미검증 — `flutter_secure_storage` 10.x→11.x breaking change**. 채택하지
   않기로 해 조사하지 않았다.
8. **⚠️ 미검증 — `memberId` 재배정 가능성**. 계약에 되돌리는 API가 없다는 것만
   확인했다(계약 1284행). 데스크에서 Firestore를 직접 편집하는 경로는 계약 밖이다.
9. **정정 문구 미확정**(§3.3). 탈퇴·미연결·권한상실을 앱이 구분할 수 없으므로
   원인을 지목하지 않는 문장이어야 한다.
10. **⚠️ 미검증 — 320ms 페이드가 캐시 히트 경로에서 어떻게 느껴지는지**(§6.1).
    실기기 확인 필요.
