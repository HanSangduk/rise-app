## 0. 네 줄 요약

1. **기동은 7왕복이 일렬로 서 있다.** 그런데 진짜 의존성 깊이는 **2단계**다. 7개 중 **6개가 "그냥 순서대로 쓰였을 뿐"**이고, 데이터가 실제로 앞 결과를 필요로 하는 경계는 `GET /v1/me` **하나뿐**이다.
2. **`fetchHwChecks`는 `fetchHomeworks`로부터 아무것도 받지 않는다.** 두 번째 인자 `date`는 네트워크가 아니라 **로컬 시계**에서 오고(`home_repository_impl.dart:134-135`), `hwId` 매칭은 전부 받아온 뒤의 **클라이언트 조인**이다(`:166-174`). `fetchMyBookings`·`fetchHomeworks`도 마찬가지로 **요청 자체는** `fetchMyPasses`와 무관하다 — 쿼리 파라미터가 `member` 하나뿐이다.
3. **프리페치의 점화 지점은 `app.dart`의 `restoreLanding` 클로저 하나다.** 다만 `ref.read(homeViewModelProvider.future)`를 그냥 쏘면 **역효과**다: 이 provider는 autoDispose이고(`home_view_model.g.dart:113`) 구독자가 없으면 riverpod가 요청이 나간 채로 element를 폐기한다 — 이 저장소가 이미 한 번 밟고 주석으로 남긴 함정이다(`staff_directory.dart:56-60`). 그 결과는 **왕복 4개의 정확한 중복**이지 프리페치가 아니다.
4. **가장 위험한 건 "성공한 프리페치"가 아니라 "붙잡아 둔 실패"다.** 프리페치 결과를 붙들면 홈이 스피너 대신 `RiseErrorView`로 착지한다(`home_screen.dart:94-101`) — 오늘은 알아서 풀리던 일시적 실패가 **탭을 눌러야만 풀리는 종착점**이 된다. 그래서 규칙은 하나다: **성공만 승계하고 실패는 버린다.**

## 1. 진짜 의존성 그래프

### 1.1 기동 → 사용 가능한 홈까지의 왕복 전수

`preload`는 어디에도 쓰이지 않아 4개 탭 브랜치가 전부 기본값 `preload: false`다(`app_router.dart:65,68,71,74` / go_router 16.3.0 `route.dart:1114,1436`). 따라서 **예약·기록·마이 뷰모델은 기동에 관여하지 않는다.** FCM·analytics·remote config·Crashlytics도 없다(`pubspec.yaml` 의존성 전체). 기동 경로의 네트워크는 아래가 전부다.

| # | 호출 | 호출 지점 | 쿼리 파라미터 | 실제 입력 |
|---|---|---|---|---|
| 0 | Firebase `getIdToken()` | `dio_client.dart:47` | — | 로컬 캐시(1시간 이내) / 만료 시 `securetoken.googleapis.com` 왕복 |
| 1 | `GET /v1/me` | `me_api.dart:11` ← `auth_repository_impl.dart:207` ← `session_restore.dart:91` | **없음** | 토큰만 |

### 1.2 진짜 의존 vs 그냥 순서대로 쓰인 것

**진짜 의존은 하나뿐이다.** `#1 → {#4, #5, #6, #7}`. `memberId`는 `/v1/me` 응답에서만 나오고(`auth_repository_impl.dart:210,220`), 네 호출 전부 그걸 쿼리 파라미터로 요구한다.

나머지는 전부 **작성 순서**일 뿐이다. 하나씩 반박한다.

#### ① `_readStaffMap()`이 패스 매핑을 먹이는가 — 먹인다. 그러나 네트워크 의존이 아니다.

`staffMap`은 `:51`(`trainerName`) · `:54`(`trainerInactive`) · `:58`(`trainerOffdays`) · `:118`·`:119`(다음 예약의 코치 표시)에서 쓰인다. 즉 **`passes` 리스트를 조립하기 전에는 손에 있어야 한다.**

하지만 `StaffDirectory.fetchAll()`은 **인자를 하나도 받지 않는다**(`staff_directory.dart:26-27`). `/v1/staff`는 센터 전원을 통째로 돌려주고, 서버가 센터를 토큰에서 판정한다. `#4`의 응답을 기다릴 이유가 전혀 없다 — `#1`조차 기다릴 필요가 없다.

> 정확히 말하면 이건 **네트워크 의존이 아니라 조립 시점 의존**이다. `Future.wait([staffMapFuture, passesFuture])` 뒤에 조립하면 그대로 성립한다. 지금은 `await` 두 줄이 나란히 있어서(`:39`, `:40`) 그 구분이 코드에서 지워져 있다.

#### ② `fetchMyBookings`가 `fetchMyPasses`에 의존하는가 — **요청은 아니다.**

`bookings_api.dart:17-19`가 보내는 건 `{'member': memberId}` 하나다. `selected.trainerId`는 `:105`의 `.where((b) => b.status == 'confirmed' && b.trainerId == selected.trainerId)` — **받아온 리스트를 거르는 클라이언트 필터**다. 서버는 트레이너 필터를 받지도 않는다.

> `docs/design/스플래쉬_교차검증.md:332`는 이걸 "`fetchMyPasses`의 `trainerId`에만 의존"이라고 적었다. **의존을 과대평가한 표현이다.** 요청은 무관하고 후처리만 의존한다 — 그래서 도달 가능한 모양은 "2왕복"이 아니라 **"게이트 1개 + 그 뒤 4개 동시"** 다.

#### ③ `fetchHomeworks`도 같다.

`home_remote_data_source.dart:12-14`가 보내는 건 `{'member': memberId}`. `selected.trainerId` 비교는 `:141`의 필터이고, 게다가 `scope == 'center_notice'`면 그 비교를 건너뛴다 — 즉 **응답의 일부는 트레이너와 무관하게 항상 쓰인다.**

#### ④ `fetchHwChecks`가 `fetchHomeworks`에서 뭔가를 받는가 — **아무것도 받지 않는다.** (질문의 핵심)

`fetchHwChecks(memberId:, date: todayIso)`의 두 인자를 각각 추적하면:

- `memberId` — `#1`에서 온다.
- `todayIso` — `DateFmt.isoDate(DateFmt.todayKst())`, `home_repository_impl.dart:134-135`. **`fetchHomeworks` 호출(`:137`)보다 두 줄 위에서 이미 확정된다.** 로컬 시계 읽기다.

두 리스트가 만나는 지점은 `:166-174`의 이중 루프 — `c.hwId == hw.id && c.date == todayIso`. **이미 받아 온 두 리스트에 대한 순수 클라이언트 조인**이다.

> 결론: `#6`과 `#7`은 **완전히 독립**이다. 지금 순차인 이유는 `:137`이 `:155`보다 위에 있다는 것뿐이다.
>
> **주의 — 병렬화할 때 절대 건드리면 안 되는 것**: `todayIso`가 `:134`에서 **한 번만** 읽히고 굳는다는 성질. 이건 스타일이 아니라 불변식이다. `:129-133`과 `home_view_model.dart:163-172`가 설명하듯, 읽기와 쓰기가 시계를 각각 읽으면 23:50 로드 → 00:05 체크에서 어제 목록이 오늘 문서를 덮는다. `Future.wait`로 바꾸더라도 **시계 읽기는 wait 위에 그대로 남겨야 한다.**

#### ⑤ `centerPolicy`가 세션에 의존하는가 — **인위적 의존이다.**

`center_policy_provider.dart:24-25`가 `session == null`이면 폴백을 즉시 반환한다. 주석(`:23`)은 이유를 밝힌다 — "로그인 전엔 호출하지 않는다(401/403 소음 방지)".

그런데 `/v1/center`는 파라미터가 없고(`center_api.dart:16`) 서버가 토큰에서 센터를 판정한다. 그리고 프리페치를 점화하려는 시점에는 이미 `FirebaseAuth.instance.currentUser != null`이 확인된 뒤다(`session_restore.dart:76`) — 즉 **Bearer가 붙는다**(`dio_client.dart:47-50`). `sessionProvider`가 채워지길 기다리는 건 "로그인했는가"의 **과한 대리 지표**다.

> 트레이드오프: 아직 회원 연결 전(`MemberNotLinkedFailure`)인 사용자는 `/v1/center`에서 403을 받을 수 있다. 비용은 낭비된 요청 1개뿐이고(`:41-43`이 전부 삼키고 폴백), 그 경로는 최초 1회 온보딩에만 나온다. **얻는 게 크다.**

```

      │
      ├─── GET /v1/me ──────► memberId ──┬── GET /v1/passes    (member)

깊이 = 2.   현재 코드의 깊이 = 7.
```

**레벨 0** (토큰만 있으면 됨): `/v1/me` · `/v1/staff` · `/v1/center`
**레벨 1** (memberId 필요): `/v1/passes` · `/v1/bookings` · `/v1/homeworks` · `/v1/hw-checks`

`Future.wait`는 `lib/` **전체에 0건**이다(전수 검색). 병렬화 전례가 아예 없다는 뜻이라, 도입하면 그 자체가 새 패턴이 된다.

## 2. 정량화

> **이 절의 숫자는 전부 추정이다.** 나는 이 세션에서 아무것도 계측하지 않았다. 아래는 코드에 박힌 상수와 이 저장소에 남아 있는 **기존 실측치**에서 구조적으로 추론한 값이고, 실측치와 추정치를 표기로 구분했다.

### 2.1 RTT 가정과 그 근거

코드의 타임아웃은 **상한이지 전형값이 아니다.** 전형값을 유도할 근거는 셋이다.

| 근거 | 값 | 출처 |
|---|---|---|
| Cloud Run 콜드 스타트 | **380~525ms (실측)** — 24시간 17회 | `work_log/P12-audit-sweep.md:33` |
| 실기기 기동(아이콘 탭 → 복원 완료) | **1.3초 (실측)** | `splash_gate.dart:70` 주석 |
| 복원 예산 6초의 근거 문장 | "서버는 싸고, **변동은 전부 무선 구간이다**" | `session_restore.dart:88-90` |
| DNS / TCP+TLS / 서버 처리 분해 | 50~300 / 100~400 / 20~60ms | `docs/design/스플래쉬_기동경로.md:236-244` |

여기서 두 개의 상수를 세운다.

- **C = 첫 연결 수립 ≈ 350ms** (DNS + TCP + TLS의 p50 추정). `dioProvider`는 앱 수명 동안 1개라(`dio_client.dart:12-13`) **이후 요청은 연결을 재사용한다.**
- **R = 연결 재사용 시 1왕복 ≈ 150ms** (무선 RTT 90~130 + 서버 처리 20~60). 상기 "서버는 싸다"와 정합한다.
- **콜드 스타트 가산 ≈ +450ms**, 첫 요청에만. uptime check가 2분마다 때려 대체로 웜이다(`기동경로:241`).

### 2.2 직렬 비용 vs 병렬 비용 (추정)

**HTTP/1.1이라는 제약을 먼저 명시한다.** `httpClientAdapter`·`http2`·`native_dio_adapter`·`cronet` 어느 것도 쓰지 않는다(`pubspec.yaml` + `lib/` 전수 0건) → dio 5.11.0의 기본 `IOHttpClientAdapter` → `dart:io HttpClient` → **HTTP/1.1, 멀티플렉싱 없음.** 병렬 요청은 **추가 TCP 연결**을 연다. 다만 핸드셰이크들이 **서로 겹치므로** 벽시계는 합이 아니라 max다.

| 구간 | 현재(직렬) | 병렬(깊이 2) |
|---|---|---|
| 레벨 0 | `C + R` = 500ms — 단, `/v1/staff`·`/v1/center`가 여기 없고 뒤에 줄 서 있음 | `C + R` = **500ms** (3개 동시, 핸드셰이크 겹침) |
| 레벨 1 | — | `R` = **150ms** (4개 동시) |
| **합계 (웜 인스턴스)** | `C + 7R` = **1,400ms** | `C + 2R` = **650ms** |
| **합계 (콜드 인스턴스)** | ≈ **1,850ms** | ≈ **1,100ms** |

**절감 ≈ 750ms (약 54%).**

사용자 체감으로 갈라 보면 더 선명하다.

| 회원이 보는 것 | 현재 | 병렬만 | 병렬 + 프리페치 |
|---|---|---|---|
| 스플래시 (`/v1/me` 대기) | 실측 1.3초 | 1.3초 (변화 없음) | 1.3초 (변화 없음) |
| **홈 스피너** (`home_screen.dart:85`) | **6왕복 = 900ms** (콜드 1,350ms) | 2왕복 = 300ms | **≈ 0ms** (§2.3) |

### 2.3 프리페치가 겹칠 수 있는 창 (추정)

프리페치는 **비용을 줄이는 게 아니라 이미 낭비되고 있는 시간에 겹쳐 넣는 것**이다. 두 개의 창이 있다.

**창 A — 스플래시 전체 구간.** 스플래시는 첫 Flutter 프레임부터 `_restored`(`app.dart:45,56`)까지 떠 있고, 실측 1.3초다. 그 시간의 대부분은 `/v1/me` 대기다. **레벨 0의 `/v1/staff`·`/v1/center`를 여기에 넣으면 한계 비용이 0이다** — `/v1/me`가 끝나기 전에 같이 끝난다.

**창 B — 세션 확정부터 스플래시가 완전히 걷힐 때까지.** 이게 덜 알려진 쪽인데 꽤 넓다. `sessionProvider.notifier.set(value)`는 `session_restore.dart:103`에서 실행되고, 그 **뒤에** 이런 것들이 남아 있다:

| 남은 일 | 근거 | 추정 |
|---|---|---|
| `await store.clear()` — SharedPreferences 디스크 쓰기 | `session_restore.dart:105` | 수~수십 ms |
| `restoreAuthLanding` 반환 → `finally`에서 `setState` | `app.dart:53-57` | 1 프레임 |
| go_router가 새 `RouteMatchList` 세우고 `/home` 빌드 · 첫 실제 페인트 | `app_router.dart:39-41` | 1~수 프레임 (+ Pretendard 6.4MB 최초 파싱) |
| `SplashGate` 페이드아웃 | `splash_gate.dart:59` (`fadeOut = 320ms`) | **320ms** |

합쳐서 **≈350~450ms의 공짜 선행 시간**이다. 레벨 1이 병렬이면 `R ≈ 150ms`이므로, **레벨 1 네 개가 스플래시가 다 걷히기 전에 끝난다.**

> 그래서 최종 그림은 이렇다 — **스플래시가 걷히는 순간 홈은 이미 데이터를 손에 들고 있다.** 스피너 900ms가 0ms가 된다. 이게 "스플래시 나오는 동안 미리 가져오면 좋잖아"의 정확한 실현 형태다.

### 2.4 덤 — 최악 케이스가 3배 짧아진다

**홈 로드에는 예산이 하나도 없다.** `restoreBudget` 6초는 `loadSession`에만 걸리고(`session_restore.dart:91-96`), `SplashGate.ceiling` 8초는 오버레이에만 걸린다(`splash_gate.dart:70`). `loadHome`에는 **아무것도 없다.**

재시도가 0회이므로(`dio_client.dart:25-61`에 인터셉터 2개뿐, `guardApi`도 재호출 없음) 호출당 최악은 `receiveTimeout` 10초다(`api_config.dart:12`).

```
현재: 6왕복 순차 × 10초 = 최악 60초 동안 빨간 스피너
병렬: 2레벨       × 10초 = 최악 20초
```

체감 개선과 별개로 **이건 견고성 개선이다.**

## 3. 프리페치 설계

### 3.1 점화 지점 — `app.dart`의 `restoreLanding` 클로저

후보를 셋 놓고 둘을 버린다.

| 후보 | 판정 |
|---|---|
| `main.dart` — `runApp` 전 | **버린다.** `await`가 `runApp`보다 앞이면 순수 가산이다. 첫 프레임이 늦어져 네이티브 스플래시가 더 오래 남는데, 그건 우연한 이득이지 설계가 아니다. 게다가 이 시점엔 세션이 없다. |
| `SplashGate.initState` | **버린다.** `SplashGate`는 `ref`가 없는 평범한 `StatefulWidget`이고(`splash_gate.dart:46`), 클래스 주석이 스스로 "덮으라고 있는" 층이라고 밝힌다. 데이터 오케스트레이션을 붙이면 14개 위젯 테스트(`test/core/brand/splash_gate_test.dart`)가 걸린 그 순수성이 깨진다. |
| **`_RiseMemberAppState`** — `restoreLanding` 클로저(`app.dart:49-58`) | **여기다.** 이미 앱 수명 동안 1회만 돌고, `ConsumerState`라 `ref`가 있고, 스플래시를 걷는 `finally`를 이미 들고 있다. |

그 안에서 **점화 시점은 둘**이다.

**T0 — `await restoreAuthLanding(ref)` 직전.** 레벨 0의 두 개를 깨운다.

- `staffMapProvider` — **오늘 그대로 안전하다** (§3.2).
- `centerPolicyProvider` — 두 가지 선결 조건이 있다 (§3.2, §3.3).

`/v1/staff`는 착지 경로 셋 중 **둘**에서 쓰인다: `/home`(→ `home_coach_card.dart:52`가 watch)과 `/login/center-confirm`(→ `center_confirm_screen.dart:44`가 watch). 즉 **T0 워밍은 홈으로 안 가는 회원에게도 이득**이다. 낭비되는 경로는 `/login`(미로그인)뿐인데, 거기는 애초에 `currentUser == null`이라 `restoreAuthLanding`이 즉시 반환하므로(`session_restore.dart:76`) **점화 조건을 `currentUser != null`로 두면 그 경로도 안 탄다.**

**T1 — 세션이 확정되는 순간.** 레벨 1(홈 뷰모델)을 깨운다. 두 가지 배선이 가능하다.

1. `restoreAuthLanding`에 콜백 인자를 추가해 `session_restore.dart:103` 직후 부른다 — 정확하지만 침습적이다.
2. `_RiseMemberAppState.initState`에서 `ref.listenManual(sessionProvider, ...)`로 **첫 non-null 세션**에 1회 래치를 건다 — `flutter_riverpod-3.0.3/lib/src/core/widget_ref.dart:242`가 정확히 `initState`용으로 설계된 API다.

**2번을 권한다.** 트리거를 "복원이라는 특정 호출부"가 아니라 **"이제 회원이 누군지 안다"는 실제 선결 조건**에 붙이기 때문이고, 덤으로 **최초 로그인 경로도 같이 덮는다**(온보딩을 막 끝낸 회원도 같은 워밍을 받는다). 이미 `app.dart:73`에 `ref.listen(sessionProvider, ...)`가 있어 패턴도 낯설지 않다 — 단, 그 리스너는 `build` 안이라 별개이고, 프리페치용은 `initState`의 `listenManual`이어야 한다.

### 3.2 비위젯 컨텍스트에서 `ref.read(...future)`는 여기서 안전한가

**provider마다 답이 다르다. 그리고 홈 뷰모델에 대해서는 "아니오"다.**

#### 메커니즘 (riverpod 3.0.3, 상류 소스로 확인)

- `ProviderElement.mayNeedDispose()`는 `isAutoDispose && !isActive && keepAliveLinks.isEmpty`이면 폐기를 예약한다 — `riverpod-3.0.3/lib/src/core/element.dart:1123-1131`.
- `isActive`는 `listenerCount - pausedActiveSubscriptionCount > 0` — `element.dart:385`. **`ref.read`는 리스너를 남기지 않는다.**
- 폐기 예약을 받은 element는 `ProviderScheduler`가 처리한다: *"Providers are disposed if they spent at least one full frame without any listener"* (`scheduler.dart:34`), *"The provider will be disposed at the end of the next event-loop"* (`scheduler.dart:138-141`).
- 임시 구독을 닫을 때 `mayNeedDispose`가 불린다 — `provider_subscription.dart:79`.

#### 이 저장소는 이미 이걸 밟았다

`staff_directory.dart:56-60`이 실측 기록을 남기고 있다:

> "repository는 화면처럼 watch하지 않고 `staffMapReaderProvider`를 통해 read로 들어오는데, 그러면 **구독자가 0이라 요청이 나간 채로 element가 폐기되고 `.future`가 "disposed during loading"으로 깨진다** (그리고 탭마다 다시 요청이 나가 단일화가 무의미해진다). **실측으로 확인한 경로**라 링크를 먼저 걸고, 실패했을 때만 되돌린다."

그래서 `staffMapProvider`는 `ref.keepAlive()`를 **await 앞**에 건다(`:71`). 상류 소스와 이 주석이 정확히 같은 것을 말한다.

#### provider별 판정

| Provider | autoDispose? | keepAlive 시점 | `ref.read(...future)` 프리페치 |
|---|---|---|---|
| `staffMapProvider` | 예 | **fetch 전** (`staff_directory.dart:71`) | ✅ **안전.** 지금 그대로 쏴도 된다. |
| `centerPolicyProvider` | 예 | **성공 후** (`center_policy_provider.dart:31`) | ⚠️ **비행 중에는 링크가 없다.** 오늘은 항상 `ref.watch`로만 도달해(`home_view_model.dart:44`, `home_screen.dart:38`) 잠복해 있을 뿐이다. `read`로 프리페치하면 깨어난다. |
| `homeViewModelProvider` | 예 (`home_view_model.g.dart:113`) | **없음** | ❌ **안전하지 않다.** 아래 참조. |

`centerPolicyProvider`의 처방은 `staffMapProvider`가 이미 쓴 것과 같다 — **`keepAlive()`를 fetch 위로 올리고, 실패 시 `link.close()`로 되돌린다.** 지금 `:31`의 위치는 "성공만 캐시"라는 의도를 표현하지만(`:12-20`의 주석), 그 의도는 `link.close()`로도 똑같이 표현되고 비행 중 폐기 위험은 사라진다.

#### 홈 뷰모델의 연쇄 붕괴

`homeViewModelProvider`를 `ref.read(...future)`로 쏘면 이렇게 된다.

```
ref.read(homeViewModelProvider.future)
  → element 생성, build() 시작
  → ref.watch(centerPolicyProvider.future)     ← centerPolicy element에 리스너 1개 생김
  → loadHome() 시작, 왕복 4~6개 발사
  ─── 이벤트 루프 끝 ───
  → homeViewModel: 리스너 0 → scheduleProviderDispose        (element.dart:1123)
  → 폐기되며 centerPolicy 구독 해제 → centerPolicy도 리스너 0 → 같이 폐기
  → .future 깨짐 · 요청은 취소되지 않음 (lib/ 전체에 CancelToken 0건)
  ─── 그 뒤 ───
  → HomeScreen mount, ref.watch(homeViewModelProvider)       (home_screen.dart:35)
  → 새 element → 왕복 4~6개 전부 재발사
```

**결과: 프리페치 이득 0, 요청 수 2배.** 그것도 무선이 가장 차가운 순간에.

#### 안전한 형태

**구독을 붙들어라.** `ref.listenManual(homeViewModelProvider, (_, __) {})`가 리스너 카운트를 1로 만들어 `isActive`를 참으로 유지하고, 그러면 나중에 `HomeScreen`이 `ref.watch`할 때 **같은 element**에 붙어 이미 해소된 `AsyncData`를 즉시 받는다. `listenManual`은 위젯이 폐기될 때 구독을 자동으로 닫는다(`widget_ref.dart:240`) — `_RiseMemberAppState`는 앱 수명이므로 실질적으로 앱이 살아 있는 동안 유지된다.

`unawaited(...)`로 감싸는 fire-and-forget 전례는 이미 있다(`qr_scan_screen.dart:47` 등). **프리페치는 어떤 경우에도 `restoreLanding`의 await 체인에 들어가면 안 된다** — `_restored`가 `finally`에 있는 이유(`app.dart:53-57`)를 그대로 존중해야 한다.

### 3.3 프리페치가 실패하면

세 provider의 실패 처리는 서로 다르고, **둘은 이미 옳다.**

| Provider | 실패 시 | 사용자에게 보이는가 |
|---|---|---|
| `staffMapProvider` | `staffMapReader`가 빈 맵으로 삼킨다 (`staff_directory.dart:128-137`) · 실패는 캐시 안 함(`:79`) | ❌ 안 보인다. 코치 이름 문구가 통째로 생략될 뿐(`home_screen.dart:333-339`). **best-effort로 설계됨.** |
| `centerPolicyProvider` | `CenterPolicy.fallback` 반환, **절대 throw 안 함** (`center_policy_provider.dart:41-43`) | ❌ 안 보인다. |
| `homeViewModelProvider` | `AsyncError`가 element에 **남는다** | ⚠️ **보인다.** §4의 함정. |

앞의 둘은 프리페치해도 새 위험이 없다. 세 번째가 전부다.

## 4. 함정 — 실패한 프리페치와 중복 요청

### 4.1 "홈이 어차피 재시도할 텐데 뭐가 나빠지나"

**결과를 붙드느냐 아니냐에 따라 정확히 갈린다. 그리고 두 경우 다 나빠진다 — 다른 방식으로.**

#### 경우 A — 결과를 안 붙든다 (구독 없이 `ref.read`)

에러는 element와 함께 버려진다. `HomeScreen`이 새 element를 만들어 정상 로드한다. **의미론적으로는 아무것도 나빠지지 않는다.**

그런데 §3.2의 연쇄 붕괴가 그대로 일어나 **왕복 4~6개가 중복 발사**된다. `CancelToken`이 `lib/` 전체에 0건이므로 버려진 요청도 **바이트는 끝까지 간다.** 즉 이 경우의 손해는 "체감이 나빠짐"이 아니라 **"이득 0에 트래픽 2배"** 이고, 하필 신호가 나쁜 상황에서 두 벌의 요청이 같은 무선을 두고 경쟁한다. **프리페치라는 이름의 순손실이다.**

#### 경우 B — 결과를 붙든다 (구독 유지 — 프리페치가 작동하려면 이쪽이어야 한다)

**이쪽은 명백히 나빠진다.**

`HomeScreen`이 그 element에 붙으면 `async.when`의 `error:` 가지를 그린다 — `RiseErrorView`(`home_screen.dart:94-101`). 스피너가 아니다.

- **오늘**: 느리지만 결국 되는 망 → 스피너가 돌다가 내용으로 바뀐다. 회원은 아무것도 안 한다.
- **프리페치 후**: 스플래시 창(무선이 막 깨어나고, DNS가 차갑고, 앱이 방금 뜬 — **일시적 실패가 가장 잦은 바로 그 구간**)의 실패가 화면에 **굳는다.** 회원이 "다시 시도"를 눌러야만 풀린다.

> **일시적 실패를 회복 가능한 상태에서 탭이 필요한 종착점으로 승격시킨 것이다.** 이게 이 설계에서 가장 조심해야 할 단 하나다.

#### 처방 — 성공만 승계하고 실패는 버린다

```
프리페치 구독의 규칙:
  AsyncData  → 유지한다. HomeScreen이 이 element에 붙어 즉시 그린다.
  AsyncError → 구독을 닫는다. 리스너 0 → 다음 이벤트 루프 끝에 element 폐기
               → HomeScreen이 새 element를 만들고 스피너부터 시작한다 (= 오늘과 동일)
```

이러면 **"프리페치는 절대 상황을 악화시키지 않는다"가 불변식이 된다.** 최악이 오늘과 같아진다.

구현 시 확인할 것 두 가지:

1. **리스너 콜백 안에서 구독을 닫는 것** — riverpod가 통지 중인 시점이라 `Future.microtask`로 한 프레임 미루는 편이 안전하다. 실기기가 아니라 위젯 테스트로 잡을 수 있는 종류다.
2. **`EmptyPassesFailure`는 에러가 아니다.** `loadHome`은 회원권 0개일 때 이걸 던지고(`home_repository_impl.dart:41-44`) 홈은 이걸 **타입으로 구분해 전용 빈 상태**를 그린다(`home_screen.dart:86-93`). 이건 "정상적으로 도달한 종착점"이라 버릴 이유가 없다. 다만 **단순함을 택해 모든 `AsyncError`를 버리는 쪽을 권한다** — 비용은 드문 경로에서 로드 1회 더이고, 대신 "실패는 항상 버린다"는 규칙이 예외 없이 성립해 나중에 무너지지 않는다.

### 4.2 중복 in-flight 요청 — 세 가지 출처

#### ① 고아 element 중복 — **실재하고, 가장 크다**

§3.2 · §4.1-A. 프리페치 element가 비행 중 폐기되고 홈이 새 element를 만든다. **회원 스코프 왕복 4개가 정확히 2벌.** 처방은 구독 유지.

#### ② 공유 provider 디듀프 — **이건 제대로 작동한다**

`staffMapProvider`와 `centerPolicyProvider`는 element가 하나다. 비행 중에 두 번째 독자가 들어오면 **같은 `Future`에 붙고 두 번째 요청은 나가지 않는다** — element가 살아 있는 한. `staffMapProvider`는 `:71`의 선(先) `keepAlive`로 그걸 보장한다.

실제로 오늘 홈에서 `/v1/staff`는 두 곳이 쓰는데(repository의 `staffMapReader` `:132`, `HomeCoachCard`의 `ref.watch` `home_coach_card.dart:52`) **왕복은 1개다**. `home_screen.dart:133`의 주석이 그걸 명시한다("staffMapProvider는 홈이 이미 watch 중이라 왕복 0"). **T0 프리페치는 여기에 그냥 얹힌다** — 새 요청을 만들지 않고 홈의 임계 경로에서 `/v1/staff`를 통째로 들어낸다.

`centerPolicyProvider`도 같은 성질이지만 **§3.2의 keepAlive 시점 문제를 먼저 고쳐야** 이 성질이 프리페치 경로에서도 성립한다.

#### ③ 탭 간 결합 — 새 위험은 아니지만 알고 있어야 한다

`booking_view_model.dart:95`가 `await ref.watch(homeViewModelProvider.future)`를 한다. 즉 **홈 element의 수명은 예약 탭에도 영향을 준다.** 프리페치 구독을 앱 수명 동안 유지하면 예약 탭 첫 진입도 빨라진다(부수 이득). 반대로 §4.1의 "에러 시 구독 닫기"는 예약 탭에도 같은 방식으로 옳게 동작한다 — 새 element에서 다시 로드한다.

#### ④ 곁다리 — 토큰 인터셉터의 동시 실행

`dio_client.dart:46-50`은 **요청마다** `await FirebaseAuth.instance.currentUser?.getIdToken()`을 한다. 병렬로 3~4개를 쏘면 `getIdToken()`도 3~4개가 동시에 돈다. Firebase SDK가 갱신을 캐시·디듀프하지만, **토큰이 만료된 상태에서의 동시 갱신은 지금 코드가 한 번도 겪어 보지 않은 경로**다(오늘은 전부 순차). 차단 사유는 아니고 **실기기에서 확인할 항목**이다(§8).

## 5. 순서 — 무엇이 첫 "의미 있는" 페인트를 막나

### 5.1 스플래시가 기다려야 하는 것: `GET /v1/me` 하나뿐 (지금 그대로)

`/v1/me`는 데이터만 게이트하는 게 아니라 **착지 화면 자체를 게이트한다.** 결과에 따라 `/home` · `/login/center-confirm` · `/login` 셋으로 갈린다(`session_restore.dart:44-56`). 이게 확정되기 전엔 무엇을 덮고 있는지조차 모른다. **이미 스플래시가 여기서 기다리고 있고, 그게 맞다.**

### 5.2 홈 안에서 첫 의미 있는 페인트를 막는 것: `GET /v1/passes`

`home_repository_impl.dart:40`. 네 가지 근거 전부 코드에서 나온다.

1. **레이아웃 자체가 갈린다.** 회원권이 0개면 `EmptyPassesFailure`를 던지고(`:41-44`) 홈은 **완전히 다른 트리**를 그린다(`home_screen.dart:86-93`). 이게 손에 오기 전엔 *무엇을 그릴지*조차 모른다.
2. **헤드라인 요소가 전부 여기서 나온다.** 헤더 배지(`home_screen.dart:399-402`) · `RemainingRing`(`:177-180`) · 패스 스위처 칩(`:120-124`) · 유효기간 줄(`:201`).
3. **본문 전체를 지울 수 있다.** `hasUsablePass == false`면 헤더 배지와 본문이 통째로 빠진다(`home_screen.dart:49,69,73` · `home_repository_impl.dart:203`).
4. **나머지의 셀렉터다.** `selected.trainerId`(`:79-84`)가 예약 필터(`:105`)와 Home Work 필터(`:141`)의 기준이다. 다른 응답들은 **이걸로 걸러지는 쪽**이다.

### 5.3 배경으로 계속 흘러도 되는 것

| 호출 | 왜 게이트가 아닌가 |
|---|---|

### 5.4 그럼 `/v1/passes`를 위해 스플래시를 더 붙잡아야 하나 — **아니다**

유혹적이다. 프리페치가 잘 돌면 패스는 스플래시 페이드 도중에 도착하니, 조금만 더 붙들면 항상 완성된 화면으로 착지시킬 수 있을 것 같다. **네 가지 이유로 거절한다.**

1. **`/v1/me` 전에는 시작조차 못 한다.** 패스를 기다리는 건 스플래시에 **왕복 하나를 통째로 더하는 것**이다. 겹치는 게 아니라 늘리는 것이다.
2. **`SplashGate`가 이미 이 원칙을 세워 놨다.** `:53-58` — "머무는 구간을 두지 않는다 … 거기에 hold를 더하면 그건 전환이 아니라 **새로 만들어낸 기다림**이다."
3. **상한 논리가 깨진다.** `ceiling` 8초는 "복원 예산 6초 + 여유"로 잡혀 있다(`:61-70`). 스플래시 아래에 두 번째 네트워크 구간을 넣으면 그 근거가 무너지고, 느린 회선에서 **정상 동작 중에 상한이 발화해** 반쯤 지어진 화면으로 회원을 떨어뜨린다.
4. **`기동경로 §5-3`이 이미 결론을 냈다.** "천장을 넘어가는 대기는 스플래시가 아니라 **착지 화면 안의 스켈레톤**이 받아야 한다."

**따라서**: 스플래시가 걷힐 때 패스가 아직 안 왔으면 → 홈이 스피너(또는 나중에 스켈레톤)를 보여준다. **오늘과 정확히 같다.** 프리페치는 p50을 0으로 만들고 최악을 건드리지 않는다. 그게 옳은 비대칭이다.

## 8. 검증

### 8.1 먼저 알아야 할 것 — 기동 경로에 회귀 테스트가 없다

`createRouter(restoreLanding: ...)`를 non-null로 부르는 테스트가 **하나도 없고**, `restoreAuthLanding` 종단 테스트도, `app.dart:73`의 리스너 테스트도 없다(`기동경로 §6.6` 마지막 행). 순수 함수(`classifyRestore` / `restoreLandingRoute`)만 검증돼 있다(`test/features/auth/presentation/session_restore_test.dart`).

**즉 지금 이 경로를 건드리면 깨져도 아무도 알려주지 않는다.** 3단계는 테스트를 먼저 깔지 않으면 안 된다.

### 8.2 3단계와 함께 들어가야 할 테스트

| 대상 | 검증 내용 |
|---|---|
| 중복 방지 | 프리페치 후 `HomeScreen` mount 시 각 엔드포인트가 **정확히 1회**만 불린다 (mock repository 호출 카운트). `test/features/home/home_kst_axis_test.dart:148`의 `ProviderContainer.test` 패턴 재사용 가능. |
| 실패 폐기 | 프리페치가 `NetworkFailure`로 끝난 뒤 `HomeScreen`이 **`RiseErrorView`가 아니라 스피너**로 시작한다. |
| 빈 상태 보존 | 프리페치가 `EmptyPassesFailure`로 끝난 경우의 화면(정책에 따라 승계 또는 재로드 — §4.1의 선택을 못 박는다). |
| 세션 게이트 | 세션이 없는 동안에는 프리페치가 발사되지 않는다 (`connected`가 아닌 착지에서 호출 0회). |
| 스플래시 독립성 | 프리페치가 **영원히 pending**이어도 `_restored`가 정상 시각에 true가 되고 스플래시가 걷힌다 (`app.dart:53-57`의 `finally` 보증). |
| 시계 불변식 | 병렬화 후에도 `HomeSummary.homeworkDate`와 `GET /v1/hw-checks`의 `date=`가 **같은 값**이다 (0단계 회귀). |

### 8.3 실기기에서 측정할 것

`--dart-define=API_BASE_URL`을 반드시 주입할 것 — 기본값이 `http://localhost:8080`이다(`api_config.dart:6-9`).

1. **스플래시 걷힘 시각 vs 홈 첫 내용 페인트 시각.** 이 문서의 전체 주장이 "그 간격이 0에 수렴한다"이다. 릴리스 빌드, 실기기(P11의 갤럭시 S21 울트라), 운영 백엔드.
2. **§2의 R·C 추정치를 실측으로 대체.** 특히 병렬 시 동시 TLS 핸드셰이크가 실제로 겹치는지 — HTTP/1.1이라 연결이 N개 열린다(§2.2).
3. **동시 `getIdToken()` (§4.2-④).** 토큰을 일부러 만료시키고 병렬 4요청을 태워, 갱신이 1회로 디듀프되는지 확인.
4. **웜 스타트 경로.** 복원이 100ms에 끝나면 창 B(≈400ms)가 그대로 남는지, 아니면 스플래시가 먼저 걷혀 프리페치가 오히려 홈 로드와 겹치는지.
