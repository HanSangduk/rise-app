# 체형 분석 타임라인 — 정보구조 설계

- 작성: 2026-08-27 · 렌즈: **정보구조(information architecture) — 사진이 쌓였을 때 무엇을 보여줄 것인가**
- 병렬 렌즈 2개는 이 문서가 다루지 않는다: **(a) 비교 인터랙션(와이프 슬라이더)**, **(b) 전체화면 뷰어**. 이 문서는 "무엇을 · 어떤 순서로 · 어느 밀도로 보여줄 것인가"만 다룬다. 두 사진을 **고르는 곳까지**가 내 범위이고, 고른 다음에 두 사진을 어떻게 겹쳐 보는가는 (a), 한 장을 크게 보는 건 (b)다.
- 모든 주장은 **읽은 코드**에 근거한다. 근거 파일은 §9.
- 코드는 한 줄도 고치지 않았다. 설계만.

## 0. 먼저 — 브리핑의 전제 하나를 정정한다

> "Currently `_beforeIndex`/`_afterIndex` default to the two most recent"

**코드는 그렇지 않다.**

```dart
void _resetIndices() {
  final n = widget.album.countFor(_pose);
  _beforeIndex = 0;                    // entries는 오래된 순 → 0 = 가장 처음
  _afterIndex = n > 0 ? n - 1 : 0;     // n-1 = 가장 최근
}
```

`BodyPhotoAlbum.from`이 포즈별로 `a.date.compareTo(b.date)`로 정렬하므로(`records_models.dart:144`) 인덱스 0은 **최초 촬영**이다. 즉 현재 기본값은 이미 **처음 vs 최근**이고, 이 문서가 "가장 유용하다"고 주장하려던 바로 그 조합이다.

**그러니 §2의 결론은 "기본값을 바꾸자"가 아니라 "이미 맞는 기본값이 이름도 없고 되돌아올 길도 없다"가 된다.** 이건 더 작은 수정이고 더 확실한 이득이다. 잘못된 전제 위에 설계를 쌓았으면 이미 옳은 동작을 뒤엎을 뻔했다.

## 1. 스케일 표 — 지금 UI가 몇 장에서 무너지는가

### 1.1 카드의 세로 구성 (현재)

```
RiseCard 패딩 13
├ RiseCardHeader                       ≈ 28dp   제목 + 포즈 배지
├ _PoseChips  (Wrap)                   ≈ 52dp × 포즈 줄수     ← N에 무관, 포즈 수·라벨 길이에 비례
├ SizedBox 4
├ 날짜 칩     (Wrap)                   ≈ 56dp × ceil(N_pose/4) ← N_pose에 정비례 ★
├ SizedBox 8
├ 사진 2장 (Row · Expanded)             = 130dp  고정
└ note 2줄                             ≈ 43dp
RiseCard 패딩 13
```

**★ 여기가 전부다.** 날짜 칩 `Wrap`만 유일하게 사진 장수에 정비례해서 자란다. 사진은 몇 장이 쌓이든 **130dp 고정**이다. 즉 사진이 쌓일수록 **답(사진)의 지분이 줄고 컨트롤(칩)의 지분이 커지는** 구조다.

폭 계산:
- 날짜 칩 `"8/14"` ≈ 56dp(+ spacing 4) → **266dp에 4개/줄**. `"12/24"`면 3개/줄.
- 포즈 칩 `"차렷 3"`(3자 라벨) ≈ 71dp → **3개/줄**.
- 포즈 칩 12자 라벨 + 카운트 ≈ **220dp** → **1개/줄**.

**폴드(fold)** — ListView 뷰포트: `568 − 상태바·AppBar ≈76 − 세그먼트 ≈71 − 바텀내비 ≈64 = 357dp`, 콘텐츠 패딩 22 빼고 **≈335dp**. 카드 내용이 335dp를 넘으면 그 아래는 스크롤해야 보인다.

### 1.3 무너지는 지점을 정확히

**(A) 날짜 칩 `Wrap` — N_포즈 ≥ 8에서 실패**
6장까지는 2줄이라 견딘다. 8장(=8개월)에서 사진이 폴드에 걸리고, **15장(=15개월)에서 사진이 통째로 폴드 밖으로 나간다.** 월 1회 촬영하는 회원은 **1년 3개월째에 "사진을 보려면 회색 알약 15개를 지나 스크롤해야 하는" 화면**을 만난다. 그리고 그 회색 알약 15개는 서로 구별이 안 된다 — `8/14`와 `9/12`는 회원에게 **아무 정보도 주지 않는다.** 어느 게 살 빠진 달인지 날짜로는 알 수 없다.

**(B) 날짜 라벨 `M/D`에 연도가 없다 — 13개월째 충돌**
`_shortDate(d) => '${d.month}/${d.day}'` (`body_photo_timeline.dart:220`). N_포즈 15면 기간이 15개월이므로 **같은 문자열이 두 번 나오는 게 보장된다.** 2025-08-14와 2026-08-14가 둘 다 `8/14`, 그것도 `Wrap`의 정반대 끝에. 정렬은 시간순이지만 라벨이 그걸 배신한다.

**(C) 포즈 칩 `Wrap` — 라벨 길이에 의해 먼저 무너진다**
서버가 **8개 × 12자**를 허용한다(`ValidateBodyPoses`). 12자 한글 라벨 + 카운트는 220dp라 266dp 폭에 **1개밖에 안 들어간다.** 8포즈 = **8줄 = 416dp = 화면 1.2개.** 사진이 0장이어도 이 상태가 된다 — 즉 **N과 무관하게 지금 당장 재현 가능한 파손**이다. 대표가 어드민에서 "왼쪽 옆구리 확인" 같은 라벨을 8개 만들면 끝이다.
게다가 `poseKeys`는 `시퀀스 ∪ 데이터 key`라 상한이 8이 아니다 — 시퀀스를 두 번 갈아엎으면 잔여 key가 붙어 **10~12줄**도 가능하다.

**(D) 포즈 칩 카운트에 단위가 없다**
`'${PoseSpec.labelFor(...)} ${album.countFor(key)}'` → 화면에는 **"차렷 3"**으로 뜬다. 코드 주석은 "장수를 라벨에 함께 실어"라고 하지만 렌더 결과에 "장"이 없다. `차렷 3`은 3장인지 3번째인지 3순위인지 읽는 사람이 정할 문제가 된다.

**(E) 날짜 칩 탭 규칙이 두 개 선택을 하나로 붕괴시킨다 — N ≥ 2에서 상시 재현**

```dart
onTap: () => setState(() {
  _beforeIndex = afterIndex;   // 지금 after를 before로 밀고
  _afterIndex = i;             // 누른 걸 after로
}),
```

- **이미 선택된 오른쪽(after) 칩을 다시 누르면** `i == afterIndex`이므로 `_beforeIndex = i`, `_afterIndex = i` → **둘이 같아진다.** 다음 빌드에서 `entries[i]`가 좌우에 똑같이 그려진다. **자기 자신과의 비교** — 1장 분기에서 방금 막아낸 바로 그 결함이, N ≥ 2에서는 칩 한 번 더 누르는 것으로 되살아난다.
- **이미 선택된 왼쪽(before) 칩을 누르면** 두 사진이 **좌우로 자리를 바꾼다.** 회원 입장에서는 "왼쪽을 눌렀더니 사진 두 장이 뒤바뀌었다."
- **before를 직접 지정할 방법이 없다.** (1월, 8월)을 보려면 1월 → 8월 **순서로** 눌러야 하고, 그 순서 규칙은 화면 어디에도 없다. 사진이 쌓일수록 원하는 쌍을 맞추는 데 필요한 탭 수와 시행착오가 늘어난다.
- **두 선택 칩이 서로 구별되지 않는다.** 둘 다 `selected: true`라 완전히 같은 스타일이다. 어느 쪽이 왼쪽(전)이고 어느 쪽이 오른쪽(후)인지 칩만 보고는 알 수 없다.

**(F) 새로 찍은 사진이 자동으로 선택되지 않는다 — "쌓임"의 이음매에서 나는 문제**
`refresh() => ref.invalidateSelf()`이고, Riverpod `.when`은 새로고침 중 이전 data를 유지하므로(`skipLoadingOnRefresh` 기본 `true`) `data:` 서브트리가 살아 있다 → **`initState`가 다시 돌지 않고 `_afterIndex`가 그대로 남는다.** 촬영 직후 사진이 n장 → n+1장이 되어도 `_afterIndex`는 여전히 옛 `n-1`(이제 끝에서 두 번째)이다. **회원이 방금 찍은 사진은 날짜 칩에는 나타나지만 선택되지 않는다.**
반대로 세그먼트를 운동 탭으로 갔다 오면 위젯 타입이 바뀌어 State가 폐기되고 인덱스가 리셋된다. **유지돼야 할 때 리셋되고, 리셋돼야 할 때 유지된다.**

## 2. 월 6개월차 회원이 이 탭을 열었을 때 — 기본 화면

### 2.1 회원의 질문은 "사진 다 보여줘"가 아니다

월 1회 촬영이면 6개월차에 회원이 가진 건 **6회차 × 포즈 수**다. 이 탭을 여는 동기는 하나다: **"내가 변하고 있나?"**

이 질문에 답이 되는 비교와 안 되는 비교가 있다.

| 비교 쌍 | 회원에게 보이는 것 | 판정 |
|---|---|---|
| **처음(1회차) ↔ 최근(6회차)** | 5개월치 변화 | ✅ **유일하게 신호가 노이즈를 이기는 구간** |
| 직전(5회차) ↔ 최근(6회차) | 4주치 변화 | ⚠️ 조명·거리·자세 정확도·촬영 시각(부기)·펌핑 차이에 묻힌다. **압축 없는 폰 원본 두 장의 차이 대부분은 몸이 아니라 촬영 조건이다** |
| 임의의 두 회차 | 회원이 궁금할 때만 | 필요는 하다. 기본값일 이유는 없다 |

**기본값은 처음 ↔ 최근이 맞다. 그리고 코드는 이미 그렇게 하고 있다(§0).** 바꿀 게 없다. 문제는 다른 데 있다.

### 2.2 지금 기본값의 실제 문제 — 이름이 없고, 돌아올 길이 없다

1. **그게 "처음 vs 최근"이라는 걸 화면이 말하지 않는다.** 회원이 보는 건 `8/14`와 `3/2`라는 두 칩과 두 사진뿐이다. "이게 네 5개월 25일치 변화다"라는 **가장 중요한 한 문장이 없다.**
2. **한 번 칩을 누르면 영영 못 돌아온다.** 되돌리는 컨트롤이 없다. 유일한 복귀 경로는 다른 세그먼트로 나갔다가 다시 들어오는 것 — 회원이 알아낼 리 없는 우회로다.
3. **새 사진을 찍어도 "최근"이 갱신되지 않는다(§1.3 F).** 기본값이 옳아도 갱신이 안 되면 6회차 회원에게는 1↔5 비교가 남는다.

### 2.3 결정

> **기본 쌍은 `처음 ↔ 최근`을 유지한다. 대신 (a) 이름을 붙이고, (b) 되돌아올 칩을 주고, (c) 새 사진이 오면 "최근"을 자동으로 그쪽으로 옮긴다.**

- **(a) 이름** — 사진 위 한 줄: `6회차 · 처음 3/2 → 최근 8/27` + 두 타일 캡션을 `처음`/`최근`으로. 두 사진이 각각 무엇인지가 사진에 붙어 있어야 한다.
- **(b) 복귀** — 같은 줄 오른쪽에 `처음↔최근` 텍스트 버튼. **현재 쌍이 이미 처음↔최근이면 렌더하지 않는다.** (아무 일도 안 하는 컨트롤을 그리지 않는다 — P31에서 죽은 슬라이더를 걷어낸 것과 같은 원칙이다.)
- **(c) 갱신** — 인덱스가 아니라 `storagePath`로 선택을 들고 있으면 목록이 늘어도 선택이 밀리지 않는다. 그리고 "회원이 after를 직접 고른 적이 없다"면 새 사진이 왔을 때 after를 최신으로 옮긴다. 회원이 명시적으로 골랐다면 건드리지 않는다 — 회원 선택이 데이터 갱신에 밀리면 안 된다.
- **기본 포즈는 `defaultPose`(사진 최다) 그대로 유지.** 근거가 옳다 — 비교가 성립할 확률이 가장 높은 포즈다(`records_models.dart:178`). 다만 §5 E4 케이스에서 **"지난 포즈"가 최다가 되어 기본 선택이 되는 경우**를 걸러야 한다(사진은 많지만 앞으로 절대 늘지 않는 포즈로 첫 화면을 여는 건 잘못된 첫인상이다). 규칙: **현재 시퀀스에 있는 포즈 중 최다**를 우선하고, 그런 포즈가 전부 0장일 때만 지난 포즈로 떨어진다.

### 2.4 "직전 회차"는 기본값이 아니라 프리셋

월 단위 변화가 안 보인다고 회원이 안 궁금한 건 아니다. 프리셋 칩으로 준다: `처음↔최근` · `직전 회차` · `3개월 전`. 프리셋은 **탭 한 번에 의미 있는 쌍**을 만든다 — 칩 두 개를 순서 맞춰 누르는 지금의 방식보다 저렴하고 실패하지 않는다.
성립하지 않는 프리셋은 **그리지 않는다**(after가 최초 회차면 `직전 회차` 없음, 기간이 3개월 미만이면 `3개월 전` 없음).

## 3. 제안 구조 — 세로가 N에 무관해지는 배치

### 3.1 원칙

이 카드는 **탭 안의 탭**(기록 → 체형 분석)이다. 세로를 요구할 자격이 없다. 그래서 설계 목표를 하나로 잡는다:

> **N = 1일 때와 N = 200일 때 카드 높이가 같아야 한다.**

달성 방법은 단순하다. **자라는 축을 세로에서 가로로 돌린다.** 두 `Wrap`이 유일한 가변 요소이므로, 둘 다 **가로 스크롤 1행**으로 바꾸면 카드 높이는 상수가 된다.

### 3.2 배치

```
┌ RiseCard ─────────────────────────────────────────── 266dp ─┐
│ 체형 분석 타임라인                              [ 차렷 ]      │  헤더 28
├──────────────────────────────────────────────────────────────┤
│ ‹ (차렷 6장) (T자 6장) (전굴 6장) (OH스쿼트 0장) …  →       │  포즈 행 52  ← 가로 스크롤 1행
├──────────────────────────────────────────────────────────────┤
│ 6회차 · 처음 3/2 → 최근 8/27          [처음↔최근]           │  쌍 라벨 44  ← 44dp 탭 타깃
├──────────────────────────────────────────────────────────────┤
│ ┌───────────────┐  ┌───────────────┐                        │
│ │               │  │               │                        │  사진 130
│ │   처음 3/2    │  │   최근 8/27   │  ← 빨간 보더 = 최근    │
│ └───────────────┘  └───────────────┘                        │
├──────────────────────────────────────────────────────────────┤
│ ‹ [▣][ ][ ][ ][ ][▣] →      2026 ┊                          │  필름스트립 64  ← 가로 스크롤 1행
│    └────── 비교 중 구간 ──────┘                              │     최신 쪽에 정렬해서 열림
├──────────────────────────────────────────────────────────────┤
│ (처음↔최근) (직전 회차) (3개월 전)                           │  프리셋 52   ← 폴드 아래 허용
│ 같은 포즈끼리 나란히 놓고 비교해요 · 격자는 촬영할 때…        │  note 43     ← 폴드 아래 허용
└──────────────────────────────────────────────────────────────┘
```

세로 예산 (26 패딩 + 28 + 52 + 44 + 130 + 64 = **344dp**, 폴드 335dp):
필름스트립 하단 몇 dp가 걸치지만 **사진 두 장과 쌍 라벨은 항상 폴드 위**다. 프리셋과 note는 의도적으로 폴드 아래 — 둘 다 각주다.
그리고 이 344dp는 **N = 1이든 200이든, 포즈가 1개든 8개든 동일하다.** 이게 표 §1.2의 1047dp를 대체하는 값이다.

폴드 위 우선순위(위에서부터 지켜야 할 순서): **헤더 → 포즈 행 → 쌍 라벨 → 사진 2장 → 필름스트립**. 공간이 더 줄면 필름스트립부터 폴드 아래로 내려간다(컨트롤이지 답이 아니다).

### 3.3 그룹핑을 무엇으로 할 것인가 — 월(月)은 아니다

**결론: 1차 = 포즈, 2차 = 촬영 회차(날짜). 월 헤더는 넣지 않는다.**

근거:
- **촬영 세션이 이미 자연스러운 묶음이다.** `camera_view_model`은 `poseIndex`를 시퀀스 끝까지 밀며 한 자리에서 전 포즈를 찍는다(`camera_view_model.dart:317`). 즉 **한 세션 = 한 날짜 = 포즈당 사진 1장.**
- 그러므로 **한 포즈 안에서 사진 N장 = 회차 N개**다. 월 1회 촬영자에게 월 헤더를 붙이면 **헤더 1개당 항목 1개** — 순수한 낭비이고, 세로를 두 배로 쓴다.
- 회원이 실제로 쓰는 서수는 날짜가 아니라 **회차**다("3개월 전에 찍은 거"). 그래서 스트립 타일에 `3회차` 서수를, 큰 타일 캡션에 날짜를 둔다.
- **연도는 월 헤더가 아니라 스트립 안의 구분선으로 해결한다.** 연도가 바뀌는 지점에만 얇은 세로선 + `2026` 라벨. §1.3 (B)의 `M/D` 충돌이 이걸로 정확히 해소되고, 세로는 0dp 든다.

**포즈를 1차 축으로 두는 이유**는 도메인이 이미 그렇게 생겼다 — `BodyPhotoAlbum.byPose`가 포즈별 리스트고, 비교는 같은 포즈끼리만 성립한다(다른 포즈 두 장을 나란히 놓는 건 비교가 아니다). 이건 UI 선택이 아니라 데이터의 모양이다.

### 3.4 포즈 행 — `Wrap` → 가로 스크롤

- 8개 × 12자 = 416dp 세로가 **52dp 고정**이 된다. 이게 이 문서에서 가장 큰 단일 절감이다.
- **`poseKeys` 순서는 절대 바꾸지 않는다.** 촬영 화면과 같은 순서여야 회원이 "내가 찍은 그 포즈"를 찾는다 — 코드 주석이 이미 방어하고 있는 계약이다(`body_photo_timeline.dart:185-190`). 가로 스크롤은 순서를 보존한다. 정렬을 바꾸는 대안(사진 있는 포즈 먼저)은 **이 계약을 깨므로 채택하지 않는다.**
- 대신 **0장 포즈는 흐리게**(`chipFg` → `muted`, 카운트 강조 없음). 목록에는 남는다(코드 주석의 근거 유지: 빼 버리면 회원은 그 포즈를 찍을 수 있다는 사실 자체를 모른다). 눈이 건너뛸 뿐 사라지지 않는다.
- **선택된 칩은 자동으로 뷰에 스크롤해 넣는다.** 안 그러면 가로 스크롤의 대가로 "지금 뭐가 선택됐는지 모름"을 얻는다. 헤더 배지가 현재 포즈를 이미 말하고 있어 이중 안전장치가 된다.
- 라벨에 **단위를 붙인다**: `차렷 6장` (§1.3 D 수정).
- 시퀀스에서 빠진 포즈에는 `지난 포즈` 표식 (§5 E4).

### 3.5 필름스트립 — 날짜 칩을 대체한다

**왜 칩이 아니라 섬네일인가.** 사진이 쌓일수록 `8/14`라는 문자열이 담는 정보량은 0에 수렴한다. 회원은 날짜로 사진을 기억하지 않는다. **44dp 섬네일은 실루엣과 자세를 담아서, 어느 회차가 어느 몸이었는지 알아볼 수 있게 한다.** 스트립의 유일한 임무가 "비교할 두 장을 고르게 하는 것"이므로, 고를 대상이 보여야 한다.

- 타일 **44 × 58dp**(3:4) + 간격 4 → **266dp에 5.5개 보임**. 44dp는 탭 타깃 최소치를 정확히 만족한다.
- **시간순(왼쪽=과거)** 유지 + **열릴 때 스크롤 위치는 맨 오른쪽(최신)**. 순서는 왼쪽=전 / 오른쪽=후인 아래 두 타일의 배치와 일치해야 하고, 초기 시선은 방금 찍은 사진에 있어야 한다. 이 둘은 충돌하지 않는다 — 순서와 스크롤 위치는 다른 축이다.
- **전/후를 구별해 표시한다**: `전`은 회색 보더 + `전` 캡션, `후`는 `redBorder` + `후` 캡션 — 아래 큰 타일 두 개(`highlighted` 여부)와 같은 시각 규칙. 그리고 **선택된 두 타일 사이에 밑줄을 그어 "비교 중인 구간"을 보여준다.** 이게 타임라인이 실제로 표현해야 할 내용이다: 점 두 개가 아니라 **구간**.
- **탭 규칙을 고친다(§1.3 E)**: 누른 인덱스가 `before`에 더 가까우면 `before`를 옮기고, `after`에 더 가까우면 `after`를 옮긴다. 구간의 양 끝을 잡아 끄는 것과 같은 모델이라 배울 게 없다. 그리고 **`before == after`가 되는 이동은 무시한다** — 자기 자신과의 비교로 붕괴하는 경로를 규칙 차원에서 없앤다.
- **로딩 전에는 날짜 라벨을 보여준다.** 섬네일이 도착하면 그 자리에 채워진다. 즉 **최악의 경우 스트립은 지금의 날짜 칩과 같고, 그보다 나빠질 수 없다.** (§7의 비용 결론이 여기에 걸린다.)
- **연도 경계에만 얇은 구분선 + 연도 라벨.**
- 타일 로드 실패는 44dp에 문구가 안 들어가므로 **작은 `!` + 탭 재시도**로 축약. 문구를 쓰는 건 큰 타일에서만(현행 `_PhotoTile` 유지).

**N이 아주 클 때(≥ 24)**: 스트립 양 끝에 `처음으로` / `최근으로` 점프를 붙인다. 200장이면 가로 9600dp라 처음까지 30번 스와이프해야 하는데, 프리셋(`처음↔최근`)과 이 점프가 그 경로를 1탭으로 만든다.
**월 단위로 솎아내는(thinning) 안은 기각한다.** 회원이 실제로 찍은 회차를 화면에서 숨기는 건 이 코드베이스가 일관되게 거부해 온 것이다 — `poseKeys`의 합집합 규칙 전체가 "이미 찍은 사진은 계속 보여야 한다"는 한 문장 위에 서 있다. 세로가 아까워서 사진을 숨기면 안 된다. 가로는 무한하다.

## 4. 정보구조 요약 — 무엇을 보여줄 것인가

사진이 쌓였을 때 이 탭이 보여줘야 하는 것을 우선순위로 못박으면:

| 순위 | 보여줄 것 | 어디에 | 왜 |
|---|---|---|---|
| 1 | **처음과 최근, 그 사이 기간** | 쌍 라벨 + 두 타일 캡션 | 회원의 질문("변했나")에 대한 직접적인 답 |
| 2 | **비교 중인 두 장** | 130dp 타일 2개 | 답의 실물 |
| 3 | **지금 어느 포즈인가 / 다른 포즈엔 몇 장 있나** | 포즈 행 + 헤더 배지 | 같은 포즈끼리만 비교가 성립한다는 규칙을 화면이 대신 설명 |
| 4 | **전체가 몇 회차이고 지금 어느 구간을 보고 있나** | 필름스트립 + 구간 밑줄 | 타임라인의 본체. 점이 아니라 구간 |
| 5 | 다른 쌍으로 가는 지름길 | 프리셋 칩 | 탐색 비용을 1탭으로 |
| 6 | 규칙 각주 | note | 폴드 아래로 보내도 되는 유일한 것 |

**보여주지 말아야 할 것**: 사진 장수에 비례해 자라는 어떤 것도 폴드 위에 두지 않는다. 지금 날짜 칩 `Wrap`이 정확히 그 위반이다.

## 5. 빈 상태 · 준빈 상태 — 확정 문구

**목소리 규약**: `{사실} — {다음 행동}`, 해요체, 느낌표 없음. 같은 탭의 기존 문구와 동형(`'아직 인바디 기록이 없어요 — 위 "기록 추가"로 결과지 숫자를 남겨보세요'`).

> ### ⚠️ 먼저 — 현행 문구에 남아 있는 세 번째 거짓 주장
> 현행 두 곳이 **"촬영 탭에서"**라고 말한다(`body_photo_timeline.dart:122,123`). **촬영은 탭이 아니다.** `app_shell.dart:8-12`가 명시한다: *"바텀 내비 셸 — 탭 4개(홈·예약·기록·마이) + 가운데 촬영 버튼. 촬영은 탭이 아니다(P21)."*
> 회원은 존재하지 않는 다섯 번째 탭을 찾게 된다. 아래 문구는 전부 **"가운데 촬영 버튼"**으로 고쳐 쓴다. 이게 죽은 슬라이더·"자동 비교"·"코치가 그리드 눈금으로"에 이어 이 위젯에서 나온 네 번째 사실 불일치다.

### E0 · 앨범 전체 0장

```
아직 촬영한 사진이 없어요 — 가운데 촬영 버튼으로 첫 사진을 남겨보세요
```
현행 대비 변경: `촬영 탭에서` → `가운데 촬영 버튼으로`.
포즈 행은 이때도 그린다(0장 포즈들이 흐리게) — 무엇을 찍게 되는지 미리 보여주는 게 이 화면의 유일한 잔여 가치다.

### E1 · 선택 포즈 1장 (다음 촬영에 이 포즈가 **있음**)

```
비교하려면 사진이 2장 이상 필요해요 — 다음 촬영 때 이 사진과 나란히 놓고 비교해요
```
현행(`…다음 촬영 후 전/후를 나란히 볼 수 있어요`)과 거의 같지만 **"이 사진과"**를 넣는다. 화면에 보이는 그 한 장이 버려지는 게 아니라 **기준점으로 적립됐다**는 뜻이 되어야 한다. 6개월 뒤 이 한 장이 §2의 "처음"이 된다.
쌍 라벨 자리에는: `1회차 · 8/27` (회차 표기를 여기서부터 일관되게 시작한다).

### E2 · 선택 포즈만 0장, 다른 포즈엔 사진 있음

```
{포즈} 사진은 아직 없어요 — 위에서 {최다포즈}({n}장)를 보거나, 가운데 촬영 버튼으로 남겨보세요
```
예: `전굴 사진은 아직 없어요 — 위에서 차렷(6장)을 보거나, 가운데 촬영 버튼으로 남겨보세요`
현행은 "위에서 다른 포즈를 고르거나"였다. **어느 포즈에 몇 장 있는지 이름을 대면** 회원이 포즈 행을 훑어볼 필요가 없다.

### E3 · 총 2장인데 포즈가 달라 비교 불가 ★ 지금 가장 잘못 안내되는 상태

`defaultPose`가 동수라 `poseKeys` 순서상 앞선 포즈(1장)를 고르고, 화면은 E1 문구를 낸다. 그런데 바로 위 포즈 행에는 **`차렷 1장` `T자 1장`**이 보인다. 회원이 읽는 것: *"2장 찍었는데 왜 2장 이상 필요하대?"* — 화면이 스스로와 모순된다.

```
같은 포즈가 2장 모여야 비교할 수 있어요
지금은 차렷 1장 · T자 1장이에요 — 둘 중 하나를 한 번 더 찍어보세요
```
(두 줄. 첫 줄이 규칙, 둘째 줄이 현재 상태 + 행동.)
**판정 조건**: `album.totalCount >= 2 && album.byPose.values.every((l) => l.length < 2)`. 이게 참일 때만 이 문구를 쓰고, 아니면 E1으로 떨어진다.

### E4 · 트레이너가 포즈를 바꿔서 **옛 포즈에만** 사진이 있음 ★ 현행이 지킬 수 없는 약속을 하는 상태

`poseKeys`의 잔여 key(`records_models.dart:166`) — 시퀀스에서 빠졌지만 사진이 남은 포즈. 이 앨범은 **영원히 늘지 않는다.** 다음 촬영이 이 포즈를 찍지 않기 때문이다.

**포즈 칩에 표식**: `옆구리 4장 · 지난 포즈`

**E4-a · 잔여 포즈에 2장 이상 (비교는 됨)**
```
지금 촬영 순서에는 없는 포즈예요 — 찍어둔 4장은 계속 볼 수 있지만 새로 추가되지는 않아요
```

**E4-b · 잔여 포즈에 1장 (비교 불가)** — 여기서 현행 E1 문구를 쓰면 **거짓말이 된다.** `"다음 촬영 때 이 사진과 나란히 놓고 비교해요"의 그 다음 촬영은 영원히 오지 않는다.**
```
사진이 1장뿐이라 비교할 수 없어요 — 지금 촬영 순서에 없는 포즈라 새로 추가되지도 않아요
위에서 차렷(6장)을 보시겠어요?
```

**E4-c · 앨범 전체가 잔여 포즈뿐** (대표가 시퀀스를 통째로 갈아엎음)
```
촬영 순서가 바뀌었어요 — 예전에 찍은 사진은 그대로 볼 수 있어요
새 순서로 한 번 더 찍으면 그때부터 비교가 다시 쌓여요
```
이 경우 **기본 선택 포즈는 잔여 포즈로 떨어질 수밖에 없다**(현재 시퀀스가 전부 0장) — §2.3의 예외 규칙이 여기서 발동한다.

**라벨이 raw key로 새는 경우**: `labelFor`는 시퀀스 → `legacyLabels` → **raw key**로 폴백한다(`bodycheck_models.dart:40`). 커스텀 포즈가 삭제되면 회원 화면에 `left_flank_v2` 같은 슬러그가 그대로 뜬다. **고치지 않는다** — 코드 주석의 판단이 옳다("모르면 모르는 대로 보여주는 편이 정직하고, 사진이 사라지지도 않는다"). 대신 옆의 `지난 포즈` 표식이 "이건 지금 쓰지 않는 옛 이름"이라는 맥락을 준다. 이건 §8의 서버 작업(라벨 스냅샷)으로만 근본 해결된다.

### E5 · 조회 실패 — 현행 유지

```
사진을 불러오지 못했어요 — 아래로 당겨 새로고침해주세요
```
정확하다. `RefreshIndicator`가 실제로 붙어 있다(`records_screen.dart:54`). 실패 시 포즈 칩을 숨기는 현행 판단도 유지 — 전부 "0장"으로 보여 사진이 없는 것처럼 읽힌다는 근거가 맞다.

### E6 · 개별 타일 실패 — 현행 유지 + 스트립용 축약

큰 타일: 현행 `_PhotoTile`의 실패 메시지 + `다시 시도` 유지.
스트립 타일(44dp): 문구가 안 들어가므로 **`!` 아이콘 + 탭 재시도**. 라벨(날짜)은 유지 — 어느 회차가 실패했는지는 알아야 한다.

### E7 · 새 문구가 하는 주장과 근거 (거짓 주장 방지 체크리스트)

| 문구가 주장하는 것 | 근거 | 판정 |

## 7. 타일당 비용 — 필름스트립 20장의 실제 값

### 7.1 메타데이터는 공짜다

`GET /v1/body-photos?member=`는 페이지네이션도 기간 필터도 없이 전량을 준다(`handlers_media.go:10`). 한 건은 `id · member_id · pose · direction · date · storage_path · blurred` 정도라 **~200바이트**.

| N_전체 | JSON 크기 | 판정 |
|---|---|---|
| 20 | ≈ 4KB | 무시 가능 |
| 200 | ≈ 40KB | 무시 가능 |
| 288 (8포즈 × 월1회 × 3년) | ≈ 60KB | 무시 가능 |

**목록 API에 페이지네이션이 필요하다는 결론은 나오지 않는다.** 병목은 여기가 아니다. (다만 `ListBodyPhotos`가 매 호출마다 **센터 전체** 스윕을 도는 건 별개 문제 — §8.3.)

### 7.2 바이트가 전부다

사진 한 장의 실제 크기를 정하는 것들:
- 카메라 `ResolutionPreset.veryHigh`(1080p급) — `body_camera_provider.dart:81`
- **압축·리사이즈 없음.** `body_photo_uploader.dart:40`은 10MB **이상을 거부**할 뿐 줄이지 않는다. `takePicture()` 원본 JPEG이 그대로 올라간다.
- 하드 상한 **10MB**(`maxUploadBytes`, Storage 규칙과 동값).

현실적 추정 **장당 ≈ 1.2MB**(1080p JPEG 중간값). 아래 계산은 이 값 기준이고, 기기에 따라 2~4배까지 오를 수 있다.

**그리고 캐시가 없다.** 업로드가 `cacheControl: 'private, max-age=0, no-store'`를 박고(`body_photo_uploader.dart:53`), 읽기는 `getDownloadURL`이 아니라 `getData`다(P8 민감정보 규약 — 규칙을 매번 통과시켜야 하므로 이 선택은 옳고 바꿀 수 없다). 결과: **CDN 캐시 0, 디스크 캐시 0.** 유일한 캐시는 프로세스 안의 `static Map`이라 **앱을 껐다 켜면 전부 다시 받는다.**

### 7.3 20장 즉시 표시의 비용

| 비용 항목 | 계산 | 값 |
|---|---|---|
| **네트워크** | 20 × 1.2MB | **≈ 24MB** — 앱 실행마다 반복 (HTTP 캐시 없음) |
| 체감 시간 | 24MB @ 10Mbps LTE | **≈ 20초** |
| **로더 캐시 RAM** | 같은 24MB가 `_cache`에 상주, 축출 없음 | **≈ 24MB, 영구** |
| **디코드 RAM (현행 `cacheWidth: 720`)** | 720×960×4B = 2.76MB × 20 | **≈ 55MB** — Flutter `ImageCache` 기본 상한 100MB라 **축출도 안 된다** |
| **합계** | | **≈ 80MB 추가** |

320dp급 기기는 대개 RAM이 넉넉하지 않다. 80MB는 프레임 드랍이 아니라 **OOM 등급의 문제**다.

**두 비용을 분리해서 판정한다.**

**(A) 디코드 비용 — 클라이언트에서 해결된다. 공짜.**
현행 `cacheWidth: 720`은 130dp 큰 타일에 맞춘 값이다. 44dp 스트립 타일에는 `44 × devicePixelRatio(≈3) ≈ **132px**`면 충분하다.
`132×176×4B ≈ **93KB**` → 20장 = **1.9MB**. 55MB → 1.9MB, **29배 감소**. 코드 한 줄이다.

**(B) 전송 비용 — 클라이언트에서 해결되지 않는다.**
`getData`는 부분 다운로드가 없다. 132px로 그리려고 해도 **1.2MB 전체를 받아야 한다.** 이건 클라이언트가 이길 수 없는 항목이다.

**그래서 지연(lazy) 로드가 타협이 아니라 유일한 답이다.**
가로 `ListView.builder`는 화면에 보이는 것만 만든다. 266dp에 48dp 타일이면 **동시 6장 = ≈7.2MB**가 첫 진입 비용이고, 그 이상은 **회원이 스크롤한 만큼만** 는다. 20장을 다 보려고 끝까지 스크롤하면 결국 24MB지만, 그건 **회원이 요청한 24MB**다. 탭을 열었다는 이유만으로 청구되는 24MB와는 다른 성질이다.

**정직한 판정:**
> **지연 로드 필름스트립은 서버 작업 없이 지금 만들 수 있다.** 첫 진입 ≈7MB(장당 1.2MB 가정)이고, 나머지는 회원 조작에 따라 든다.
> **즉시 로드 20장 스트립, 그리드 뷰, "전체 보기"는 서버 작업 없이는 만들면 안 된다.** §8-1이 선행 조건이다.
> 그리고 지연 로드라도 **섬네일 하나당 1.2MB는 계속 든다.** 이건 절감이 아니라 **연기**다. 회원이 6개월간 스크롤을 반복하면 총량은 같다. §8-1이 이걸 80배 줄인다.

**첫 진입 7MB도 무조건 쓰지는 않는다.** 스트립은 **날짜 라벨을 먼저 그리고 섬네일을 나중에 채운다.** 즉 바이트가 도착하기 전의 스트립은 **지금의 날짜 칩과 동일한 화면**이다 — 스트립이 지금보다 나빠지는 경우가 원리적으로 없다.

### 7.4 부수적으로 발견한 것 (내 렌즈 밖이지만 스트립이 악화시킨다)

1. **`FirebaseBodyPhotoLoader._cache`는 무한이고 축출이 없다**(`body_photo_loader.dart:38`). 주석의 근거("경로에 촬영시각이 박혀 stale이 될 수 없다")는 **정합성**에 대한 것이지 **크기**에 대한 게 아니다. 지금은 동시 2장이라 안 터졌을 뿐이다. 스트립을 붙이면 이 맵이 그대로 커진다. → LRU 상한(예: 12개 / 24MB) 필요.
2. **`clearCache()`를 아무도 호출하지 않는다.** 주석은 "회원이 바뀌면 남의 사진이 캐시에 남아 있으면 안 된다"고 명시하는데, `lib/` 전체에 호출처가 0개다(선언 1줄뿐). **계정 전환 시 이전 회원의 P8 민감정보 바이트가 프로세스에 남는다.** 성능이 아니라 **개인정보 문제**이고, 스트립이 캐시 크기를 키우면 노출 표면도 같이 커진다.
3. 스트립(132px)과 큰 타일(720px)이 **같은 바이트를 두 해상도로 디코드**한다. 바이트는 `_cache` 덕에 한 번만 받지만 디코드된 비트맵은 두 벌이 된다. 의도적으로 감수하는 비용이라는 걸 코드에 남겨야 한다(선택 중인 2장에만 해당 = +5.5MB).

## 8. 서버 작업이 필요한 것

**이 절은 §3~6의 "지금 만들 수 있는 것"과 섞이지 않는다.** 아래 없이도 §3의 구조는 전부 성립한다.

### 8-1. 섬네일 파생본 — **필수 (그리드/즉시 로드를 하려면)**

| | 지금 | 섬네일 도입 후 |
|---|---|---|
| 스트립 20장 전송량 | ≈ 24MB | 20 × ≈15KB = **≈ 300KB** |
| 배수 | — | **≈ 80배 감소** |
| 즉시 로드 | 불가 | 가능 |
| 그리드(전체 보기) | 불가 | 가능 |

**설계 제약(전부 P8 규약에서 나온다):**
- 파생본은 **같은 민감정보다.** 반드시 같은 `storage.rules` 경로 규칙과 같은 동의 검사 아래 놓여야 한다. 규칙이 `match /members/{memberId}/body/{fileName}`으로 **세그먼트 4개**를 고정하므로(`body_photo_storage_path.dart:25`) `.../body/thumb/xxx.webp`는 **규칙 매칭에서 빗나가 전면 차단에 걸린다.** → 하위 폴더가 아니라 **같은 폴더의 파일명 접두어**여야 한다(예: `thumb-{원본파일명}.webp`), 혹은 규칙을 함께 고쳐야 한다. **이걸 놓치면 조용한 403이 난다.**
- 읽기는 **반드시 `getData`.** `getDownloadURL`의 무기한 토큰 URL은 규칙을 우회하므로 원본에서 배제한 근거가 섬네일에도 그대로 적용된다(`body_photo_loader.dart` 헤더 주석 · `storage.rules` 헤더 주석에서 이미 두 번 배제됐다).
- **삭제·파기에 반드시 동반돼야 한다.** `DeleteBodyPhoto`(회원 본인이면 즉시 완전 파기), `purgeBodyPhoto`, `PurgeBodyPhotos`가 전부 섬네일도 지워야 한다. **안 지우면 "지운 사진"이 섬네일로 살아남는다** — 배포된 개인정보처리방침의 "지체 없이 파기" 약속이 거짓이 되는 경로다. 이건 최적화가 아니라 **정확성 요구사항**이다.
- 문서에 `thumb_path` 필드 추가 + **nullable이어야 한다.** 기존 사진에는 파생본이 없고, `required`로 두면 파싱이 던져 기록 탭 3개가 통째로 죽는다(`InbodyRecord.source`가 같은 이유로 nullable인 전례가 `records_models.dart:92-97`에 남아 있다). 클라이언트는 `thumb_path ?? storage_path`로 폴백한다 — 옛 사진은 원본을 받고, 새 사진은 섬네일을 받는다. **백필 없이 점진 적용된다.**

**우선순위: §3의 구조를 먼저 배포하고, 스트립이 실제로 쓰이는지 확인한 뒤에 만든다.** 프로덕션 사진이 1장인 지금 섬네일 파이프라인을 먼저 세우는 건 순서가 거꾸로다. 지연 로드 스트립이 §7.3대로 성립하므로 v1이 이걸 기다릴 이유가 없다.

### 8-2. 포즈 라벨 스냅샷 — **선택**

사진 문서에 `pose_label`(촬영 시점 라벨)을 함께 저장하면, 대표가 커스텀 포즈를 지워도 회원 화면의 `left_flank_v2` 슬러그 노출(§5 E4)이 사라진다. 없어도 §3은 동작하고, 지금의 raw key 폴백은 "사진을 잃는 것보다 낫다"는 이미 내린 판단이라 급하지 않다.

### 8-3. 페이지네이션 — **필요 없다. 다만 다른 걸 하나 지적한다**

§7.1대로 메타데이터는 288건에서도 60KB라 병목이 아니다. **페이지네이션은 요청하지 않는다.**

대신 조회 경로에 실제 스케일 위험이 있다:

```go
// service.go:2755 — ListBodyPhotos 안
s.sweepBodyPhotoPurge(ctx, p.CenterID)   // 센터 전체 스윕
```

`GET /v1/body-photos` **매 호출마다 센터 전체**의 파기 대상을 훑는다. 이건 O(회원 사진 수)가 아니라 **O(센터 전체 사진 수)**다. 기록 탭을 열 때마다, 아래로 당길 때마다 돈다. 회원이 늘수록 이 조회가 느려지고, 그 비용은 **내 기능과 무관하게** 증가한다.
코드 주석이 이유를 밝히고 있다("스케줄러가 없어(Cloud Scheduler API 미활성) 조회 시점에 센터 전체를 훑는다") — 즉 **알려진 임시 조치**다. 필름스트립이 조회 횟수를 늘리지는 않으므로(목록은 여전히 탭 진입당 1회) 이 설계가 문제를 악화시키지는 않지만, "체형 타임라인을 키운다"는 대화에서 언급 없이 지나가면 안 되는 항목이라 여기에 남긴다. **해결은 Cloud Scheduler 활성화 + 스윕 분리**지 페이지네이션이 아니다.

## 10. 자문자답

**Q. 가로 스크롤은 "숨기는" 것 아닌가? `Wrap`은 최소한 다 보여준다.**
A. `Wrap`도 폴드 아래는 안 보인다 — 세로로 숨길 뿐이다. 차이는 **비용의 성격**이다. 세로로 숨기면 회원이 **사진을 보려고** 칩을 지나쳐 스크롤해야 한다(원치 않는 스크롤). 가로로 숨기면 **다른 포즈를 찾을 때만** 스크롤한다(원한 스크롤). 그리고 §1.2 #8에서 `Wrap`이 실제로 하는 일은 "다 보여주기"가 아니라 "사진을 2.6스크린 아래로 밀어내기"다.

**Q. 왜 그리드(격자)로 다 펼치지 않나? 사진첩의 표준인데.**
A. §7.3. 20장 즉시 로드가 24MB / 55MB 디코드다. 그리드는 화면당 12~15장이 동시에 보이므로 지연 로드의 이점도 대부분 잃는다. **§8-1 없이는 만들 수 없다.** 그리고 이 탭의 임무는 "사진첩"이 아니라 "비교"다 — 격자는 §2의 질문("변했나")에 답하지 않는다.

**Q. `_shortDate`에 연도를 넣으면 되는 것 아닌가? 구분선보다 간단한데.**
A. `2025/8/14`는 56dp → 84dp가 되어 **줄당 4개가 3개로 준다** — 세로가 33% 늘어난다. 연도는 스트립 전체에서 **경계 1~2곳에만** 필요한 정보인데, 매 항목에 붙이면 필요 없는 곳까지 값을 치른다. 구분선은 그 값이 0이다.

**Q. 두 팀(슬라이더 · 전체화면 뷰어)과 겹치는 곳은?**
A. 접점 두 개, 겹침 없음.
① 필름스트립이 고르는 **두 장의 정체**를 슬라이더 팀이 그대로 받는다. 계약은 `(before: BodyPhotoEntry, after: BodyPhotoEntry)`이고 **`before != after`는 이 문서가 보장한다**(§3.5 붕괴 가드). 슬라이더가 자기 자신 두 장을 받는 경우를 방어할 필요가 없어진다.
② 스트립 타일 탭은 **선택**이지 열기가 아니다. 전체화면 뷰어는 **큰 타일 탭**으로 들어간다 — 두 제스처가 다른 위젯에 있어 충돌하지 않는다.

**Q. 프로덕션이 1장인데 200장을 설계하는 게 과한가?**
A. 표 §1.2가 답한다. **8포즈 × 12자 라벨 파손(#7)은 사진 0장에서도 지금 당장 재현된다** — 대표가 어드민에서 포즈를 만들기만 하면 된다. 15개월 파손(#6)은 월 1회 촬영자에게 **확정된 미래**다. 그리고 §3의 수정은 "200장 대비"가 아니라 **자라는 축을 세로에서 가로로 돌리는 한 번의 결정**이라, 1장에서도 200장에서도 같은 코드다.

**Q. 새 사진을 자동으로 "최근"에 넣으면 회원의 선택을 덮어쓰는 것 아닌가?**
A. 그래서 조건을 건다 — **회원이 after를 명시적으로 고른 적이 없을 때만.** 고른 적이 있으면 그대로 두고, 대신 스트립에 새 타일이 나타나므로 회원이 알아챈다. 그리고 선택은 인덱스가 아니라 `storagePath`로 들고 있어야 목록이 늘어도 밀리지 않는다(§1.3 F의 근본 원인이 인덱스 보관이다).

**Q. 이 설계가 새로 만드는 거짓 주장은 없나?**
A. §5 E7이 문구별 근거표다. 검증에서 하나 걸렸다 — **"{n}회차"는 같은 날 같은 포즈를 재촬영하면 어긋난다.** 파일명 `epochMillis`가 덮어쓰기를 막으므로 같은 날 2장이 실제로 가능하다. 대응: 회차는 **날짜 단위로 세고**, 같은 날 여러 장은 같은 회차 안에 나란히 둔다. 세는 방식을 표기에 맞추는 게 아니라 표기를 사실에 맞춘다.
