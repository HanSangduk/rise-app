## 2. 마크 옮겨 적기 — `CustomPainter` 전사

### 2-1. SVG 명령 전수 대조 (원본 파일과 1:1 확인)

`design/brand/rise-mark.svg:21-27`을 명령 단위로 전부 셌다.

| 경로 | SVG 원문 | 명령 | Dart |
|---|---|---|---|
| 큰 아치 `:21-23` | `M` ×1, `C` ×6 | 7 | `moveTo` ×1 + `cubicTo` ×6 |
| R 다리 `:24` | `M` ×1, `C` ×2 | 3 | `moveTo` ×1 + `cubicTo` ×2 |
| 안쪽 r 획 `:25` | `M` ×1, **`L` ×2, `Q` ×2** | 5 | `moveTo` + `lineTo` ×2 + `quadraticBezierTo` ×2 |
| 베이지 점 `:27` | `<circle>` | 1 | `drawCircle` |

> **주의 — 흔한 오독.** 세 번째 경로는 `L` 하나 + `Q` 하나가 **아니라** `L`·`Q`·`L`·`Q` 넷이다. 원문:
> ```
> M 159.5,290  L 159.5,214  Q 159.5,195.5 178,195.5  L 190,195.5  Q 197,196 201,198.5
> ```
> 첫 `L`은 세로 기둥(290→214), 두 번째 `L`은 위쪽 가로 획(178→190)이다. 하나로 줄이면 r의 어깨가 사라진다.
> 현재 `rise_mark.dart:55-59`는 **넷 다 옳게 옮겨져 있다.**

**절대/상대 좌표 검증.** 원본은 `M`·`C`·`L`·`Q` 전부 **대문자 = 절대 좌표**다. Flutter의 `cubicTo(x1,y1,x2,y2,x3,y3)` / `quadraticBezierTo(x1,y1,x2,y2)` / `lineTo(x,y)`도 전부 절대 좌표를 받는다(`sky_engine/lib/ui/painting.dart:3252-3291`). **따라서 누적 계산이 필요한 자리가 한 곳도 없고, 숫자를 그대로 옮기면 된다.** 만약 원본이 소문자였다면 각 명령의 시작점을 누적해야 했다 — 이건 우연히 쉬운 것이지 항상 쉬운 게 아니다.

`Q`의 인자 순서도 확인했다: SVG `Q cx,cy x,y`(제어점 먼저, 끝점 나중) = Flutter `quadraticBezierTo(x1,y1, x2,y2)`(제어점 먼저). **순서 동일.**

### 2-2. 좌표 변환 — 지금 코드가 맞다 (증명)

`rise_mark.dart:67-77`:

```dart
canvas.translate(centeringX, centeringY);   // T1
canvas.scale(scale);                        // S
canvas.translate(-viewBoxLeft, -viewBoxTop); // T2
```

캔버스 변환은 **왼쪽부터 누적**되므로 합성 행렬은 `T1 · S · T2`이고, 점 `p`는

```
p ↦ T1 + S·(p − (112, 106))
```

로 간다. viewBox 원점이 원점으로 이동한 뒤 스케일되고, 그다음 박스 중앙에 놓인다 — **정확하다.** 순서를 바꾸면(예: `translate(-left,-top)`을 `scale` 앞에 두면) 이동량이 스케일되지 않아 마크가 박스 밖으로 나간다. 지금 순서가 유일하게 맞는 순서다.

**부수 효과 하나가 중요하다**: `canvas.scale(s)` 뒤에 그리는 `strokeWidth = 21.5`는 **viewBox 단위**로 해석되어 화면에서 `21.5 × s` dp가 된다. 이게 의도한 동작이다 — 마크가 커지면 획도 같은 비율로 굵어져야 브랜드가 유지된다. 스트로크는 CTM을 반영해 디바이스 공간에서 테셀레이션되므로 **어떤 크기에서도 선명하다.** 별도 보정이 필요 없다.

### 2-3. `Path`를 매 프레임 다시 만들고 있다 (D7)

```dart
// rise_mark.dart:95-96 — 현재
canvas.drawPath(
  RiseMarkGeometry.strokePaths(),   // ← paint()가 불릴 때마다 새 Path
```

`paint()`는 애니메이션 중 프레임마다 불린다. 매번 네이티브 `Path` 객체를 새로 할당하고 12개 명령을 다시 밀어 넣는다. 할당 자체는 싸지만 **엔진의 경로 테셀레이션 캐시가 경로 객체를 키로 쓴다** — 매 프레임 새 객체면 캐시 히트가 구조적으로 0이다.

고정: 지연 초기화되는 `static final`로 한 번만 만든다.

```dart
static final Path strokes = _buildStrokes();   // Dart의 static final은 지연 초기화
static Path _buildStrokes() { ... }            // 기존 strokePaths() 본문 그대로
```

`Path`는 가변 객체이므로 **누구도 여기에 `addPath`/`reset`을 하지 않는다**는 규약이 필요하다. 페인터는 읽기만 한다.

### 2-4. `strokeJoin` — SVG 기본값과 다르다 (D9)

`rise-mark.svg:20`은 `stroke-linecap="round"`만 지정하고 **`stroke-linejoin`은 지정하지 않는다.** SVG 기본값은 `miter`이고, Flutter `Paint.strokeJoin`의 기본값도 `miter`다. 그런데 `rise_mark.dart:102`가 `StrokeJoin.round`를 **명시적으로 설정**한다.

주석의 근거("획은 이어진 곡선이라 join도 둥글어야 캡과 실루엣이 맞는다")는 **틀렸다.** cap과 join은 독립적인 속성이고, 서로 "맞출" 대상이 아니다.

**실제로는 아무 차이도 없다.** 모든 접합부의 접선 꺾임각을 계산했다:

| 접합부 | 꺾임각 |
|---|---|
| 아치 `(182,121)` | **0.00°** (완전 G1 연속) |
| 아치 `(210,122)` | 1.23° |
| 아치 `(257,155)` | 1.36° |
| 아치 `(262,196)` | 1.16° |
| 아치 `(240,238)` | 4.40° ← 최대 |
| 다리 `(232,280)` | **0.00°** |

최대 4.4°다. miter limit 기본값 4는 약 29° 이하에서 발동하지도 않는다. **miter든 round든 렌더 결과가 동일하다.**

그래서 이건 성능 문제도 외관 문제도 아니고 **원칙 문제**다: 원본에 없는 속성을 임의로 추가하면, 나중에 마크가 바뀌어 실제 꺾임이 생겼을 때 SVG와 Dart가 조용히 갈라진다. **`strokeJoin` 줄을 지운다**(Flutter 기본값 = SVG 기본값 = miter).

### 2-6. 크기 상수 — `size`가 폭인 것이 함정이다

```dart
// rise_mark.dart:142-144 — 현재
SizedBox(width: size, height: size * viewBoxHeight / viewBoxWidth)
```

`RiseMark(size: 132)`(`splash_gate.dart:127`)는 **폭 132 dp · 높이 136.04 dp**를 만든다. 스케일 계수는 `132/196 = 136.04/202 = 0.67347 dp/단위`.

문제: §3의 교정 절차에서 실기기 스크린샷으로 재는 값은 **높이 또는 지름**이지 폭이 아니다. 안드로이드 12의 제약도 정사각 캔버스(960 px) 위에 정의된다. `size`가 폭이라는 사실이 문서 어디에도 안 적혀 있고, 파라미터 이름이 그걸 숨긴다.

**권고**: `RiseMark({required double boxHeight})`로 바꾸고 `width = boxHeight * 196 / 202`로 계산한다. 기본값은 **136.0**(오늘 렌더되는 크기 그대로) — 교정 전까지 픽셀이 변하지 않는다.

이 문서의 모든 지각 계산은 **박스 높이 136.04 dp · 0.67347 dp/단위**를 기준으로 한다. 이 값이 교정으로 바뀌면 §5의 진폭도 함께 재계산해야 한다(§8-1).

### 2-7. Dart — 확정본

```dart
abstract final class RiseMarkGeometry {
  // 원본: design/brand/rise-mark.svg. 좌표를 고칠 때는 SVG와 icons.html도 함께.
  static const viewBoxLeft = 112.0;
  static const viewBoxTop = 106.0;
  static const viewBoxWidth = 196.0;
  static const viewBoxHeight = 202.0;

  static const strokeWidth = 21.5;          // svg:20
  static const navy  = Color(0xFF3B4C60);   // svg:20
  static const beige = Color(0xFFCEBBAA);   // svg:27
  static const cream = Color(0xFFF6F4EF);   // svg에 없음 — 배경은 쓰는 쪽이 깐다

  static const dotCenter = Offset(287, 284.5);  // svg:27
  static const dotRadius = 17.0;                // svg:27

  /// 획 3개가 **하나의 Path**다. 3개로 쪼개지 말 것 — §7-3.
  /// 지연 초기화되므로 첫 접근 때 한 번만 만들어진다. 절대 변형하지 말 것.
  static final Path strokes = _buildStrokes();

  static Path _buildStrokes() {
    final p = Path();

    // 큰 열린 아치 — svg:21-23 · M + C×6 (전부 절대 좌표)
    p.moveTo(127, 164);
    p.cubicTo(137, 143, 158, 124, 182, 121);
    p.cubicTo(190, 120, 202, 120, 210, 122);
    p.cubicTo(232, 127, 249, 138, 257, 155);
    p.cubicTo(263, 167, 265, 180, 262, 196);
    p.cubicTo(259, 214, 251, 228, 240, 238);
    p.cubicTo(231, 245, 221, 249, 206, 249);

    // R의 다리 — svg:24 · M + C×2
    p.moveTo(208, 252);
    p.cubicTo(217, 263, 224, 272, 232, 280);
    p.cubicTo(240, 288, 245, 291, 250, 293);

    // 안쪽 r형 획 — svg:25 · M + L + Q + L + Q  (L도 Q도 각각 두 번이다)
    p.moveTo(159.5, 290);
    p.lineTo(159.5, 214);
    p.quadraticBezierTo(159.5, 195.5, 178, 195.5);
    p.lineTo(190, 195.5);
    p.quadraticBezierTo(197, 196, 201, 198.5);

    return p;
  }

  /// viewBox 좌표계를 [size] 안에 비율을 지켜 앉힌다. 합성 = T1·S·T2 (§2-2).
  static void applyTransform(Canvas canvas, Size size) {
    final scale = math.min(size.width / viewBoxWidth, size.height / viewBoxHeight);
    canvas.translate(
      (size.width  - viewBoxWidth  * scale) / 2,
      (size.height - viewBoxHeight * scale) / 2,
    );
    canvas.scale(scale);
    canvas.translate(-viewBoxLeft, -viewBoxTop);
  }
}

/// 네이비 획만. **애니메이션 입력이 alpha 하나뿐**이라 등장·대기 내내 재페인트가 0이다.
class RiseStrokesPainter extends CustomPainter {
  RiseStrokesPainter({required this.alpha}) : super(repaint: alpha);

  final Animation<double> alpha;   // 퇴장에서만 1→0

  @override
  void paint(Canvas canvas, Size size) {
    final a = alpha.value;
    if (a <= 0) return;
    canvas.save();
    RiseMarkGeometry.applyTransform(canvas, size);
    canvas.drawPath(
      RiseMarkGeometry.strokes,
      Paint()
        ..style = PaintingStyle.stroke
        ..strokeWidth = RiseMarkGeometry.strokeWidth
        ..strokeCap = StrokeCap.round
        // strokeJoin은 설정하지 않는다 — SVG 기본값도 Flutter 기본값도 miter. §2-4
        ..isAntiAlias = true
        ..color = RiseMarkGeometry.navy.withValues(alpha: a),
    );
    canvas.restore();
  }

  // repaint 리스너가 갱신을 건다. 페인터 인스턴스는 수명 내내 하나다.
  @override
  bool shouldRepaint(RiseStrokesPainter old) => false;
}

/// 베이지 점만. 등장 구간에서 프레임마다 다시 그려지지만 drawCircle 한 번이다.
class RiseDotPainter extends CustomPainter {
  RiseDotPainter({required this.opacity, required this.radiusFactor})
      : super(repaint: Listenable.merge([opacity, radiusFactor]));

  final Animation<double> opacity;
  final Animation<double> radiusFactor;

  @override
  void paint(Canvas canvas, Size size) {
    final o = opacity.value;
    if (o <= 0) return;
    canvas.save();
    RiseMarkGeometry.applyTransform(canvas, size);
    canvas.drawCircle(
      RiseMarkGeometry.dotCenter,                          // 절대 움직이지 않는다
      RiseMarkGeometry.dotRadius * radiusFactor.value,     // 0.86 → 1.00
      Paint()
        ..isAntiAlias = true
        ..color = RiseMarkGeometry.beige.withValues(alpha: o),
    );
    canvas.restore();
  }

  @override
  bool shouldRepaint(RiseDotPainter old) => false;
}
```

`withOpacity`가 아니라 `withValues(alpha:)`인 이유: `withOpacity`는 Flutter 3.44에서 **deprecated**다(`sky_engine/lib/ui/painting.dart:344` — "Use .withValues() to avoid precision loss"). 현재 코드(`rise_mark.dart:104`)도 이미 `withValues`를 쓴다.

## 3. 네이티브 PNG와의 정합 — **이 문서에서 제일 위험한 항목** (D1)

모션 문서 §3-3이 "픽셀 매칭이 1순위"라고 썼지만, **정확히 어떻게 어긋나는지**는 계산하지 않았다. 계산해 보면 함정이 하나 있고 그 크기가 크다.

### 3-1. 함정

네이티브 스플래시는 **점 없는 마크**를 보여준다(모션 §3-1). 그래서 PNG를 만들려면 `rise-mark.svg`에서 `<circle>`을 뺀 변형이 필요하다. 그런데 **점은 마크의 오른쪽 끝이다** — viewBox 오른쪽 경계 308을 정하는 게 점(최대 x = 304)이지 획(최대 x = 274.128)이 아니다.

따라서 점을 빼면 **잉크의 bbox가 실제로 줄어든다**:

| | 폭 | 높이 | 잉크 중심 x |
|---|---|---|---|
| 전체 (Flutter가 그리는 것) | **187.750** | 194.157 | 210.125 |
| 네이비만 (점 제거) | **157.878** | 194.157 | 195.189 |

**여기서 어떤 도구든 "잉크에 맞춰 다시 fit"을 하면 끝난다.** `design/brand/README.md:29-33`의 재생성 파이프라인은 `icons.html`을 headless Chrome으로 렌더하는 것이고, 그 파일은 "색·배치 파라미터가 달라 분리했다"고 명시돼 있다 — **즉 자체 배치 로직을 갖고 있다.** SVG 최적화기(`svgo` 등)도 기본 설정에서 viewBox를 다시 계산한다.

**재fit 했을 때의 어긋남:**

| 증상 | 크기 | 조건 |
|---|---|---|
| **수평 점프** | 210 − 195.189 = **14.81 단위 = 9.97 dp** (0.67347 dp/단위) | **어떤 fit 규칙에서도 발생한다** |
| 수직 점프 | **0** | 점의 y 범위 `[267.5, 301.5]`가 네이비의 y 범위 `[109.593, 303.750]` 안에 완전히 들어가서, 점을 빼도 세로 bbox가 안 변한다 |
| 크기 차 | **0 ~ 7.9 %** | 높이 기준 fit이면 0 %(세로 bbox 불변), 대각선을 안전원에 맞추는 fit이면 270.09 → 250.24 = **1.079배** |

**수평 점프 약 10 dp는 조건 없이 일어난다.** 3배 기기에서 30 물리픽셀이다. 이건 "미세한 어긋남"이 아니라 **명백한 글리치**이고, 이음매를 감추려고 만든 설계가 이음매를 폭발시킨다. 크기 차는 도구의 fit 규칙에 달렸지만, 점프만으로 이미 충분히 나쁘다.

### 3-2. 규칙

> **점 없는 PNG는 `viewBox="112 106 196 202"`를 그대로 유지한 채 `<circle>` 요소 하나만 지워서 렌더한다.** viewBox를 다시 계산하는 어떤 도구도 이 경로에 넣지 않는다.

### 3-3. 정확한 출력 사양

안드로이드 12 스플래시(아이콘 배경 없음)는 **288 dp 캔버스 / 안쪽 192 dp 원**이고, `flutter_native_splash`의 `android_12.image`는 **960×960 px, 안전원 지름 640 px**다. 즉 `1 px = 0.3 dp`.

Flutter 쪽 박스 높이 136.04 dp에 맞추려면:

| 항목 | 값 |
|---|---|
| viewBox 높이(202 단위) → | **453.5 px** (= 136.04 / 0.3) |
| viewBox 폭(196 단위) → | **440.0 px** |
| 스케일 | 2.2449 px/단위 |
| 캔버스 | 960 × 960, 위 440.0 × 453.5 영역을 **정중앙에** (검산: viewBox 중심 `(210,207)` → 캔버스 `(480.0, 480.0)`) |
| 안전원 검증 | 캔버스 중심에서 네이비 잉크까지 **최대 242.2 px** ≤ 반경 320 px ✅ **24.3 % 여유** |

> 안전원 검증에 대각선이 아니라 **최대 반경**을 쓴다. viewBox 전체를 유지하면 네이비 잉크는 캔버스 중앙이 아니라 **왼쪽으로 치우쳐** 앉으므로(오른쪽이 점 자리), 중심 기준 반경이 실제 제약이다.

iOS `LaunchImage`도 같은 규칙: viewBox 전체를 높이 136.04 dp로 렌더하고 `ios_content_mode: center`.

### 3-4. 검수 — 눈대중 금지

1. 생성된 PNG를 열어 **캔버스 대비 네이비 잉크의 좌우 여백이 비대칭인지** 본다. 대칭이면 재fit된 것이다(전체 viewBox를 유지하면 잉크는 **왼쪽으로 치우쳐** 있어야 한다 — 오른쪽에 점 자리가 비어 있으므로).
   - 960 캔버스 기준 기대값: 좌 여백 **269.5 px**, 우 여백 **336.0 px**. 이 차이 **66.5 px**가 "점 자리"다. 좌우가 같으면 재fit된 것이다.
2. 안드로이드 12+ 실기기에서 ① 시스템 스플래시 → ③ Flutter 첫 프레임을 60fps 화면 녹화 후 **프레임 단위 재생**.
3. 이 검증을 통과하기 전에는 §4의 모션 튜닝을 시작하지 않는다.

## 4. 커브와 타이밍

### 4-1. 컨트롤러는 **둘**이다 (현재는 하나)

현재 구현은 컨트롤러 1개(`dotIn + fadeOut = 540ms`)를 `Interval`로 나눠 쓴다. 그래서 등장과 퇴장이 **하나의 재생 시간축에 직렬로 묶여 있고**, 그게 D2(죽은 시간 540ms)의 구조적 원인이다. 등장은 *기다리는 동안* 일어나야 하고 퇴장은 *준비된 순간* 시작해야 하는데, 하나의 컨트롤러로는 두 시작점을 가질 수 없다.

| 컨트롤러 | 길이 | 시작 시점 |
|---|---|---|
| `_arrive` | **350 ms** | 첫 프레임 다음 `addPostFrameCallback` (커밋 체크 통과 시) |
| `_leave` | **280 ms** | `ready`가 뜬 뒤 한 프레임 넘긴 시점 |

두 개를 쓰면 §4-5의 조정 규칙이 자연스럽게 표현되고, "등장이 끝났든 말든 준비되면 나간다"가 상태 기계가 아니라 그냥 두 컨트롤러의 독립성으로 해결된다. 티커 2개의 비용은 무시할 수 있다.

**`_settle`이 정확히 1.000으로 돌아오도록 설계한 것**(§4-2)이 여기에 기여한다 — 퇴장의 시작 스케일을 실행 시점에 읽어 올 필요 없이 `begin: 1.0`으로 하드코딩할 수 있다. 모션 문서의 원안(호흡이 1.014에서 끝나고 퇴장이 거기서 이어받음)은 두 컨트롤러를 값으로 연결해야 해서 압축·중단 시 계단이 생긴다.

### 4-2. 타임라인 — 확정

`t = 0`은 **Flutter 첫 프레임**이다. 정지 구간(0~90ms)은 `_arrive` 안의 `Interval` 하한으로 표현한다.

#### `_arrive` (350 ms)

| 대상 | from → to | 창 (ms) | `Interval` | `Curve` |
|---|---|---|---|---|
| 점 **불투명도** | 0 → 1 | 90 → 250 | `Interval(90/350, 250/350)` = `(0.2571, 0.7143)` | `Curves.easeOutSine` |
| 점 **반지름 계수** | **0.86 → 1.00** | 90 → 350 | `Interval(0.2571, 1.0)` | `Curves.easeOutCubic` |
| 마크 **scale** (settle) | 1.000 → **1.022** → 1.000 | 90 → 350 | `Interval(0.2571, 1.0)` + `TweenSequence` 110 : 150 | `easeOutCubic` / `easeInOutSine` |

#### `_leave` (280 ms)

| 대상 | from → to | 창 (ms) | `Interval` | `Curve` |
|---|---|---|---|---|
| 마크 **불투명도** | 1 → 0 | 0 → 180 | `Interval(0, 180/280)` = `(0, 0.6429)` | `Curves.easeInCubic` |
| 마크 **scale** | 1.000 → 1.048 | 0 → 280 | — | `Curves.easeInCubic` |
| 크림 **알파** | 1 → 0 | 0 → 280 | — | `Curves.easeInOutCubic` |
| 앱 콘텐츠 **scale** | 0.985 → 1.000 | 0 → 280 | — | `Curves.easeOutCubic` |
| 앱 콘텐츠 **불투명도** | — | — | — | **없음. §7-5** |

**Flutter 쪽 최대 노출 = 350 + 280 = 630 ms**, 그중 **죽은 시간은 280 ms**(퇴장뿐)다. 현재 구현은 540 ms 전부가 죽은 시간이다.

#### 앱 콘텐츠 불투명도를 뺀 이유 (모션 문서 §4-1에서 변경)

원안은 크림 알파 1→0과 앱 콘텐츠 불투명도 0→1을 **동시에** 건다. 그러면 중간 프레임에서 앱 콘텐츠가 70 % 불투명일 때 그 **아래에 아무것도 없다** — 게이트의 크림은 앱 위에 있으므로, 반투명 앱은 윈도 배경(안드로이드 다크 = 검정)과 합성된다. 결과는 탁한 어두운 틴트다.

크림 알파가 이미 크로스페이드를 만든다. 앱 콘텐츠는 **불투명하게 두고 스케일만** 준다. 레이어 하나가 통째로 사라지고(§7-5) 함정도 사라진다.

### 4-3. 커브를 그 이름으로 고른 이유

Flutter 3.44 SDK에서 실제 정의를 확인했다(`animation/curves.dart`).

| 커브 | 정의 | 시작 기울기 | 끝 기울기 | 쓰는 곳 · 이유 |
|---|---|---|---|---|
| `easeOutSine` | `Cubic(0.39, 0.575, 0.565, 1.0)` :1640 | 1.47 | 0 | **점 불투명도.** 계열 중 가장 얕다 — 첫 2프레임에 "번쩍" 켜지지 않는다 |
| `easeOutCubic` | `Cubic(0.215, 0.61, 0.355, 1.0)` :1664 | **2.84** | 0 | **점 반지름 · settle 상승 · 앱 콘텐츠.** 앞이 빠르고 끝이 완전히 멎는다 — 오버슈트 없이 "도착" |
| `easeInOutSine` | `Cubic(0.445, 0.05, 0.55, 0.95)` :1735 | 0.11 | 0.11 | **settle 복귀.** 양끝 기울기가 거의 0이라 피크와 착지가 둘 다 부드럽다 |
| `easeInCubic` | `Cubic(0.55, 0.055, 0.675, 0.19)` :1559 | 0.10 | **2.49** | **마크 퇴장(불투명도+scale).** 가속하며 멀어진다 |
| `easeInOutCubic` | `Cubic(0.645, 0.045, 0.355, 1.0)` :1760 | 0.07 | 0 | **크림 알파.** 유일한 전면(全面) 변화라 시작·끝이 모두 무를 필요가 있다 |

**끝 기울기 0이 핵심 제약이다.** 등장 계열(`easeOutSine`/`easeOutCubic`/`easeInOutSine`)은 전부 끝 기울기가 0 근처다 — 값이 목표에 **멎는다**. `Curves.linear`나 `easeIn` 계열로 끝내면 마지막 프레임에서 속도가 살아 있어 "툭 끊긴 것"으로 읽힌다.

**`easeOutBack`류 오버슈트는 의도적으로 전면 배제한다.** 바운스는 친근함/장난이고, 이 마크는 손그림 획 3개 + 점 하나로 절제가 성격이다.

**솔직한 한계**: 점 불투명도의 창은 160 ms(60fps에서 9.6프레임)다. 이 길이에서 `easeOut`과 `easeOutSine`의 값 차이는 **어느 순간에도 알파 0.02 이하** — JND 아래다. 즉 이 자리의 커브 선택은 **미학적으로 무차별**하고, 실제로 하중을 받는 제약은 두 개뿐이다: ① 단조 증가 ② 끝 기울기 0. `easeOutSine`을 고른 건 반지름(`easeOutCubic`)과 **다른 모양**을 줘서 두 속성이 각각의 리듬을 갖게 하려는 것이고, 그 이상의 주장은 하지 않는다.

### 4-4. 60 fps와 120 fps에서 실제로 보이는 것

이 앱은 iOS에서 **120 Hz가 켜져 있다** — `ios/Runner/Info.plist:5-6`에 `CADisableMinimumFrameDurationOnPhone = true`가 있다. 없었다면 ProMotion 기기도 60 fps로 잠긴다.

프레임당 이동량으로 환산했다(박스 높이 136.04 dp, 네이비 최외곽 반경 **72.67 dp**, 3배 기기 기준).

| 구간 | 최대 속도 | 60 fps 프레임당 | 120 fps 프레임당 | 판정 |
|---|---|---|---|---|
| settle 상승 (2.2 %, 110 ms) | 41.2 dp/s | 0.69 dp = **2.1 px** | 0.34 dp = 1.0 px | 둘 다 매끄럽다. **차이 없음** |
| 점 반지름 (0.86→1.00, 260 ms) | 17.5 dp/s | 0.29 dp = 0.9 px | 0.15 dp = 0.4 px | 차이 없음 |
| 마크 퇴장 scale (4.8 %, 280 ms) | 31.0 dp/s | 0.52 dp = **1.6 px** | 0.26 dp = 0.8 px | 차이 없음 |
| **앱 콘텐츠 scale (1.5 %, 280 ms)** | 66.7 dp/s (화면 모서리 439 dp) | 1.11 dp = **3.3 px** | 0.56 dp = 1.7 px | **여기만 차이가 난다** |

**결론: 마크에서 벌어지는 일은 60 fps와 120 fps가 구별되지 않는다.** 이동량이 프레임당 2 px 남짓이라 sample-and-hold 디스플레이의 스트로빙 임계에 못 미친다.

**차이는 앱 콘텐츠 스케일에만 있고, 그마저도 프레임을 흘렸을 때만 보인다.** 화면 모서리가 프레임당 3.3 px 움직이는 상황에서 한 프레임을 놓치면 6.6 px 점프 — 이건 보인다. 그래서 §7에서 앱 콘텐츠 스케일이 유일한 측정 대상이 된다.

**부수 함의**: 120 Hz 기기에서 프레임 예산이 16.7 ms가 아니라 **8.3 ms**다. 기동 중 래스터 스레드에서 이 예산은 빡빡하다(§7-1).

### 4-5. 조정 규칙 — 죽은 시간을 만들지 않는다 (D2)

현재 코드는 `_start()`를 **`ready`가 true가 될 때만** 부른다(`splash_gate.dart:71, 77`). 즉 등장 260 ms가 앱이 준비된 **뒤에** 재생된다. 웜스타트 · 미로그인 사용자는 `session_restore.dart:73`에서 `await` 없이 즉시 반환되므로, 오늘 즉시 쓸 수 있던 앱에 **540 ms의 대기가 새로 생긴다.** 모션 문서 §8-1이 명시적으로 금지한 바로 그것이다.

```dart
@override
void initState() {
  super.initState();
  WidgetsBinding.instance.addPostFrameCallback((_) {
    if (!mounted) return;
    // 커밋 체크 — 이미 준비됐으면 등장을 시작조차 하지 않는다.
    if (widget.ready) { _startLeave(); return; }
    _arrive.forward();
  });
}

@override
void didUpdateWidget(SplashGate old) {
  super.didUpdateWidget(old);
  if (widget.ready && !old.ready) {
    // 목적지에 한 프레임을 준다 — 그래야 페이드인이 빈 프레임에서 시작하지 않는다.
    WidgetsBinding.instance.addPostFrameCallback((_) => mounted ? _onReady() : null);
  }
}

void _onReady() {
  if (_arrive.isCompleted || _arrive.value == 0) { _startLeave(); return; }
  // 남은 등장을 최대 120ms로 압축. 되감거나 자르지 않는다.
  _compressed = true;                                  // settle을 끈다 — 아래 참조
  final remainingMs = ((1 - _arrive.value) * 350).round();
  _arrive
      .animateTo(1.0,
          duration: Duration(milliseconds: math.min(remainingMs, 120)),
          curve: Curves.linear)
      .whenCompleteOrCancel(_startLeave);
}
```

| `ready` 시각 | 등장 | 죽은 시간 |
|---|---|---|
| 첫 프레임에 이미 true | **없음** | **+0 ms** (퇴장 280만) |
| 0 < t < 350 ms | 남은 만큼, 최대 120 ms로 압축 | ≤ +120 ms |
| t ≥ 350 ms | 이미 공짜로 끝났다 | **+0 ms** |

**압축 시 settle을 끄는 이유** — 모션 문서 §5-2는 "남은 시간을 압축해 가속"이라고만 썼다. 그런데 settle의 상승부(110 ms)를 그대로 가속하면 최대 압축(350→120 ms, 2.9배)에서 최대 속도가 **41.2 → 120 dp/s**가 된다. 그건 settle이 아니라 **팝**이다(§5-5의 진폭 논증이 무너지는 지점). 압축 경로에서는 `_compressed` 플래그로 마크 스케일을 1.000에 고정하고 **점의 불투명도·반지름만** 마무리한다. 점은 어느 프레임에서 잘려도 깨진 마크가 되지 않으므로 안전하다.

## 5. 점의 도착 — 1.69 : 1을 정면으로

모션 문서 §7-2가 계산한 값들을 독립적으로 재계산했고 **소수점까지 일치**한다. 그런데 거기서 끌어낸 **결론 두 개가 틀렸다.**

### 5-1. 실측 (WCAG 2.x 상대 휘도, 직접 계산)

| 조합 | 명암비 | 상대 휘도 Y | **L\*** | ΔL\* |
|---|---|---|---|---|
| 네이비 `#3B4C60` / 크림 `#F6F4EF` | **7.998 : 1** | 0.0694 / 0.9053 | 31.68 / 96.21 | **64.54** |
| **베이지 `#CEBBAA` / 크림** | **1.689 : 1** | 0.5156 / 0.9053 | 77.02 / 96.21 | **19.19** |
| 크림 / 흰 `#FFFFFF` | 1.099 : 1 | 0.9053 / 1.0 | 96.21 / 100.00 | 3.79 |
| 네이비 / 흰 | 8.792 : 1 | — | — | 68.32 |

베이지의 크림 대비 **Weber 대비 = 43.0 %**.

### 5-2. 정정 ① — "1.69:1은 거의 안 보인다"는 **사실이 아니다**

명암비 1.689는 낮지만, 그건 **비율**이다. 지각되는 것은 **L\* 차이**이고 그 값은 **19.19**다. 이건 흰 배경 위 밝은 회색 정도의 차이로 **정상 시력에서 명확하게 보인다.** 게다가 이 점은 지름 **22.9 dp**(반지름 17단위 × 0.67347 × 2)로 작지 않다.

WCAG 3:1 기준은 "보이는가"의 임계가 아니라 **저시력 사용자가 UI 컨트롤을 신뢰성 있게 식별할 수 있는가**의 임계다. 두 질문은 다르다.

### 5-3. 정정 ② — WCAG 1.4.11은 **애초에 적용되지 않는다**

SC 1.4.11(Non-text Contrast)에는 두 개의 예외가 있고, 베이지 점은 **둘 다** 해당한다.

| 예외 | 적용 |
|---|---|
| **Logotypes** — 로고/브랜드명의 일부 | 점은 `rise-mark.svg`의 구성 요소다. `design/brand/README.md:15-16`이 색 변경을 금지한다 |
| **Decoration** — 내용 이해에 필요하지 않은 그래픽 | 점 없는 R은 그 자체로 완결된 마크다(모션 §3-2의 2번). 점이 전달하는 정보는 0이다 |

**따라서 "3:1 미달 = 실패"라는 프레이밍은 과잉이다.** 실패가 아니다.

### 5-4. 그럼 진짜 문제는 무엇인가

저시력이 아니라 **조건**이다. ΔL\* 19는 다음 상황에서 잡음 바닥으로 내려간다:

- 직사광선 아래 휴대폰 (유효 대비가 3~5배 하락)
- 저휘도 OLED / 자동 밝기 최저치
- 블루라이트 필터·야간 모드 필터가 켜진 화면
- **그냥 그 순간에 화면을 안 보고 있었을 때**

즉 문제는 "누구에게 안 보인다"가 아니라 **"한 번뿐인 연출 비트가 상당한 비율의 세션에서 관측되지 않는다"**이다.

### 5-5. 정정 ③ — 기존 "호흡"은 지각 임계의 **1/10**이다

모션 문서 §4-1의 호흡은 `scale 1.000 → 1.014, 1400 ms, linear`이고, §7-2는 이것을 **접근성 요구사항**이라고 못 박았다("호흡이 있어야 어떤 시력에서도 지각 가능한 신호가 남는다"). 계산해 보면 이 두 주장은 **서로 모순이다.**

네이비 최외곽 반경 **72.67 dp**(§2-5), 시청 거리 300 mm(1 dp = 1.819 arcmin) 기준:

| | 총 변위 | 속도 | 판정 |
|---|---|---|---|
| **호흡 1.4 % / 1400 ms / linear** | 1.02 dp = **1.85 arcmin** | 0.73 dp/s = **1.32 arcmin/s** | 기준틀 없는 운동 지각 임계(≈ 10~20 arcmin/s)의 **1/10 이하** |

그리고 스플래시에는 **정지 기준틀이 없다** — 마크 주변은 균일한 크림이고, 화면 가장자리는 200 dp 넘게 떨어져 있어 상대 운동의 참조로 기능하지 못한다. 상태바 시계가 유일한 정지 요소인데 350 dp 밖이다.

모션 문서 자신도 "개별로는 지각 임계 이하"라고 적었다(§4-2). **지각 임계 이하인 것이 접근성 보증이 될 수는 없다.** 보이지 않는 신호는 아무에게도 아무것도 말하지 않는다. 같은 이유로 "없으면 멈춘 것으로 읽힌다"도 성립하지 않는다.

부수적으로: 호흡은 1400 ms에 **포화**한다. 라우터 예산 2200 ms를 다 쓰는 실패 경로에서는 마지막 800 ms가 완전 정지다 — 존재 이유였던 케이스를 덮지도 못한다.

**결론: 1.4 % / 1400 ms 호흡은 삭제한다.** 미학적으로도 접근성으로도 아무 일을 하지 않으면서, §7의 프레임 예산에서 **대기 구간 전체를 매 프레임 리페인트로 만드는 유일한 원인**이다.

### 5-6. 채택 — 마크 전체의 **settle**, 진폭 2.2 %

점의 도착에 **시간 동기된** 마크 전체의 단발 스케일 excursion을 건다: `1.000 → 1.022 → 1.000`, 피크는 도착 시작 110 ms 후.

**왜 마크 전체 스케일인가**

| 조건 | 충족 |
|---|---|
| 브랜드 규칙 위반 없음 | 셋이 **함께** 스케일된다 → 상대 위치 불변. `rise-mark.svg:17-18`이 금지한 건 개별 이동이다 |
| 명암비 8.00 : 1 위에서 일어난다 | 네이비가 캐리어. 점(1.69:1)은 그 위의 디테일 |
| 저공간주파수 신호 | 형태 전체의 변화는 시력이 떨어져도 살아남는다. 22.9 dp짜리 저대비 원반은 정확히 반대 성질이다 |
| 공짜 | 레이어 변환이다 — 리페인트 0, `saveLayer` 0 (§7-3) |

**왜 2.2 %인가 — 진폭 표** (반경 72.67 dp, 300 mm)

| 진폭 | 피크 변위 | arcmin | 읽히는 것 |
|---|---|---|---|
| 1.0 % | 0.73 dp | 1.32 | 변위 임계(Dmin ≈ 1~2 arcmin) 언저리 — **잡음** |
| 1.4 % (기존 호흡) | 1.02 dp | 1.85 | 임계 근처. 단발이면 겨우, 1400 ms에 펴 바르면 안 보인다 |
| **2.2 %** | **1.60 dp** | **2.91** | **Dmin의 2~3배. 감지되지만 무엇이 움직였는지 말할 수 없다** ← 채택 |
| 3.0 % | 2.18 dp | 3.97 | "마크가 커졌다"고 말할 수 있다 |
| 4.0 % | 2.91 dp | 5.29 | 명백한 확대 |
| 6.0 % | 4.36 dp | 7.93 | **팝/바운스.** 장난스럽고 싸 보인다 |

2.2 %는 **감지 임계를 확실히 넘기는 가장 작은 값**이다. 그리고 상승 110 ms 동안 최대 속도가 41.2 dp/s = **75 arcmin/s**로 운동 감지 임계(10~20 arcmin/s)의 **4배**다 — 짧은 창에서는 변위와 속도 둘 다 임계를 넘긴다.

**방향이 확대인 이유**: 점의 반지름도 0.86→1.00으로 커진다. 같은 방향이라 **두 개의 사건이 아니라 하나의 사건**으로 묶인다. 축소(1.000→0.978)를 먼저 검토했지만, 정합 유지 90 ms 직후에 마크가 **작아지면** "네이티브가 보여주던 것보다 작은 것으로 바뀌었다" — 즉 우리가 없애려는 이음매 아티팩트로 읽힐 위험이 있다.

**대칭으로 1.000에 돌아오는 이유**: §4-1 — 퇴장이 `begin: 1.0`을 하드코딩할 수 있고, 압축·중단 어느 시점에서 잘려도 계단이 안 생긴다.

**타이밍이 점보다 먼저 피크에 닿는 이유**: settle 피크는 t = 200 ms, 점 불투명도 완료는 t = 250 ms. **캐리어가 시선을 부르고 그다음 디테일이 해상된다.** 순서가 반대면 점이 완성된 뒤에 마크가 흔들리는 게 되어 두 사건이 된다.

### 5-7. 점 자체 — 반지름 0이 아니라 0.86에서 (D5)

현재 `rise_mark.dart:113`은 `dotRadius * dotProgress`로 **반지름 0에서** 키운다. 불투명도는 없다. 결과: 풀 채도의 아주 작은 티끌이 부풀어 오른다 — 모션 문서 §4-2가 "뿅 하고 튀어나온다(장난스럽다)"며 배제한 그 인상이다.

확정: **반지름 계수 0.86 → 1.00**(9.85 dp → 11.45 dp) + **별도의 불투명도 0 → 1**. 두 창이 다르다(불투명도 160 ms, 반지름 260 ms) — 점이 **선명해진 뒤에 자리를 잡는다.** 반대면 흐린 것이 커지는 = 초점이 안 맞는 인상이 된다.

### 5-8. 그리고 — 접근성 보증은 **퇴장**이 진다

settle은 크래프트 장치이지 접근성 보증이 **아니다.** 그렇게 팔지 않는다.

이 화면에서 **모든 세션에 반드시 일어나고 누구도 놓칠 수 없는 사건**은 퇴장이다:

- 화면 **전체**의 크림이 걷힌다 (전면 변화)
- 네이비 마크가 **8.00 : 1 → 0**으로 사라진다 (ΔL\* 64.5)
- 앱 콘텐츠가 올라온다

등장은 §4-5의 커밋 체크에 따라 **일어나지 않을 수도 있다**. 퇴장은 100 % 일어난다. 접근성 관점에서 "이 화면에 지각 가능한 신호가 있는가"의 답은 **퇴장이고, 언제나 그렇다.** 등장은 보이는 사람에게 주는 덤이다.

### 5-9. 검토했지만 채택하지 않은 것

| 안 | 왜 |
|---|---|
| **획 굵기 변조** (21.5 → 22.8, 잉크 +6 %) | 저공간주파수 휘도 신호로는 영리하다. 하지만 계산해 보면 마크 영역 평균 휘도 변화가 약 1.85 %로 시간 대비 임계(≈ 1 %) **바로 위** — 신뢰할 수 없다. 게다가 매 프레임 스트로크 재테셀레이션을 강제해 §7의 "래스터 한 번" 성질이 깨진다 |
| **네이비를 미세하게 어둡게** | 같은 신호를 공짜로 얻지만 `design/brand/README.md:15-16` 위반이고, 화면 깜빡임으로 읽힌다 |
| **크림 배경을 1 % 밝게** | 전면 휘도 변화라 감지력은 최고다. 하지만 §3의 픽셀 정합 감각을 깨고 화면 밝기 버그처럼 보인다 |
| **점을 3:1까지 어둡게** | 브랜드 색 변경. 명시 금지 |
| **점 주변 링·글로우 추가** | 마크에 없는 요소를 추가하는 것 |

## 6. 모션 감소 — 무엇이 **대신** 그려지는가

### 6-1. 지금 코드는 하드컷으로 되돌린다 (D6)

```dart
// splash_gate.dart:83-86 — 현재
if (MediaQuery.maybeDisableAnimationsOf(context) ?? false) {
  setState(() => _gone = true);   // ← 게이트가 통째로 사라진다
  return;
}
```

`_gone = true`는 게이트를 트리에서 빼는 것이다. 전환이 0 프레임이 되고, **기동경로 문서가 "뚝 끊긴다"의 정체라고 밝힌 그 하드컷으로 정확히 되돌아간다.**

모션 감소는 *전환을 없애라*가 아니라 *움직이지 마라*다. Apple의 Reduce Motion은 슬라이드를 **크로스디졸브로 치환**하지 제거하지 않는다. WCAG 2.3.3 Understanding도 명시한다 — **"요소의 색이나 불투명도를 바꾸는 것은 motion animation이 아니다."** 즉 페이드는 모션 감소에서 **허용되는 대체 수단**이지 제거 대상이 아니다.

### 6-2. 정확히 무엇이 그려지는가

| 항목 | 기본 | `disableAnimations == true` |
|---|---|---|
| **게이트 수명** | 첫 프레임 ~ `ready` + 280 ms | **완전히 동일** (~ `ready` + 200 ms). 짧아지는 건 **전환**이지 **덮개**가 아니다 |
| **첫 프레임** | 크림 + 네이비 획, 점 없음, scale 1.000 | **동일.** 픽셀 정합은 모션이 아니다 |
| **대기 구간** | 정지 | **정지 (동일)** |
| 점 불투명도 | 0 → 1, 160 ms | **0 → 1, 200 ms, `easeOutSine`** — 유지 |
| 점 반지름 | 0.86 → 1.00 | **1.00 고정** — 크기 변화 = 모션 |
| 마크 settle | 1.000 → 1.022 → 1.000 | **없음** (1.000 고정) |
| 퇴장 · 마크 불투명도 | 1 → 0, 180 ms, `easeInCubic` | **1 → 0, 200 ms, `Curves.linear`** |
| 퇴장 · 마크 scale | 1.000 → 1.048 | **없음** |
| 퇴장 · 크림 알파 | 1 → 0, 280 ms, `easeInOutCubic` | **1 → 0, 200 ms, `easeInOutSine`** |
| 퇴장 · 앱 scale | 0.985 → 1.000 | **없음 — `ScaleTransition` 위젯 자체를 만들지 않는다** |
| **전환 총량** | ≤ 630 ms | **≤ 400 ms** |

**핵심 문장 두 개:**

> **① 모션 감소는 게이트의 *수명*을 절대 줄이지 않는다. 줄이는 것은 *전환*뿐이다.** 복원이 1.8초 걸리면 두 모드 모두 게이트가 1.8초 떠 있다. 모션 문서 §7-1의 "총 길이 ≤ 400 ms"는 전환 예산이지 노출 시간이 아니다 — 그 표기가 D6의 원인일 가능성이 높다.

> **② 점은 모션 감소에서도 페이드인한다.** 네이티브 스플래시에 점이 없으므로, 하드컷으로 점을 찍으면 그건 **플래시**다. 전정계 민감·광과민 사용자에게 플래시는 페이드보다 나쁘다. 그리고 불투명도 변화는 WCAG 정의상 motion animation이 아니다.

### 6-3. 플래그를 언제 읽는가 (D8)

```dart
// splash_gate.dart:71 → :83 — 현재
if (widget.ready) _start();          // initState 안
  → MediaQuery.maybeDisableAnimationsOf(context)   // ← InheritedWidget 의존 등록
```

`initState`에서 `dependOnInheritedWidgetOfExactType`을 호출하면 debug 빌드에서 assert가 던진다("... was called before initState() completed"). **지금은 도달하지 않는다** — `_restored`가 첫 빌드에 항상 false라 `if (widget.ready)`가 거짓이기 때문이다. 하지만 `_restored`를 Riverpod provider로 옮기거나(첫 빌드에 이미 true일 수 있다) 게이트에 `key`를 붙여 element가 재생성되는 순간 **터진다.** 잠복 지뢰다.

확정 패턴:

```dart
bool? _reduceMotion;   // 한 번 읽고 래치한다

@override
void didChangeDependencies() {
  super.didChangeDependencies();
  _reduceMotion ??= MediaQuery.maybeDisableAnimationsOf(context) ?? false;
}
```

- `didChangeDependencies`는 첫 빌드에서 `initState` **직후에** 불린다 — assert 없음.
- `??=`로 **래치**한다. 스플래시 진행 중에 사용자가 시스템 설정을 토글하는 시나리오는 실재하지 않고, 재생 중 재계획은 어느 쪽 결과보다도 나쁘다.
- SDK 확인: `MediaQuery.disableAnimationsOf`는 `widgets/media_query.dart:1950`, 데이터 필드는 `:628`, 플랫폼 소스는 `platformDispatcher.accessibilityFeatures.disableAnimations`(`sky_engine/lib/ui/window.dart:954`)에서 `:318-320`으로 흘러든다.

## 7. 프레임 예산

### 7-1. 기동 첫 프레임은 앱 수명에서 가장 비싼 프레임이다

스플래시는 하필 그때 돈다. 그 구간의 래스터 스레드에는 파이프라인 생성, 텍스처 업로드, 첫 셰이더 컴파일(Skia 폴백 경로)이 몰려 있다. 그리고 §4-4에서 확인했듯 이 앱은 iOS 120 Hz가 켜져 있어 **예산이 8.3 ms**다.

그래서 이 절의 기준은 "빠른가"가 아니라 **"기동 프레임에 무엇을 추가로 얹는가"**다.

### 7-2. 지금 구현이 얹고 있는 세 가지

**① 풀스크린 `saveLayer` × 17 프레임 (D3) — 가장 크다**

```dart
// splash_gate.dart:122-129
Opacity(
  opacity: veil,
  child: ColoredBox(color: cream, child: Center(child: RiseMark(...))),
)
```

`RenderOpacity.alwaysNeedsCompositing => child != null && _alpha > 0`이고 `isRepaintBoundary`가 그 값을 그대로 쓴다(`rendering/proxy_box.dart:884, 887`). **알파가 0보다 크기만 하면 항상 `OpacityLayer`가 푸시된다** — 1.0에서도 우회하지 않는다. 엔진이 알파를 자식 드로우 콜에 접어 넣는 최적화는 자식이 **겹치지 않는 단일 드로우 op**일 때만 성립하는데, 이 서브트리는 풀스크린 사각형 + 스트로크 경로 + 원 세 개다. **오프스크린을 가정해야 한다.**

1080×2400 · 3배 기기에서 풀스크린 오프스크린은 **약 2.6 M 픽셀**이고, 이걸 280 ms 동안 17번 할당·합성한다. 기동 중에.

**② `CurvedAnimation`을 프레임마다 2개씩 생성 (D4)**

```dart
// splash_gate.dart:110, 115 — AnimatedBuilder의 builder 안
final dot = CurvedAnimation(parent: _c, curve: Interval(...)).value;
final veil = 1 - CurvedAnimation(parent: _c, curve: Interval(...)).value;
```

`CurvedAnimation`의 생성자는 **`parent.addStatusListener(_updateCurveDirection)`를 부른다**(`animation/animations.dart:384`). 제거는 `dispose()`에서만 일어난다(`:431`). 여기서는 아무도 `dispose()`를 부르지 않는다.

540 ms × 60 fps = **약 64개의 리스너가 `_c`에 쌓인다.** 컨트롤러가 dispose되면서 결국 정리되므로 앱을 죽이지는 않지만, ⓐ 매 프레임 리스너 리스트가 커지고 ⓑ 생성자가 `debugMaybeDispatchCreated`를 호출하므로(`:383`) **Flutter의 leak-tracking 테스트에서 전부 미해제로 잡힌다.**

고정: `CurvedAnimation`은 `State`의 필드로 한 번 만들고 `dispose()`에서 해제한다. 빌더 안에서 만들지 않는다.

**③ `Path` 매 프레임 재생성 (D7)** — §2-3.

**부수: `AnimatedBuilder`의 범위가 너무 넓다.** 현재 `IgnorePointer → Opacity → ColoredBox → Center → RiseMark → SizedBox → CustomPaint` 전부가 프레임마다 재빌드된다. 위젯 재빌드 자체는 싸지만, `RiseMarkPainter`가 새 인스턴스로 만들어지면서 `shouldRepaint`가 매번 호출되고 대부분 true를 반환한다.

### 7-3. `shouldRepaint` 권고 — **페인터를 둘로 쪼갠다**

`shouldRepaint`는 페인터가 애니메이션 입력을 받는 한 이길 수 없는 싸움이다. 이기는 방법은 **비싼 쪽이 애니메이션 입력을 아예 안 받게 만드는 것**이다.

| 페인터 | 입력 | 등장(350 ms) | 대기(0~2200 ms) | 퇴장(280 ms) |
|---|---|---|---|---|
| `RiseStrokesPainter` | `alpha` 하나 | **리페인트 0** (alpha 고정 1.0) | **리페인트 0** | 180 ms만 |
| `RiseDotPainter` | `opacity`, `radiusFactor` | 프레임마다 (`drawCircle` 1회) | 리페인트 0 | 180 ms만 |

**`CustomPainter(repaint: Listenable)`을 쓴다.** `super.repaint`에 `Animation`을 넘기면 `RenderCustomPaint`가 거기에 리스너를 걸고 `markNeedsPaint()`를 직접 호출한다 — **위젯 트리를 재빌드하지 않고** 페인트만 다시 돈다. 페인터 인스턴스가 수명 내내 하나이므로 `shouldRepaint`는 아예 호출되지 않고, 그래서 `=> false`로 두는 게 맞다(§2-7).

**결과: 스플래시 전체에서 위젯 재빌드가 사실상 0이다.** 마크 스케일은 `ScaleTransition`(`AnimatedWidget` — 자기 자신만 재빌드), 크림 알파만 1위젯짜리 `AnimatedBuilder`.

**두 페인터 사이에 `RepaintBoundary`를 넣는다** — 점의 리페인트가 획의 레이어를 더럽히지 않게. 둘은 **기하적으로 겹치지 않으므로**(§2-5: 10.22 단위 여유) 그리는 순서도 무관하다.

**절대 하면 안 되는 것 — 획 3개를 3번의 `drawPath`로 쪼개기.** 아치의 끝 cap `(206,249)`과 다리의 시작 cap `(208,252)`은 중심 거리 3.6, 반지름 10.75로 **심하게 겹친다.** 하나의 `drawPath` 안에서는 래스터라이저가 커버리지를 한 번에 계산하므로 겹침이 문제되지 않는다. 3번으로 쪼개면 반투명 페인트에서 **겹침부만 진하게** 나온다(알파 a에서 `1-(1-a)²`, a=0.5이면 0.75 대 0.5). 지금 코드가 하나의 `Path`인 것은 우연히 옳고, **그게 §7-4에서 `saveLayer`를 0으로 만드는 근거다.**

### 7-4. 마크를 한 번만 래스터화해야 하는가 — **아니다 (조건부 에스컬레이션)**

**권고: 순수 벡터로 간다.** 이유:

| 항목 | 값 |
|---|---|
| 총 경로 길이 | 475.97 단위 × 0.67347 = **약 320 dp** |
| 곡선 개수 | 3차 8 + 2차 2 + 직선 2 = **12 세그먼트** |
| 예상 테셀레이션 정점 | 수백 개 |
| 예상 비용 | **0.1 ms 미만** — 8.3 ms 예산의 1 % 남짓 |
| 리페인트가 실제로 도는 프레임 | 퇴장 180 ms = 60 fps에서 **11 프레임**뿐 (§7-3) |

**캐시가 갚아 주는 것보다 캐시의 복잡도가 크다.** `Picture.toImageSync`(`sky_engine/lib/ui/painting.dart:8497`, 존재 확인)를 쓰면 비동기 처리·메모리 수명·해제 시점·**샘플링으로 인한 안티에일리어싱 변화**가 따라온다. 마지막 항목이 특히 나쁘다 — 벡터→래스터 전환 프레임에서 가장자리가 미세하게 달라지는데, 이 화면의 1순위가 **이음매를 안 보이게 하는 것**이다.

**에스컬레이션 조건과 방법** — 아래 측정에서 래스터 스레드가 예산을 넘길 때만:

1. `toImageSync`로 획을 **위젯의 디바이스 픽셀 크기 × 2**로 굽는다.
2. 굽는 시점은 **대기 구간**(유휴 프레임이 있다). 프레임 0~1에서는 절대 하지 않는다 — 래스터 스레드가 가장 바쁠 때다.
3. 벡터→래스터 교체는 **퇴장이 시작된 뒤에** 한다. 마크가 이미 사라지는 중이라 안티에일리어싱 변화가 묻힌다. **정합 이음매에서는 절대 교체하지 않는다.**
4. `drawImageRect` + `FilterQuality.medium`.

### 7-5. 오버레이 스택 — 확정

```dart
Stack(
  fit: StackFit.expand,
  children: [
    // ① 앱 콘텐츠 — 불투명하게 유지. 스케일만. (§4-2)
    RepaintBoundary(
      child: ScaleTransition(scale: _appScale, child: widget.child),
    ),

    // ② 크림 — 알파를 **색에 굽는다**. Opacity 위젯을 쓰지 않는다 → saveLayer 0.
    Positioned.fill(
      child: AbsorbPointer(
        child: AnimatedBuilder(
          animation: _veil,
          builder: (_, __) => ColoredBox(
            color: RiseMarkGeometry.cream.withValues(alpha: _veil.value),
          ),
        ),
      ),
    ),

    // ③ 마크 — 페인터 자체의 알파로 페이드. Opacity 위젯 없음.
    Positioned.fill(
      child: IgnorePointer(
        child: Center(
          child: SizedBox(
            width: _boxHeight * 196 / 202,
            height: _boxHeight,
            child: ScaleTransition(
              scale: _markScale,
              child: Stack(fit: StackFit.expand, children: [
                RepaintBoundary(
                  child: CustomPaint(painter: RiseStrokesPainter(alpha: _markAlpha)),
                ),
                CustomPaint(painter: RiseDotPainter(
                  opacity: _dotAlpha, radiusFactor: _dotRadius)),
              ]),
            ),
          ),
        ),
      ),
    ),
  ],
)
```

**설계 전체에서 `saveLayer`가 0개다.** 세 가지가 맞물려 성립한다:

1. 크림은 `Opacity` 위젯이 아니라 **색의 알파** → 풀스크린 사각형 드로우 하나, 레이어 없음
2. 획은 **하나의 `Path` + 하나의 `drawPath`** → 커버리지가 한 번에 해결되어 프리미티브 알파가 정확 (§7-3)
3. 점은 **네이비와 10.22 단위 떨어져 있다** → 겹침 없음, 프리미티브 알파가 정확 (§2-5)

추가로:

- **`Transform`/`ScaleTransition`에 `filterQuality`를 절대 설정하지 않는다.** 설정하면 `saveLayer` + 이미지 필터가 강제되고 자식이 리샘플링되어 흐려진다. `null`(기본값)이면 자식이 새 스케일로 다시 래스터되어 선명하다.
- **퇴장 t ≥ 180 ms에서 마크를 트리에서 뺀다.** 마크 알파가 0에 도달한 뒤에도 6프레임을 더 그린다. 페인터의 `if (a <= 0) return;`이 이미 방어하지만, 서브트리 자체를 빼는 게 더 싸다.
- **`_gone`이면 래퍼 없이 `return widget.child`.** `Transform`·`Opacity`·`RepaintBoundary` 어느 것도 남기지 않는다. 앱 수명 내내 붙는 합성 비용이다.
- **대기 구간에 앱 콘텐츠가 불투명한 크림 아래에서 계속 그려진다.** Flutter에 가림 컬링이 없으므로 이건 피할 수 없고, 사실 **원하는 낭비다** — 목적지를 미리 데워 둔다. 다만 `RepaintBoundary`로 감싸 래스터가 재사용되게 한다. 복원 중에는 자식이 go_router의 `SizedBox.shrink()`라 비용이 0이라는 점도 유리하다.

## 9. 자기 비판 — 이 명세에서 제일 약한 세 곳

### 9-1. §5의 arcmin 계산 전부가 **두 개의 미측정 값** 위에 서 있다

`0.67347 dp/단위`(= `RiseMark(size: 132)`)와 **시청 거리 300 mm**. 전자는 누군가 코드에 적은 값이지 기동경로 §8의 교정을 통과한 값이 아니고, 후자는 통용되는 어림값이다. 실제 휴대폰 시청 거리는 250~450 mm로 흩어진다.

**무너지는 지점**: 실기기 교정 결과 박스 높이가 136 dp가 아니라 **90 dp**로 나오면 모든 변위가 34 % 줄어 2.2 % settle이 **1.92 arcmin**이 된다 — 내가 "Dmin의 2~3배"라고 주장한 자리가 임계 근처로 내려앉는다. 그 경우 settle 진폭을 **3.33 %**로 올려야 한다(변위를 2.91 arcmin으로 되돌리는 값). 시청 거리 450 mm를 함께 가정하면 **4.99 %**까지 올라가고, 그건 §5-6 표에서 내가 "명백한 확대"로 분류한 구간이다 — **즉 마크가 작으면 settle이라는 장치 자체가 성립하지 않을 수 있다.**

**반증 방법**: §3-4의 실기기 교정을 먼저 끝내고 `boxHeight`를 확정한 뒤 §5-6 표를 재계산한다. 표를 다시 만들 수 있게 계산 근거를 전부 노출해 뒀다: **반경 = 107.906 viewBox 단위 × (boxHeight / 202) dp** · **1 dp = `atan(0.15875 mm / 시청거리) × 60` arcmin** (300 mm에서 1.819).

### 9-2. "2.2 %는 settle로 읽히고 6 %는 바운스로 읽힌다"는 **측정이 아니라 내 주장**이다

**감지** 임계는 심리물리학 문헌의 값으로 계산했다. 하지만 "느껴진다"와 "바운스로 보인다" 사이의 경계는 미학적 판단이고 내가 그었다. §5-6 표의 세 번째 열은 계산 결과가 아니라 해석이다.

**무너지는 지점**: 이 경계가 실제로는 훨씬 위(예: 4 %)에 있다면 2.2 %는 아무도 못 느끼는 채로 복잡도만 늘린 것이다. 반대로 경계가 아래(1.5 %)에 있다면 2.2 %가 이미 싸구려로 보인다.

**반증 방법**: 1.4 % / 2.2 % / 4.0 % 세 버전을 실기기에서 240 fps로 녹화하고, 무엇이 바뀌었는지 모르는 5명에게 보여준다. ① 5명 중 아무도 1.4 %와 2.2 %를 구별하지 못하면 settle은 값을 못 벌고 있으므로 **삭제한다**(그러면 §5는 5-8의 "퇴장이 접근성을 진다"만 남는다 — 그 결론은 settle과 독립적이므로 살아남는다). ② 5명 중 3명 이상이 2.2 %를 "통통 튄다"고 표현하면 1.5 %로 내린다.

### 9-3. "`saveLayer` 0개"는 **엔진 동작에 대한 추론**이지 관측이 아니다

§7-5의 결론은 "하나의 `drawPath`가 자기 겹침 커버리지를 한 번에 해결한다"에 의존한다. 기하는 증명했다(겹침 위치·거리·반지름 전부 계산). 하지만 **반투명 페인트가 걸린 자기 겹침 스트로크를 Impeller가 어떻게 처리하는지는 엔진 구현 세부이고 릴리스마다 바뀌어 왔다.** 나는 기하를 읽었지 엔진 소스를 읽지 않았다.

**무너지는 지점**: Impeller가 스트로크 지오메트리를 테셀레이션한 뒤 삼각형 단위로 알파 블렌딩하면, 아치 끝과 다리 시작이 겹치는 약 21 dp 원반이 퇴장 페이드 동안 **더 진하게** 나온다. 알파 0.5에서 0.75 — 상대적으로 50 % 차이다.

**반증 방법**: §7-6의 측정 4번. 마크를 알파 0.5로 고정 렌더하고 viewBox 좌표 `(207, 250.5)` 부근(아치/다리 접합부)과 같은 획의 비겹침 지점(예: `(159.5, 250)`)의 픽셀을 비교한다. 다르면 **마크 박스 크기의 `saveLayer` 하나**를 도입한다 — 136 × 140 dp, 3배에서 약 0.17 M 픽셀로 현재 구현의 풀스크린 2.6 M 픽셀보다 **15배 싸다.** 즉 이 가정이 틀려도 §7-2의 D3 교정은 그대로 유효하다.

**한 줄로**: 세 약점 중 9-1이 가장 무겁다 — §3의 실기기 교정 하나가 §5 전체의 숫자를 확정하거나 무너뜨린다. **그래서 §3이 §4·§5보다 먼저다.**
