# 라이즈 컨디셔닝 어드민 (React)

라이즈 컨디셔닝 센터의 관리자 백오피스. 대표(owner)는 센터 전체(매출·통계·설정 포함), 트레이너는
담당 회원·본인 일정·본인 정산만 보는 역할 기반 화면입니다.

## 스택

React 19 · Vite 6 · TypeScript(strict) · **TanStack Query v5**(서버상태) · **Tailwind v4**(`@tailwindcss/vite`) ·
경량 shadcn 스타일 프리미티브(직접 작성) · lucide-react(아이콘 전용, 이모지 미사용) ·
firebase(Auth) · **qrcode.react 4.2.0**(데스크 체크인 QR — P11).

와드샷 콘솔(`../../web/`)과 동일한 패턴을 재사용했습니다 — `lib/{types,api,queries}` 3분할, 상태
기반 탭 라우팅, `components/ui.tsx` 프리미티브.

## 실행

```bash
npm install        # 의존성 설치
npm run dev         # http://localhost:5174 (백엔드는 /api → localhost:8080 프록시)
npm run build        # tsc(src) + tsc(vite.config) 타입체크 → vite build (2026-08-17 검증: 신선 설치 후 exit 0)
npm run preview      # 빌드 산출물 미리보기
```

백엔드를 먼저 띄우세요(포트 8080):

```bash
cd ../backend && go run ./cmd/server   # (백엔드 저장소 경로는 실제 구성에 맞게 조정)
```

백엔드가 없으면 로그인 단계(`/v1/me` 재확인)에서 막혀 로그인 화면에 머뭅니다. 로그인 후
백엔드가 내려간 경우에는 각 화면의 쿼리가 `ErrorState`로 표시됩니다(재연결 후 새로고침).

환경변수는 [.env.example](.env.example) 참고. `VITE_API_TARGET`(dev 프록시 대상)은 `.env` 파일로도
동작합니다(vite.config.ts가 `loadEnv` 사용).

> `.env.example` 하단의 `VITE_FIREBASE_API_KEY`/`_AUTH_DOMAIN`/`_PROJECT_ID` 3줄은 **죽은
> 항목**입니다. P06 실연동에서 웹 config를 `src/lib/firebase.ts`에 하드코딩하기로 정했고
> (비밀이 아니라 식별자 — 보안 경계는 백엔드 ID 토큰 검증), 코드는 `import.meta.env.VITE_FIREBASE_*`를
> **한 곳도 읽지 않습니다.** 채워 넣어도 아무 효과가 없습니다.

## 운영 배포 (Firebase Hosting)

**https://rize-218c1.web.app** — `npm run build`의 `dist/`를 Firebase Hosting에 올린다.
설정은 저장소 루트 [`../firebase.json`](../firebase.json).

**`VITE_API_BASE`는 지정하지 않는다.** 기본값 `/api`를 그대로 쓰고, Hosting이 `/api/**`를
Cloud Run(`rize-api`)으로 리라이트한다 — 브라우저 입장에선 전부 같은 오리진이라 **CORS가 아예
발생하지 않는다**(프리플라이트 왕복도 없음). Hosting은 경로 접두사를 벗겨주지 못하므로 백엔드가
`/api/v1/*`도 받도록 미러 마운트돼 있다(백엔드 README 참고). 그래서 개발(vite 프록시가 `/api`를
벗김)과 운영의 클라이언트 코드가 완전히 동일하다 — 빌드 플래그가 필요 없다.

정적 자산은 1년 immutable 캐시, `index.html`은 `no-cache`(배포 즉시 반영). SPA 딥링크는
`**` → `/index.html` 폴백으로 처리된다.

## 로그인 · 데모 역할전환

로그인 화면은 **이메일/비밀번호 실로그인**(Firebase Auth)과 로컬 개발용 **데모 버튼 2개**("대표로
로그인" · "트레이너로 로그인(정혜린)")를 함께 제공합니다. 데모 버튼은 `X-Dev-Role` / `X-Dev-Uid`
헤더(API계약_v1.md 명시, 로컬 전용)를 세팅합니다. 어느 경로든 로그인 직후 `GET /v1/me`로 실제
역할·`center_id`를 재확인하는 규칙은 동일합니다. 헤더 우측의 역할전환 pill은 **데모 모드에서만**
표시되며(실계정 로그인 시 숨김), 전환 시 TanStack Query 캐시를 통째로 비워 이전 역할의 데이터가
화면에 남지 않게 했습니다.

**어드민 셸은 스태프(대표·트레이너)만 들어옵니다.** 백엔드가 UserIndex 없는 Firebase 계정을
가입 부트스트랩 목적으로 `role=member`로 통과시키므로, 인증만으로 셸을 열면 "대시보드는 보이는데
설정 탭은 없고 패널마다 권한 오류"인 반쪽 화면이 됩니다. 그런 계정은 `NoAccess` 화면으로 끊고
다음 행동(회원 앱으로 로그인 / 대표에게 초대 요청)을 안내합니다.

### 비율 표시 규약 (P09 — 계약 v2.1)

비율은 **3상태**로 갈라 쓴다(`lib/format.ts`의 `ratioState` 한 곳에만 정책이 있다):
분모 > 0이면 퍼센트(**진짜 0.0%도 그대로**), 분모가 0이면 "—"와 "집계 대상 0건",
분모 필드가 아예 없으면(구버전 서버) "—"와 **단정하지 않는 문구**. 종전엔 같은 응답으로
매출 화면은 "—", 대시보드 비교표는 "0.0%", HW 카드는 "배정이 없어요"가 동시에 나왔다.

반환은 `{ kind: "value" | "none" | "unknown", text, rate?, note? }`이고, 분모는 왔는데 값이
`null`인 경우도 `unknown`으로 접는다(분자만 빠지는 응답도 단정하지 않는다). 완료율·재등록률·
노쇼율을 쓰는 화면은 `Sales.tsx`(KPI 3종 + 트레이너 비교표) · `Dashboard.tsx`(HW 카드 · KPI ·
트레이너 "나 vs 센터 평균") · `Homework.tsx`(배정건별) 셋뿐이므로, 규약을 바꿀 땐 이 셋만 보면 된다.

⚠ 백엔드의 `GET /v1/stats?range=`는 **아직 무시된다**(계약 v2.1이 구현 갭으로 명시). 지금 화면에
보이는 분모는 "해당 기간"이 아니라 **전 기간** 집계다 — 기간 필터 UI를 붙일 때 서버와 함께 고쳐야 한다.

### Firebase Auth 실연동 (P06 — 완료)

- `src/lib/firebase.ts` — 프로젝트 `rize-218c1` 웹 config로 `initializeApp` → `export const auth`.
  웹 config는 비밀이 아니라 식별자라 하드코딩합니다(보안 경계는 백엔드 ID 토큰 검증).
- `src/lib/auth.tsx` — `loginEmail`(signIn → `/v1/me`), `onAuthStateChanged`로 새로고침 세션
  복원, `logout`은 `signOut` + 데모 흔적 제거 + 캐시 클리어.
- 로그인 화면의 **"비밀번호를 잊으셨나요? / 처음 로그인이신가요?"** → `sendPasswordResetEmail`.
  관리자가 임시 비번으로 계정을 만들어 준 최초 로그인도 이 경로를 쓴다. 계정 존재 여부는
  노출하지 않는다(`user-not-found`도 성공과 같은 안내 — 이메일 열거 방지).
- `src/lib/api.ts` — `req()`가 `currentUser.getIdToken()`이 있으면 `Authorization: Bearer`를
  싣고 **이때 X-Dev 헤더는 아예 붙이지 않습니다**(우선순위 Firebase > 데모). 로그인 전이면
  기존 X-Dev 경로로 폴백하므로 로컬 개발은 그대로입니다.
- 운영 배포 방식은 위 **"운영 배포 (Firebase Hosting)"** 절을 따릅니다 — `VITE_API_BASE`를
  지정하지 **않고** Hosting 리라이트로 같은 오리진을 씁니다(P07). 종전에 여기 적혀 있던
  "Cloud Run URL 지정 + CORS_ORIGINS 추가"는 그 구성 이전의 안내라 지웠습니다.

## 정직한 갭 목록 (백엔드와 반드시 대조 필요)

`API계약_v1.md`는 의도적으로 압축된 참조 문서라, 화면을 실제로 구현하는 과정에서 계약에
명시되지 않은 조회 경로 4곳을 최소한으로 "가정"했습니다. 모두 `src/lib/types.ts` 하단과
`src/lib/api.ts`에 `[가정 N]` 주석으로 표시해 두었습니다.

**2026-08 갱신 — v1.1 정합 패치:** `API계약_v1.md`의 "v1.1 정합 패치" 섹션이 아래 가정
1~4와 `Slot.teams[].status`, `Stats`의 0~1 소수 비율을 모두 "가정 승인/확정"으로 반영해 더
이상 추정이 아니라 계약의 일부입니다. 같은 패치가 `Contract`(전자계약) 엔티티와 `GET
/v1/payments?member=`를 추가해, 아래 "그 외 범위를 의도적으로 좁힌 부분"의 결제·계약서 관련
항목 2개도 실구현으로 갱신했습니다(취소선 표시).

**2026-08-17 갱신 — v1.2 정합 패치(3계층 교차검증, work_log/P01) 반영:**

- **"유예 처리" 버튼 제거** — 노쇼 API 재호출(이중 차감 유발)이던 버튼을 정적 안내("최초 1회
  자동 유예")로 교체. 유예는 백엔드가 노쇼 처리 시 자동 적용합니다(P7, 유예 전용 API 없음).
- **추가 계약(재등록) 재시도 안전** — 회원권 발급 성공 후 결제 기록 실패 시, 재제출해도 회원권이
  이중 발급되지 않게 발급된 pass id를 기억하고 결제만 재시도합니다.
- **결제 `installments[].paid_at`은 RFC3339** — 계약 v1.2 확정(due는 "YYYY-MM-DD" 유지).
- **draft 계약도 "발송" 가능** — 종전엔 sent 재발송 버튼만 있어 draft의 최초 발송 수단이 없었음.
- **정산 표기 규약 확정** — `payout.value`: rate=0~1 소수(`formatPercent`), per_session=원 단위(₩/회).
- **트레이너의 `scope=center` 통계** — 백엔드가 허용(단 금액 필드·by_trainer는 비움). 트레이너
  대시보드의 "센터 평균" 비교가 실데이터로 동작하고, 쿼리 에러 시 0%로 위장하지 않고 ErrorState 표시.
- **원장 캐시 무효화 보강** — 완료/노쇼/홀딩/재개/체크인 후 열려 있는 회원 상세의 원장이 갱신됩니다.
- **`.env` 함정 2건 해소** — `VITE_API_BASE=` 빈 값이 전 API를 마비시키던 문제(`||` 폴백),
  `VITE_API_TARGET`이 .env에서 무시되던 문제(`loadEnv`) 수정.

**2026-08-18 갱신 — UI/UX 교차검증 라운드(목업 대조) 반영:**

- **트레이너 뷰 개인정보 마스킹(목업 s-cal 규칙)** — 예약 그리드·관리 모달에서 타 코치 팀은

  Cloud Run 환경변수 값과 눈으로 대조할 수 있게 했습니다. 회원 앱 쪽 스캐너는 `app/README.md`의
  "하드웨어 실연동" 절.
- **운영 정책 폼(v2.7)** — ① 위약금율 입력 상한이 **0~10%**입니다(`MAX_PENALTY_RATE = 0.1`,
  저장 시 `/100`으로 0~1 소수 변환). 종전엔 화면·계약서·회원 앱이 30%를 말하고 실제 공제만
  10%였습니다. ② **소급 고지**: "취소 컷오프·예약 용량·통계 기준은 이미 잡힌 예약과 기록에도
  바로 적용돼요. 위약금율만 계약 시점 값으로 고정돼 기존 계약은 그대로입니다." 컷오프를
  **올릴 때만** 확인 모달을 세웁니다(내리는 방향은 회원에게 불리해지지 않습니다). ③ **바뀐
  필드만 전송**합니다 — 서버는 원래 머지 시맨틱인데 폼이 항상 10필드를 보내 그 보호를
  무력화하고 있었습니다(다른 창에서 먼저 저장한 값을 통째로 되돌림). 비교 기준선은 마운트
  시점에 동결하고, 저장 버튼 라벨이 `저장 (N개 항목)`으로 변경 건수를 노출합니다.
  ④ 홀딩 상한 2개는 **회원 셀프 홀딩에만** 걸린다는 안내를 필드 옆에 답니다(어드민에서 거는
  홀딩은 상한을 지나지 않습니다).
- **고정 스케줄 삭제를 계약 v2.3에 맞춤** — 확인 문구가 서버 동작과 **정반대**였습니다("규칙만
  삭제됩니다 — 이미 생성된 선행 예약은 남아 있어요"). 실제로는 그 규칙이 만든 **미래 confirmed
  예약이 함께 취소**되므로(무차감 — 노쇼 유예 소진 없음, 지난 회차는 이력으로 보존), 그 말을
  믿고 지운 대표는 회원 4주치가 통보 없이 사라진 걸 회원 전화로 알게 됩니다. 셋을 함께 고쳤습니다:
  ① 확인 문구를 사실대로 쓰고 **삭제 전에 몇 건이 취소되는지 세어** 보여줍니다(표의 "예정 회차"
  열 + 확인 박스 문구 — 서버와 같은 판정: `recurring_id` 일치 · confirmed · 아직 시작 전).
  ② `deleteRecurring`이 `req<void>`를 버리고 **`200 {cancelled, kept}`를 읽어** 결과를 표시합니다
  ("예정 예약 N건을 함께 취소했어요(무차감) · 지난 M건은 그대로 뒀어요"). v1엔 회원 통보 채널이
  없어 **이 숫자가 대표가 회원에게 알릴 유일한 근거**라 함께 "직접 연락해주세요"를 답니다.
  ③ **`?keep_bookings=true` 옵트아웃**을 확인 단계의 체크박스로 노출합니다("이미 잡힌 회차는
  그대로 두기") — "규칙만 끊고 합의된 회차는 진행"이 실제 운영에 있어 서버가 열어 둔 길입니다.
- **만료된 고정 스케줄 정리** — 목록을 `?include_expired=true`로 부릅니다. 서버가 만료 규칙을
  기본 목록에서 숨기는 바람에 **어드민에서 지울 방법이 자체가 없어** 유령 규칙이 쌓였습니다
  (v2.3이 이 파라미터를 만든 이유가 바로 그것입니다). 만료 행은 "만료" 배지 + 목록 아래쪽으로
  내려 살아있는 규칙과 섞이지 않게 하고, 확인 문구도 갈립니다 — 취소될 미래 예약이 없으므로
  "규칙만 정리되고 지난 회차는 기록으로 남아요"라고만 말합니다(파괴적 경고를 남발하지 않습니다).

> ⚠ **운영 영향 — 데스크는 대표(owner) 계정으로 운영하세요.** 계약 v2.5에서 tap 체크인이
> **담당 예약으로 좁혀졌습니다**(`trainer`가 남의 예약을 체크인하면 403 — complete/noshow와
> 같은 규칙). 데스크 태블릿을 트레이너 계정으로 로그인해 쓰고 있었다면 다른 코치의 회원을
> 체크인할 수 없습니다. 대시보드 "오늘 일정"은 트레이너에게 **본인 수업 행만** 보여주므로
> 버튼이 사라진 것처럼 보일 뿐 별도 안내가 나오지 않습니다(행 자체가 없습니다).
